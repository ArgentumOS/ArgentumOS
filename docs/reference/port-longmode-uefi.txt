FNX: 64-bit long mode + direct UEFI boot
===========================================

Design document for porting the Fiwix kernel (32-bit i386) to run natively in
x86-64 long mode, booted directly from UEFI firmware without GRUB.

Status: initial design (2026-08). Decisions marked [D] were confirmed with the
project owner; the rest are proposals to be validated during implementation.


1. Goal and scope
-----------------
Goal: FNX boots on x86-64 UEFI firmware (QEMU/OVMF first, real hardware
later) as a long-mode kernel, keeping all existing 32-bit user space working.

Confirmed decisions:
  [D] User-space ABI: 32-bit. The kernel runs in long mode; user processes run
      in compatibility mode (CS with L=0) using the existing int 0x80 ABI.
      This is the Linux IA32-emulation model and preserves the whole FiwixOS /
      newlib / SVGAlib 32-bit ecosystem and Fiwix's "Linux 2.0 i386 ABI"
      compatibility feature.
  [D] Boot method: EFI-stub style. The kernel image itself is a PE32+ UEFI
      application (like Linux's EFI stub). One artifact, no separate loader.
  [D] Session plan: design doc + QEMU/OVMF harness + -m64 type-model sweep
      first; boot code (UEFI stub, long-mode MM) in later milestones.

Non-goals (for now): SMP, 64-bit user space, UEFI Runtime Services, ACPI
tables, IOMMU, KASLR, >4GB RAM support.

Why it is possible: almost all device drivers are pure C + port I/O, the VFS
and filesystems are ISA-neutral, and the scheduler logic is portable. What is
not portable: the boot path, the paging layer, the GDT/IDT/TSS layout, the
syscall entry, and every place a pointer is squeezed into a 32-bit integer.


2. Current architecture (what gets replaced)
--------------------------------------------
- Boot: kernel/boot.S - Multiboot v1 header, temporary GDT, enables paging
  (CR0 PG/WP/AM/NE/MP), calls bss_init(), gdt_init(), then start_kernel() in
  kernel/main.c. Kernel linked at physical 1MB (KERNEL_ADDR), virtual
  PAGE_OFFSET (0xC0000000 = 3GB/1GB, or 0x80000000 with CONFIG_VM_SPLIT22),
  see include/fnx/linker.h and fnx.ld.
- Boot info: kernel/multiboot.c parses the Multiboot info structure: cmdline,
  E820-style mmap (consumed by mm/bios_map.c bios_map_init()), initrd modules,
  ELF section headers (kernel symbol table), VBE framebuffer info.
- Paging: 2-level (10-bit PD / 10-bit PT indices), 4KB pages only, whole RAM
  identity-mapped at PAGE_OFFSET. mm/memory.c (kpage_dir, P2V/V2P),
  mm/page.c (page cache), mm/fault.c (demand paging + CoW), mm/mmap.c.
- Segments: GDT with flat 32-bit code/data + TSS (kernel/gdt.c, idt.c).
- Syscall ABI: int 0x80, Linux 2.0 i386. Entry in kernel/core386.S: the
  SAVE_ALL frame (gs,fs,es,ds,edi,esi,ebp,esp,ebx,edx,ecx,eax + CPU-pushed
  err,eip,cs,eflags,oldesp,oldss) IS struct sigcontext (include/fnx/
  sigcontext.h), so do_syscall() and trap_handler() overlay the frame.
- Context switch: kernel/sched.c context_switch() -> do_switch() in
  core386.S: pusha/pushfl, saves ESP/EIP to the software struct i386tss
  (inside struct proc), ltr + reload CR3. Not a hardware task switch.
- User ABI structs: sigcontext, old_stat/new_stat/stat64, fd_set, iovec,
  syscall numbers - all sized for 32-bit userland.
- ELF loader: fs/elf.c loads ELF32 (EM_386) executables only.

Everything above except the user ABI structs and the filesystems/drivers is
replaced or rewritten in this port.


3. Target architecture
----------------------

3.1 Boot: UEFI EFI-stub entry
- The kernel is linked as ELF64 and converted to PE32+ (objcopy --oformat
  pei-x86-64 / ld -m i386pep) with a UEFI application entry point (new
  .S/.c stub, e.g. kernel/efi_stub.c + kernel/boot64.S).
- The firmware starts us in long mode with paging on (identity map),
  interrupts possibly enabled, and a UEFI stack. The stub must not assume
  anything about the firmware's page tables or GDT.
- Stub responsibilities, in order:
  1. Set up its own stack (fixed physical area, e.g. the old kernel stack
     region at 0x10000..0x20000).
  2. Query the environment: GetMemoryMap(), GetImageInfo, LoadOptions
     (command line), GOP frame buffer info if present, system table pointer.
  3. Build the handoff structure: translate EFI memory descriptors into the
     E820-style map bios_map_init() expects (type mapping table below), copy
     the command line, record framebuffer info, save the initrd location if
     provided (documented but optional in M1).
  4. Relocate the kernel image to its linked physical base (KERNEL_ADDR,
     1MB) with AllocatePages(AllocateAddress) or a copy after ExitBootServices
     when we own all memory.
  5. Install our own 4-level page tables (identity map for low physical +
     high mapping of the kernel at its virtual base), a GDT64 with flat
     64-bit kernel segments, TSS, and an IDT64 with the exception/IRQ gates
     (this is the M3 milestone; until then the stub keeps a minimal IDT).
  6. Disable interrupts, call ExitBootServices(ImageHandle, MemoryMapKey)
     with the map from step 2, and enter the C entry point
     start_kernel() (reused) or start_kernel64() with the handoff struct.
- Memory map type translation (EFI -> E820):
    EfiConventionalMemory / EfiBootServicesCode|Data -> AVAILABLE
    EfiReservedMemoryType / EfiMemoryMappedIO / ...       -> RESERVED
    EfiACPIReclaimMemory                                  -> ACPI_RECLAIMABLE
    EfiACPIMemoryNVS                                      -> NVS
  (Multiboot constants: MULTIBOOT_MEMORY_AVAILABLE=1, _RESERVED=2,
   _ACPI_RECLAIMABLE=3, _NVS=4.)
- Early console: reuse the existing VGA text console (identity-mapped
  0xB8000) exactly as today; GOP support is optional polish later. Serial
  console (console=/dev/ttyS0) keeps working.
- The old Multiboot path (boot.S, multiboot_header) and the multiboot parsing
  are kept for the 32-bit build and kexec only, and may be dropped (or moved
  behind CONFIG_LEGACY_MULTIBOOT) once the 64-bit build is self-hosting.
  kexec is CONFIG_KEXEC=off today; decide in M7 whether to port or drop it.

3.2 Paging (long mode)
- Move from 2-level to 4-level paging: PML4/PDPT/PD/PT, 4KB pages (2MB pages
  optional later for the kernel mapping).
- Kernel virtual base for the 64-bit build: PAGE_OFFSET becomes
  0xFFFFFFFF80000000 (canonical -2GB), keeping the "kernel at high addresses,
  P2V/V2P translation" idea. V2P(addr) = addr - PAGE_OFFSET still works as
  wraparound unsigned arithmetic on 64-bit addresses.
  CONFIG_VM_SPLIT22 is a 32-bit-only concept and is dropped in 64-bit mode.
- mm/memory.c's page-table code is rewritten as the 64-bit variant (new file
  mm/memory64.c or #ifdef'd); the rest of the MM layer (page cache, buddy,
  fault, mmap, CoW, kswapd) carries over with type widening only.
- Demand paging and Copy-on-Write work unchanged at 4KB granularity.
- Reserve a small identity-mapped low window for legacy BIOS data area (EBDA,
  0x400..0x1000), the ATA/BIOS hacks that touch low memory, and the VGA
  framebuffer.

3.3 GDT / IDT / TSS
- GDT64: null, 64-bit kernel code (L=1), kernel data, 32-bit user code
  (L=0, DB=1, DPL=3), user data (DPL=3), TSS. Long-mode segments are flat and
  base/limit are ignored for code/data; only the TSS descriptor carries real
  info (64-bit base, 16-bit limit - different layout from the 32-bit
  descriptor, see SD_TSSPRESENT handling in kernel/gdt.c).
- IDT64: 16-byte gate descriptors (offset 64-bit). The int 0x80 gate becomes
  a long-mode interrupt gate whose handler is the compat syscall entry.
- TSS64: rsp0 (64-bit kernel stack pointer), plus I/O bitmap. The software
  struct i386tss in struct proc becomes a 64-bit register save area
  (struct kernel_frame or similar) - see 3.5.

3.4 Syscall ABI with 32-bit user space (compat mode)
- User code runs in compatibility mode (32-bit CS). All existing 32-bit
  binaries and the existing syscall numbers/structures keep working.
- Entry: int 0x80 from compat mode. In IA-32e mode the CPU always pushes the
  64-bit interrupt frame (SS,RSP,RFLAGS,CS,RIP + err), regardless of the
  caller's mode. The handler must translate that into the frame the C code
  expects. Two options:
    a) Keep struct sigcontext as the kernel frame and write an entry stub
       that builds it from the 64-bit frame (move rbx->ebx, ..., 32-bit
       eip/rsp from the compat frame). Minimal changes to signal.c,
       sys_sigreturn(), fork().
    b) Introduce a 64-bit kernel frame struct and adapt all consumers.
  Recommendation: (a) for M4 - smallest diff, since sigcontext is the 32-bit
  ABI anyway and stays 32-bit-layout.
- The kernel itself does not need the syscall instruction: its internal calls
  are direct. USER_SYSCALL (asm.h) is only used by init_trampoline() in
  kernel/init.c, which executes in user mode; in the 64-bit build that
  trampoline must run as 32-bit code. Plan: compile init.c's trampoline (or a
  copy) as a separate -m32 object and map it into the INIT process, or build
  init.c as -m32 (the rest of the kernel is -m64; a small mixed-TU build rule
  is needed). Decision deferred to M4.
- int 0x80 vs syscall: keep int 0x80 only; it is simple and fully sufficient
  for compat mode. (syscall/sysenter for 64-bit user space is a non-goal.)
- verify_address() in kernel/syscalls.c must treat compat user addresses as
  < PAGE_OFFSET (32-bit range); the vma-based logic carries over with
  addr_t widening.

3.5 Scheduler / process / context switch
- do_switch() is rewritten for 64-bit (SysV x86-64 calling convention):
  save/restore rbx, rbp, r12-r15, rsp, rip (no pusha in 64-bit); reload CR3;
  ltr stays a no-op reload. tss.rsp0 holds each process' kernel stack top.
- struct proc and struct vma address fields widen to addr_t (see section 4).
- struct i386tss (software save area) is replaced by a 64-bit register frame;
  the GDT TSS descriptor is updated per-process (base 64-bit) in set_tss().

3.6 printk
- Add real length modifiers: l = long, ll = long long, for %d/%u/%x/%X.
  Today the 'l' flag only triggers under CONFIG_PRINTK64 and reads long long;
  there are zero call sites using %ld/%lu, so redefining is safe on both
  ABIs. Addresses print with %lx + (unsigned long) cast; never %x with a
  pointer. (A %p specifier is deliberately not added - explicit casts are
  greppable and keep call sites portable.)

3.7 Drivers
- Port I/O helpers (inport_*/outport_* in core386.S) move to a 64-bit asm
  helper file; they are register-width independent (in/out are the same).
- PIT, PIC (8259), keyboard, PS/2, serial, VGA console, floppy, ATA/ATAPI
  (PIO + bus-master DMA), ramdisk, framebuffer: pure C + port I/O, port with
  type widening only. BGA/VBE code needs the GOP handoff info (or stays
  legacy VGA on OVMF).
- PCI config space access is port I/O based; unchanged.

3.8 ELF loading
- Userland stays ELF32 (EM_386) - the loader's *file format* logic is
  unchanged. The bug to fix regardless of ABI: include/fnx/i386elf.h
  typedefs Elf32_Addr/Off/Word as 'unsigned long', which silently becomes
  8 bytes under -m64 and corrupts every offset. They must be fixed-width
  (__u32/__u16). Internal address variables in fs/elf.c widen to addr_t.


4. Type-model policy (the contract for the whole port)
------------------------------------------------------
A new kernel-internal type makes the port mechanical and keeps the 32-bit
build byte-identical (ILP32: long = 32 bits):

    typedef unsigned long addr_t;   /* kernel-internal address */

Widen to addr_t (safe on 32-bit, correct on 64-bit):
- struct proc: entry_address, end_code, brk, brk_lower, sp, rss, vma_table
  (pointer field is already a pointer), sigcontext sp slot is ABI-fixed (no).
- struct vma: start, end.
- struct i386tss (and its 64-bit successor): esp0/rsp0, cr3, eip/rip, esp/rsp.
- kpage_dir (unsigned long *), kmalloc()/kfree()/bl_malloc()/bl_free()
  signatures, all P2V()/V2P()/PAGE_ALIGN()/GET_PGDIR()/GET_PGTBL() operands.
- Kernel pointer round-trips: every (unsigned int)ptr / (unsigned int)&x
  cast becomes (unsigned long)ptr / (unsigned long)&x.
- printk/sprintk/snprintk sites printing addresses: %x -> %lx.

Keep fixed-width (explicit __u8/16/32/64 or plain unsigned int/short, which
are 32-bit on both ABIs):
- Hardware/ABI layouts: multiboot info + mmap entries, VBE controller/mode
  (currently 'unsigned long' in multiboot1.h - must become unsigned int),
  PCI config, ATA identify, Elf32_* (after fix), linuxboot/kexec structs.
- 32-bit user ABI: struct sigcontext, old_stat/new_stat/stat64, fd_set
  (already unsigned int bits), struct iovec (iov_base is void* -> must become
  a fixed 32-bit layout via a compat_iovec or keep iov_base as __u32 until
  the M6 conversion pass), syscall numbers/args.
- __off_t/__size_t/__time_t/__ino_t/... stay __u32: they are the 32-bit user
  ABI. Consequence: kernel-internal file offsets stay 32-bit; >4GB file
  support is explicitly out of scope.

Verification: every milestone must keep `make` (32-bit) green; the -m64
compile-check target (make compile64, section 5) must have zero errors.
The 32-bit build is the reference oracle for behaviour during the port.


5. Build system / harness
-------------------------
- Default `make` keeps producing the 32-bit kernel (fnx) - always green.
- `make compile64`: compile all C sources with the 64-bit flags
  (-m64 -march=x86-64 -mno-red-zone -mno-sse -mno-sse2 ...) into
  .build/64/*.o without linking - the type-sweep verifier.
- `make build64` (M1+): link fnx ELF64, convert to PE32+
  (fnx.efi), plus the handoff.
- `make ovmf`: fetch OVMF without root: apt-get download ovmf, dpkg-deb -x
  into .build/ovmf (no sudo needed; the container has no root).
- `make run`: QEMU smoke test of the current 32-bit kernel (QEMU's built-in
  Multiboot loader via -kernel, no GRUB needed for development).
- `make run-uefi`: QEMU with -bios OVMF.fd (baseline: proves firmware runs;
  from M1 on it boots the PE32+ kernel placed as EFI/BOOT/BOOTX64.EFI on a
  FAT drive image).
- QEMU binary: ~/.local/share/fnx-qemu-tools/usr/bin/qemu-system-x86_64
  run directly (the PATH wrapper needs flatpak-spawn and is broken); env:
  LD_LIBRARY_PATH=<toolroot>/usr/lib/x86_64-linux-gnu,
  -L <toolroot>/usr/share/qemu.

   SAVE_FLAGS/GET_CR2/GET_ESP, offsetof fix, ~300 pointer-cast sites
   converted to addr_t). Acceptance: make run shows the kernel banner
   (multiboot smoke test) - VERIFIED; make compile64 reports no errors and
   no -Wpointer-to-int-cast warnings - VERIFIED. The 32-bit build is
   byte-identical in behavior (same binary size).
   NOTE: CONFIG_NET was turned off (#undef) in include/fnx/config.h to
   unblock the default build - the net layer's ext_* driver hooks are still
   missing (in-progress v1.8.0 work). Re-enable when a driver lands.
   Remaining cosmetic noise under -m64: ~140 -Wint-to-pointer-cast
   warnings from the sanctioned "(void *)kmalloc()" pattern - benign.
M1 - 64-bit boot: build64 produces a PE32+ kernel; it boots under OVMF on
   QEMU and prints the banner from a long-mode C entry. Acceptance: banner +
   "Safe to Power Off" reachable via UEFI.
   STATUS (2026-08 session): DONE. kernel/boot64/efi_stub.c collects the EFI
   memory map (GetMemoryMap x2 + AllocatePool), masks the PICs, calls
   ExitBootServices(), and enters kernel64_main() (kernel/boot64/main64.c) which
   prints the banner, firmware vendor/rev, and the full memory map over COM1
   at 115200, then halts ("M1 OK: FNX booted from UEFI into long mode").
   VERIFIED under QEMU/OVMF (make run-uefi path; run headless via
   tools/qemu.sh with -nographic -monitor none). The stub keeps the
   firmware's identity-mapped page tables (no own paging until M2).
   M1 lessons (all verified by debugging the boot):
   - The EFI stub MUST be compiled -fPIC (RIP-relative). With -fno-pie gcc
     hardcodes absolute 32-bit addresses for string literals; PE base
     relocations cannot fix up immediates, so the image only works when
     loaded at the preferred ImageBase, which UEFI does not guarantee.
     Also -fno-semantic-interposition (avoids a GOT in the PE) and: never
     take the address of a non-static function, and do not use non-static
     globals, in stub code - gcc routes both through the GOT and
     ld -m i386pep resolves GOTPCREL by loading FROM the symbol's address
     (e.g. &efi_main read the first 8 bytes of the function's code).
     Use get_rip() (lea 0(%%rip)) for self-addresses and pass the system
     table as a parameter instead of a global.
   - EFI_SYSTEM_TABLE layout: Signature(0), Revision(0x10),
     FirmwareBuildNumber(0x14), FirmwareVendor(0x18), FirmwareRevision(0x20),
     ... BootServices(0x60), NumberOfTableEntries(0x68), ConfigurationTable
     (0x70). The struct in include/fnx/efi.h originally had a bogus
     HeaderSize/CRC32/Reserved block (that is EFI_TABLE_HEADER, not part of
     the system table) which shifted every field by 8 and made BootServices
     read NumberOfTableEntries -> calls through garbage (boot crashed with
     #UD at a garbage RIP).
   - EFI error statuses carry bit 63 (EFI_ERROR_MASK): EFI_BUFFER_TOO_SMALL
     is 0x8000000000000005, not 5. Compare against EFI_SUCCESS or mask.
   - EFIAPI functions follow the MS x64 ABI: RDI/RSI/RBX/RBP/R12-R15 are
     callee-saved, so the compiler may keep C locals (e.g. &desc_size) in
     RDI across boot-services calls - do not assume SysV clobbering.
   - The 32-bit build and make compile64 are unaffected (efi.h is only
     included by kernel/boot64/).
M2 - long-mode MM: 4-level paging, kpage_dir -> pml4, P2V/V2P, demand paging
   + CoW working under the 64-bit build. Acceptance: page faults handled,
   kmalloc/mmap exercised, mem_stats sane.
   STATUS (2026-08 session, phase A DONE): kernel/boot64/paging64.c installs the
   stub's own 4-level page tables after ExitBootServices(): PML4[0] and
   PML4[511] share a PDPT whose entries 0 and 510 (PDPT_INDEX of
   PAGE_OFFSET64) share a PD covering the low 1GB in 2MB pages. This gives
   an identity map of the low 1GB plus the same memory at PAGE_OFFSET64
   (0xFFFFFFFF80000000); CR3 is switched and execution jumps to the
   high-half alias of a static high_entry() (get_rip() then reports
   0xFFFFFFFF86xxxxxx), demos P2V64/V2P64 (round-trip 0x100000 <-> 0xFFFFFFFF80100000),
   and re-enters kernel64_main(), whose direct call lands at the high alias
   too - so the whole banner/memory-map output runs from the high half.
   VERIFIED under QEMU/OVMF: 'M2-A OK: 4-level paging active, kernel mapped
   at PAGE_OFFSET64 (0xFFFFFFFF80000000), halting.' Page tables live in the
   stub's .bss (physical == runtime address under the firmware identity
   map); the mapping is fixed low-1GB (2MB pages) - no dynamic allocation
   yet.
   STATUS (2026-08 session, phase B DONE): kernel/boot64/mm64.c adds dynamic
   4KB-page mapping and a physical page allocator. The allocator is a
   first-fit bitmap over usable RAM below 1GB (EfiConventionalMemory /
   EfiBootServicesCode / EfiBootServicesData, all free after
   ExitBootServices), with the low 1MB, the loader image span (LoaderCode +
   LoaderData including the gap pages that hold the stub's .bss tables), and
   the current stack window marked used. map_page64()/unmap_page64()/
   virt_to_phys64() walk PML4->PDPT->PD->PT and allocate intermediate table
   pages on demand; the demo maps 4 pages at 0xFFFFFFFFC0000000 (PDPT entry
   511, beyond the fixed 1GB map - the whole hierarchy is built
   dynamically), writes/reads a byte pattern, cross-checks virt_to_phys64,
   unmaps and frees. VERIFIED under QEMU/OVMF: 'M2-B OK: 4KB-page allocator
   and dynamic mapping verified, halting.' (free pages 30948 -> 30946 after
   the demo: 4 data pages freed, 2 intermediate table pages stay mapped -
   accounting is exact). Shared serial/asm helpers moved to
   kernel/boot64/serial64.h (static, __attribute__((unused))).
   STATUS (2026-08 session, phase C DONE): kernel/boot64/idt64.c installs an
   IDT64 for vectors 0-31: 32 tiny asm stubs (ISR_NOERR/ISR_ERR gas macros,
   16-byte aligned) push a unified error-code slot + the vector number and
   jump to isr_common64, which saves the 15 GPRs, calls isr64_dispatch(),
   restores them and iretq's. The dispatcher handles #PF specially: if CR2
   is the known demand page (0xFFFFFFFFD0000000) it allocates a page and
   maps it via mm64.c, then returns so iretq retries the faulting access
   (real demand paging); any other vector/fault prints vector, error, rip,
   cr2, rsp and halts. The stub addresses are hidden-visibility externs
   (visibility("hidden") -> RIP-relative, no GOT) collected into a static
   stub_addr[32] table whose absolute values get PE base relocations (the
   .reloc section is back, 0x48 bytes, and OVMF applies it). kmalloc64()/
   kfree64() were added to mm64.c (page allocator -> P2V64 kernel-virtual
   addresses). VERIFIED under QEMU/OVMF: 'M2-C OK: IDT64 + page-fault
   demand paging + kmalloc64 verified, halting.' (kmalloc64(8192)
   write/read OK; first touch of the demand page faulted, was mapped, and
   the retried access read back 0x5A with the expected phys).
   STATUS (2026-08 session, phase D DONE): map_page64() now splits a 2MB
   huge page on demand (allocates a PT, fills 512 entries from the 2MB
   physical base with the huge entry's flags minus PS, replaces the PD
   entry, flushes the TLB) - so 4KB pages can be placed anywhere, including
   inside the initially 2MB-mapped low-1GB regions. MMIO above 1GB maps
   through the normal on-demand path (demo: local APIC at 0xFEE00000 via
   PML4[0] -> PDPT[3] -> PD -> PT, APIC ID read from 0xFEE00020). mem stats
   (total/free pages) printed. VERIFIED under QEMU/OVMF: 'M2-D OK: 4KB
   pages inside 2MB regions, MMIO above 1GB, mem stats verified, halting.'
   (split demo at 0xFFFFFFFF80800000 -> allocated page 0x102000, walk
   confirms; APIC ID 0x00000000; total 31141 / free 30935 pages).
   STATUS (2026-08 session, phase E DONE): kmalloc64/kfree64 upgraded to a
   slab allocator over the bitmap page allocator - size classes 16..2048
   (8 buckets), each slab page carved into fixed slots linked through a
   free list, with a 16-byte kmem_hdr {magic,bucket,npages} at each page
   start; requests > 2048 bytes take whole pages (KMEM_HUGE header).
   kfree64(void*) recovers the size/bucket from the header (bad-magic
   panics) instead of taking a page count. kmem_stats64() prints per-class
   pages/free slots. VERIFIED under QEMU/OVMF: 'M2-E OK: slab kmalloc/kfree
   with size tracking verified, halting.' (8/40/200/1000/3000/9000-byte
   objects land in classes 16/64/256/1024/huge/huge with exact slot counts,
   e.g. class 16: 255 slots 1 used; after reverse-order free the counts
   return to full).
   STATUS (2026-08 session, phase F DONE): copy-on-write. paging64_init()
   now sets CR0.WP (supervisor writes to read-only pages fault). The #PF
   handler in idt64.c distinguishes cases by the error code: write to a
   read-only page (P and W set) at COW_VA -> allocate a page, copy the old
   contents, remap the VA read-write, flush the TLB (drop the stale RO TLB
   entry) and return so iretq retries the write into the detached copy;
   not-present access (P clear) at DEMAND_VA -> demand-map a fresh page;
   anything else panics. VERIFIED under QEMU/OVMF: 'M2-F OK: copy-on-write
   + demand paging verified, halting.' (write to 0xFFFFFFFFD0200000 faulted,
   moved to a new phys 0x10d000, read back 0xEE, original page's seed
   0xA5/0x5A intact - detached).
   M2 acceptance is now met: 4-level paging, P2V/V2P, demand paging AND
   copy-on-write working, page faults handled, kmalloc exercised, mem_stats
   sane. Remaining M2-side work is code migration: porting mm/memory.c to a
   64-bit variant (mm/memory64.c or #ifdef) when the real kernel starts
   linking in the 64-bit build (M3); user-space faults and IRQ gates 32-255
   need the M3 TSS/IDT work.
M3 - interrupts/scheduling: GDT64/IDT64/TSS64, PIC, PIT, timer ticks,
   64-bit context switch; kswapd + kbdflushd run round-robin. Acceptance:
   kernel threads schedule; clock advances.
   STATUS (2026-08 session, M3 DONE - acceptance met): GDT64 (8-byte slots:
   NULL/kcode/kdata/ucode/udata/fw-data@0x30/fw-code@0x38/TSS@0x40) + TSS64
   (packed, RSP0 at SDM offset 4; base = identity alias of the static TSS)
   installed with lgdt+ltr; the firmware's CS=0x38/SS=0x30 selectors are
   kept (cached) - matching 0x30/0x38 descriptors are provided so the IDT

7. Risks and open questions
---------------------------
- int 0x80 frame translation in compat mode is the trickiest ABI bit; option
  (a) in 3.4 keeps the blast radius small but the asm must be right.
- The 'l' printk redefinition must be verified on the 32-bit build output
  (it is invisible today because no call site uses %ld/%lu).
- Firmware memory map edge cases: kernel image placed above 4GB by the
  firmware, low-1MB reserved regions, ACPI reclaimable vs NVS handling,
  EBDA preservation (Fiwix already saves 256 bytes of BDA).
- Non-canonical addresses: all 64-bit pointer arithmetic must stay below
  2^47; mistakes produce GP faults that are hard to debug without a serial
  console - plan to enable CONFIG_QEMU_DEBUGCON early in M1.
- QEMU/OVMF vs real hardware differences (GOP, RSDP, PCI topology).
- Mixed -m32/-m64 translation units (the init trampoline) need a Makefile
  rule that does not disturb the default 32-bit build.
- struct iovec: decide between a compat_iovec conversion at the syscall
  boundary (Linux-style) and keeping the ABI struct 32-bit-layout internally.
