# Sterling syntax — a modern surface over Objective-C (DRAFT v0)

Status: **DRAFT (2026-09), for review.** The surface only; no compiler yet. Every
example shows the Sterling source beside **the Objective-C it is defined to emit**.
`docs/design/sterling-plan.md` is the build plan; this document is the language.

## 0. The one rule

**There is no Sterling semantics.** Every construct here is a rename or a
re-spelling of an Objective-C concept, and the test for admitting a construct is
whether it can be stated as *"this ObjC thing, spelled this way."* If it cannot,
it is out of scope — not deferred, out.

The reason is the target: the runtime (`libobjc2`) and the class library
(the Argentum Foundation) are ours, already built, and already the thing we want
to write code against. The language's contribution is **ergonomics**, not
capability. A feature ObjC cannot express is a feature Sterling must not invent,
because inventing one is exactly how a "nicer ObjC" turns into a second
language with its own runtime — the outcome this project exists to avoid.

**One exception, and it is the only one: a *checked* operation.** A construct
that is an *assertion about the code* — something the compiler cannot prove but
the programmer can — is admitted even though ObjC has no spelling for it, because
it *removes* a case rather than adding a capability. There are three, and they are
one family, each emitting a runtime trap: `x!` for a null (§6), `as!` for a
conversion (§7.46), and arithmetic overflow (§7.40). Anything that *adds*
behaviour is still out.

Corollary: the compiler is a **transpiler**. It emits `.h` + `.m`; clang does
the rest.

## 1. The specimen

```sterling
class MyClass: Object {
    property myValue: Int64
    readonly property dynamicValue: Float32 {
        return 0.1;
    }

    class method baz(arg1: Bool, arg2: String) -> Void {
        callSomeFunc(arg: arg1);
    }

    method foobar(argname: Int32, arg2: Bool) -> Bool {
        return false;
    }
}
```

## 2. What it emits

`MyClass.h`:

```objc
/* MyClass.h — generated by sterlingc from MyClass.ag. Do not edit. */
#import <Foundation/Foundation.h>

_Pragma("clang assume_nonnull begin")

@interface MyClass : NSObject

@property (nonatomic, assign) int64_t myValue;
@property (nonatomic, readonly) float dynamicValue;

+ (void)baz:(BOOL)arg1 arg2:(NSString *)arg2;
- (BOOL)foobar:(int32_t)argname arg2:(BOOL)arg2;

@end

_Pragma("clang assume_nonnull end")
```

`MyClass.m`:

```objc
/* MyClass.m — generated by sterlingc from MyClass.ag. Do not edit. */
#import "MyClass.h"

/* Declared elsewhere; sterlingc imported it. The parameter's name is `arg`. */
extern void callSomeFunc(BOOL arg);

@implementation MyClass

+ (void)baz:(BOOL)arg1 arg2:(NSString *)arg2
{
	callSomeFunc(arg1);
}

- (BOOL)foobar:(int32_t)argname arg2:(BOOL)arg2
{
	return NO;
}

- (float)dynamicValue
{
	return 0.1f;
}

@end
```

Notes that follow from the mapping (not special cases):

- `property myValue: Int64` **stores**: `@property` + auto-synthesis gives the
  ivar; nothing is emitted into `@implementation` for it.
- `readonly property dynamicValue { … }` **declares no storage**: the `.h` property is
  `readonly` and the `.m` carries the getter, the block *being* the getter (§7.54). The
  keyword is how read-only is *written* (§5) — there is no implicit form — and a `set` block
  adds the setter, after which `readonly` is an error.
- The memory qualifier is **inferred from the type**: a class type is `strong`,
  a scalar/struct is `assign`. It is written when wanted, and where depends on what it
  is — `weak` as a prefix (`weak property x: Foo`), `copy` in the parenthesis (§7.52).
- Every declaration is non-null by default — references and, since §7.62, scalars and structs too —
  so the header opens a clang **assumed-non-null region** (§4) — `arg2: String` above is
  `NSString * _Nonnull` without saying so, and an `Int32?` carries §7.62's pair-struct rather than a
  sentinel.
- The `0.1` in the getter is a `float` because the getter's type says so, not
  because floats default to `float` — a literal takes the expected type where
  there is one (§4), and only falls back to the default `Float64` when there is
  not.
- `callSomeFunc(arg: arg1)` is a **C function** — the second outcome of §7.42's rule,
  `MyClass` having no method of that name: labels are checked against the declared
  parameter names and then **dropped**, since C has no selectors. The label is
  documentation the compiler enforces.

## 3. The concept map

The whole language, in one table. Left is the thing; right is how Sterling spells
it.

| Objective-C | Sterling |
|---|---|
| `@interface X : Y <P>` … `@end` | `class X: Y, P { … }` |
| `+ (R)m…` class method | `class method m(…) -> R` |
| `- (R)m…` instance method | `method m(…) -> R` |
| selector `foobar:arg2:` | `method foobar(argname: T, arg2: U) -> R` |
| `[o foobar:1 arg2:YES]` | `o.foobar(argname: 1, arg2: true)` |
| `[o foo]` (no arguments) | `o.foo` |
| `[MyClass baz:1]` (a class receiver) | `MyClass.baz(arg1: 1)` |
| `@property (nonatomic) int64_t x;` | `property x: Int64` |
| `@property (nonatomic) Foo *x;` | `property x: Foo` (`strong`) |
| `@property (nonatomic, weak) Foo *x;` | `weak property x: Foo` |
| `@property (nonatomic, copy) NSString *x;` | `copy property x: String` |
| `@property (nonatomic, readonly) float x;` | `readonly property x: Float32` |
| computed property | `property x: T { get { … } set { … } }` — or `readonly property x: T { … }` for a getter-only one (§7.54) |
| `@protocol P <Q>` … `@end` | `protocol P: Q, R { … }` (§7.45) |
| `@interface X (Name)` category | `extension X { … }` |
| `id` | `AnyObject` |
| `id<C>` (a protocol-qualified object) | `C` — a protocol name is a type (§7.45) |
| `instancetype` | `Self` |
| `nil` / `Nil` / `NULL` | `nil` |
| `YES` / `NO` | `true` / `false` |
| `T x = e;` (local) | `var x: T = e` — or `var x = e` when `e` carries the type |
| `const T x = e;` / `T * const x = e;` (local) | `let x: T = e` — or `let x = e` |
| `NSInteger x = 3;` (the literal default) | `let x = 3` (§4) |
| `if (x != nil) { … }` | `if let v = x { … }` / `if var v = x { … }` |
| `if (!x) { … }` early exit | `guard let v = x else { … }` / `guard var v = x else { … }` |
| `typedef struct { … } Foo;` | `struct Foo { … }` |
| `typedef struct { struct Base; … } D;` (`-fms-extensions`) | `struct D: Base { … }` |
| `typedef enum E { a, b } E;` | `enum E { a b }` |
| `typedef enum F : uint8_t { a, b } F;` | `enum F: UInt8 { a b }` |
| tagged union — `struct { … tag; union { … } value; }` | `enum E { a(x: Int32) b }` |
| bare `valueOne`, or prefixed `E_valueOne` for a union | `E.valueOne`, or `.valueOne` where the type is known (§5) |
| `(NSRange){ .location = 0, .length = 3 }` | `Range(location: 0, length: 3)` |
| `float Point_length(const Point *self);` | `method length() -> Float32` (in `struct Point`) |
| `Point_moveTo(&p, 1, 2);` | `p.moveTo(x: 1, y: 2)` |
| block type `void (^)(int32_t)` | `(Int32) -> Void` |
| block literal `^{ … }` | `{ … }` (closure) |
| `@selector(foobar:arg2:)` | `#selector(foobar(argname:arg2:))` |
| `@autoreleasepool { }` | `autoreleasepool { }` |
| `@synchronized (o) { }` | `synchronized (o) { }` |
| `@try` / `@catch` / `@finally` | `try` / `catch` / `finally` |
| `- (BOOL)f:(NSError **)e` | `method f() throws -> Bool` |
| C function `void f(int32_t a)` | `func f(a: Int32) -> Void` |
| `@"…"` | `"…"` (emitted as an `NSString` literal) |
| `@[]` / `@{}` / `@()` | `[…]` / `[k: v]` / `n` |
| `@class X;` forward declaration | automatic — the emitter manages it |
| `#import "X.h"` | `import X` |
| `self` / `super` | `self` / `super` |
| *(nothing — see §0's exception)* | `x!` force unwrap (§6) |

## 4. Types

Fixed-width and explicit; the `*` never appears in Sterling source.

| Sterling | emitted C |
|---|---|
| `Bool` | `BOOL` |
| `Int8` `Int16` `Int32` `Int64` | `int8_t` `int16_t` `int32_t` `int64_t` |
| `UInt8` `UInt16` `UInt32` `UInt64` | `uint8_t` … `uint64_t` |
| `Float32` / `Float64` | `float` / `double` |
| `Float` / `Double` | `float` / `double` — short names for `Float32` / `Float64`, as `Int` is for `NSInteger` (§7.38) |
| `Int` / `UInt` | `NSInteger` / `NSUInteger` |
| `Void` | `void` |
| `AnyObject` | `id` |
| `Self` | `instancetype` |
| `String`, `Array`, `Dictionary`, `Number`, `Error`, … | `NSString *`, `NSArray *`, … |
| `String?` | `NSString * _Nullable` |
| `(Int32) -> Void` | `void (^)(int32_t)` |
| `((Int32) -> Void)?` | `void (^ _Nullable)(int32_t)` |
| `struct Foo` | `Foo` (a C struct type, by value) |
| `enum Foo` | `Foo` — a C enum, or a C **struct** when it has associated values (§5) |
| `UnsafeMutablePointer` | `void *` |
| `UnsafePointer` | `void const *` |
| `UnsafeMutablePointer<T>` / `UnsafePointer<T>` | `T *` / `T const *` (§9.18) |
| `Character` | `char` — one UTF-8 byte; C's `char` is a type of its own, and a one-byte `'a'` literal is a `Character` while a longer one is a `String` (§9.19) |
| `CString` / `MutableCString` | `const char *` / `char *` (§7.31) |

**Every class in the prelude drops Cocoa's `NS` in Sterling and keeps it at the C
level** (decided, 2026-09): `NSString` is `String`, `NSArray` is `Array`,
`NSDictionary` is `Dictionary`, `NSError` is `Error`, `NSObject` is `Object`, and so
on by that one rule. It is a *renaming*, not a bridging — the Sterling name **is** the
class, so nothing converts and no copy is made (§7.31). `NSInteger` / `NSUInteger`
are typedefs rather than classes, and keep both their C names and their Sterling ones
(`Int` / `UInt`, above).

`Character` is **not** `UInt8`: it is C's `char`, a third type beside `signed
char` / `unsigned char`, and it is **signed on this target** — the `unsigned char`
in this section's `BOOL` note is a fact about `BOOL`'s carrier, not about `char`
(measured: `CHAR_MIN` is −128, §9.19). Its pointer pair is `CString` /
`MutableCString`, and there the plain name is the read-only one, as §7.31 says.

Every *declaration* writes its width: there is no type name whose width is
guessed, and the four **short names** — `Int`/`UInt` for `NSInteger`/`NSUInteger`,
and `Float`/`Double` for `Float32`/`Float64` (§7.38) — exist only because the C side
spells them so. Two things are therefore implicit, and only two
(decided, 2026-09):

- **A declaration's type may come from its initializer** instead of being written
  — `let p = Point(x: 0, y: 0)`, `let s = "text"`, `let b = true` (§5, §7.19).
- **An unsuffixed literal has a type of its own**: an integer literal is `Int`
  (`NSInteger`) and a float literal is `Float64` (`double`) — the one default
  width in the language, and what makes `let x = 3` mean `NSInteger x = 3;`.

The order between them matters. A literal takes the **expected type** wherever
there is one, and the default only where there is not: `return 0.1;` in a
`Float32` getter is a `float` (the getter's type — §2 shows the `0.1f`), while
`let x = 3` with nothing to expect falls back to `Int`.

**Literal spelling** (decided, 2026-09): digits may be grouped with **underscores**,
which are elided — `1_234` and `1234` are the same literal — and the radix prefixes
are `0x` hexadecimal, `0b` binary and `0o` octal (§7.37). An underscore may only sit
**between two digits**, and C's bare-leading-zero octal is not writable. Two of those
three prefixes are not free at the C level, which is why they are decided together
with their emission: `0x` and `0b` emit as written, and **`0o` emits as C's bare
leading zero** — `0o755` is `0755;` — because C has no `0o` at all.

**A literal's type is written on the literal when nothing else supplies it** —
`Int8(12)`, `Float(0.5)`, `Int64(47528946234536)` — and a value that cannot survive
the type it was given is an error rather than a truncation: there are no width
suffixes, so this is the only way to narrow a literal (§7.38).

### `nil`

**One null, and it is spelled `nil` — ObjC's word, as decided (2026-09).** The language does
not inherit ObjC's *other* names for it: where ObjC writes `Nil` (a null class) or `NULL` (a
null C pointer), Sterling writes `nil` — a class is an object and a raw pointer is a type the
same word already covers (§4's table). So the surface has one null, usable wherever a
**nullable** type is expected — `let s: String? = nil`, an argument to a `T?`, an
optional-returning call — and **not** where a `T` is wanted, which is the same rule §4's
nullability already states. **And `NULL` is not a Sterling token at all**: it is an ordinary
identifier, valid only where someone has defined it (§7.59).

**It is the *only* visible null value, and the emission converts it (decided, 2026-09, §7.59).**
One spelling in the source, and the C gets whatever its context actually needs:

| the context | the C it emits | why |
| a class type (`T?`) | `nil` | — |
| a raw pointer | `NULL` | ObjC's own spelling for a C pointer |
| a collection element | `[NSNull null]` | a null pointer cannot be an element |
| `Bool` | `false` | measured: `BOOL b = nil` is a hard error, `-Wint-conversion` |

Both pointer spellings are accepted in either position (measured: `void *p = nil` and
`int32_t *p = NULL` compile silently, and so does `Class c = Nil`), so *that* row is legibility
rather than soundness — the same surface/emission split as `0o` → `0755` and `String` →
`NSString *`. The `Bool` row is not cosmetic: a bare `nil` there does not compile at all, so
the conversion is what makes one spelling possible.

**`NSNull` still has to exist** — it is what the third row emits — and the Foundation is adding
it (2026-09). §7.31's one rule names it `Null`, and the refinement is that **`Null` is a type
and never a value**: a declaration may mention it, an author never writes it (§7.59). §9.23's
question — whether an optional can be a collection element — is answered *yes*, by that same
conversion.

### Booleans

`true` and `false` are the Objective-C booleans: `true` emits **`YES`**, `false`
**`NO`**, and their type is `Bool` — which §4 maps to `BOOL`. Both live in
libobjc2's runtime header, so the prelude's `Foundation.h` brings them in. Two
things about them are measured on this tree rather than assumed:

- **`BOOL` is not a fixed-width integer here.** libobjc2 typedefs it
  *conditionally*: `signed char` under `STRICT_APPLE_COMPATIBILITY`, `int` on
  VxWorks and Windows, and — the case for this target — **`unsigned char`**. A
  `BOOL` is therefore one byte and cannot hold `-1`, which is the classic
  Objective-C boolean trap; the language should never let one be built from a
  non-boolean.
- **`YES`/`NO` are clang's `__objc_yes`/`__objc_no`** wherever
  `__has_feature(objc_bool)` holds — it does for the 2.0 ABI — falling back to
  `((BOOL)1)`/`((BOOL)0)` otherwise. Either way the emitted `YES`/`NO` is the one
  ObjC spells.

**`Bool` stays distinct from the integer types in the source**, even though its C
carrier is a character type: `true` is not `1`, assigning an `Int32` to a `Bool`
is an error, and `let b = true` types the local by the literal rule (§7.19)
rather than falling back to `Int`. And **a condition is always a `Bool`
expression** (decided, 2026-09, §7.20): `if`, `while`, `?:` and the operands of
`&&`/`||`/`!` require `Bool`, so `if n` is an error — write `if n != 0` — and C's
`if (ptr)` idiom is `if p != nil`.

### References and values

Two rules, and everything about assignment, passing and returning follows from
them (decided, 2026-09):

- **A class instance is a *reference*.** `MyClass` denotes a pointer to an
  Objective-C object — at the runtime level, an `id`. Assigning it, passing it or
  returning it copies the *reference*, so both names then denote the same object.
- **A struct is a *value*.** Assigning, passing or returning a struct copies its
  **bytes** — C's struct assignment, and nothing more.
- A scalar is a value too, for the same reason: there is nothing to share. An
  **enum** is one of these whichever kind it is — the plain form *is* a C enum,
  and the associated-value form is a **struct** (§5) — so neither can be null.

Two things fall out of the value rule, and each is a consequence rather than a
rule of its own:

- **`StructName?` is not writable.** Nullability applies to the types that can be
  null, and a struct value cannot be. A nullable or collection-held struct must
  be boxed — `Value`, as Cocoa does (`[NSValue valueWithRange:]`).
- **A struct has no class-typed property.** ARC forbids Objective-C object
  pointers in a struct or union (clang: *"ARC forbids Objective-C objects in
  structs or unions"*) — and that is not an arbitrary restriction: it is the
  value rule. A struct is copied by bytes, and an ARC-managed pointer inside it
  could not be copied correctly. A struct's properties are scalars and other
  structs — and, for the same reason and by the same error, a tagged union's
  **associated value cannot be an object either** (§5).

The *other* difference from a class is not a consequence of the value rule but a
second decision: **a struct's methods are functions, not messages** (§5) — a
value type has no `isa`, so there is nothing to send a message to.

### Nullability

**Every type is non-nullable by default; the nullable form is `T?`.** (Decided,
2026-09 — this is *the* rule, not a per-type option.)

What it means, and where it stops:

- **It applies to the types that can be null** — class types, `AnyObject`, block
  types, and the **raw pointers** (§4's table). A raw pointer is the second family
  on this list because a `void *` genuinely can be null: so
  `UnsafeMutablePointer?` is writable, and an unmarked one is the `_Nonnull` case.
- **A scalar may be optional too — DECIDED (2026-09), superseding the paragraph
  that stood here.** The earlier text read that `Int64?` was *not writable*, on the
  ground that neither C nor ObjC has a nullable `int64_t`. That is true of the C
  level and false of the language: §7.62 makes `Int32?`, `Bool?`, `Float64?` and
  `Range?` real types by synthesising **one pair-struct per scalar type** — a value
  plus a has-value flag — so the boxed `Number?` is a *choice* rather than the only
  spelling. §7.62 admits **an imported C struct** on the same mechanism, so the
  earlier paragraph's prohibition applied to the C level rather than to this
  language — and it is the latter that governs.
- **A Sterling `enum` is the one case §7.62 does not settle.** It names scalars and
  imported C structs; an enum is neither, and §4's table lists it as its own family
  rather than as a scalar. Its representation is a scalar-sized tag, so the
  pair-struct would serve, but nobody has decided it. Left open here rather than
  resolved by inference — §9's question, not this paragraph's.
- **The emitted declarations carry the annotation.** A generated header defaults
  its whole region to non-null and writes `_Nullable` only where the source said
  `?`; so `String` emits `NSString *`, `String?` emits `NSString * _Nullable`,
  `((Int32) -> Void)?` emits `void (^ _Nullable)(int32_t)`, and the pointer pair
  emits `void * _Nonnull` / `const void * _Nullable`. The region is **clang's**,
  not a Foundation macro: `_Pragma("clang assume_nonnull begin")` … `end` (this
  tree has no `NS_ASSUME_NONNULL_BEGIN` — measured, §9.5).
  - **…and the specifiers are a clang extension too** (measured): `-pedantic`
    warns `-Wnullability-extension` on every `_Nonnull`/`_Nullable`, a `void *`
    included. So this is not a Foundation feature the emitter borrows but the same
    class of dependency as `-Wfixed-enum-extension` and `-Wmicrosoft-anon-tag` —
    **three of them now**, which is what makes a `-pedantic` decision a decision
    about the language rather than about one lowering.
- **It is only as strong as the imports — and an unannotated import is read as *nullable*
  (decided, 2026-09, §9.5).** The rule is a *declaration* promise: it says what a
  Sterling-written API answers. Where the declaration comes from a header Sterling did not write,
  the promise is the header's — and `Foundation.h` and the runtime's headers **carry no
  nullability annotations at all today** (measured: 0 across 19 headers and 434 methods), so an
  imported method's return is *unknown*. **Unknown is read as `T?`, never as non-null**: the
  compiler does not assert what it has not been told, so a nil arrives as a nil, and the
  author's `!` or binding is where it is faced. Annotating the Foundation removes those `!`s
  and changes nothing else (`foundation-plan.md` §5).
- **Four ways out of an optional, and no others** (decided, 2026-09): `x!`
  (assert — traps if null, §6), `if let` / `if var` (branch), `guard let` /
  `guard var` (early exit), and `x ?? y` (substitute — the only one that
  *produces* a plain `T` rather than getting out of the way, §6 and §7.22). §6
  states all of them; a bare `T?` is not usable where `T` is wanted.

## 5. Declarations

- **Class** — `class Name: Super, P1, P2 { … }`. `Super` may be omitted only for
  a root class, and a generated root class **must** carry libobjc2's
  `__attribute__((objc_root_class))` or `@"…"` literals are emitted as garbage
  (measured — `foundation/NSObject.h`). Sterling emits the attribute automatically
  for a class with no superclass.
  - **A class may be generic** (decided, 2026-09), and the mechanism is
    Objective-C's **lightweight generics** — a *compile-time* annotation with no
    runtime and no ABI. `class Box<T> : Object` emits `@interface Box<T> :
    NSObject`, `Box<String>` emits `Box<NSString *>`, and clang erases the
    parameter at codegen.
  - **The boundary is ObjC's own, and it is measured here.** The rule is
    *"wherever ObjC supports generics"*, and this tree's own wrapper
    (`tools/musl-clang-objc64.sh`) locates that line:
    - **A class declaration takes type parameters** — in its `@interface` and its
      `@implementation`, and in those methods' signatures (verified).
    - **A parameterized *use* works** — `Box<Root *>`, `NSArray<NSString>`
      (verified).
    - **A protocol declaration does not.** `@protocol P<T>` is parsed as a
      *conformance list* and clang answers `cannot find protocol declaration for
      'T'` (verified). A type parameter is a class feature, so `id<P>` stays
      unparameterized.
    - **A category cannot use its class's parameter.** `@interface Bag (Extra)`
      with a `- (T)last;` fails with `expected a type`, even though `Bag<T>` is in
      scope (verified) — the parameter belongs to the class, not beyond it.
    - **A type argument may be *any* type — AMENDED (2026-09).** The bullet that
      stood here read that an argument "must be an object type", with
      `NSArray<Int32>` as the canonical error. That is true of ObjC's *bare*
      lightweight generics and false of this language, which does more with the
      argument than annotate it: §7.63 **erases** for an object argument and
      **monomorphises** otherwise, so a non-object argument is not an error but a
      *different treatment*. A sized declaration makes the same point from the
      other side — §7.64's `widths[4]: Array<Int32>` is a fixed-size array of
      scalars and could not be written at all under the old rule. The corpus found
      this: five files write `Array<Int32>`, one of them with a comment reading
      "*Monomorphised: `Array<Int32>` is a C pointer*", taken straight from §7.63.
    - **What the boundary is instead.** The "a C type is out entirely" bullet that
      followed depended on the object-type rule and goes with it: a scalar, a
      `struct` and an `enum` are all admissible arguments, and **§7.63 is what
      decides** whether the declaration erases or is instantiated. Nothing is
      prohibited here that §7.62 has no representation for — and §7.62's own note
      already leaves a Sterling `enum` argument open rather than settled.
  - **The parameter is not erased in the *source*, only at codegen.** The emitted
    `.h` reads `Box<NSString *>`, so clang's own checking stays on the generated
    code, as it does everywhere else.
- **Struct** — `struct Name: Base { … }`, **a class's syntax in most of what it
  declares** — a superclass, `property`, `method` — with every difference being
  one of *semantics*: it is a value (§4), its methods are C functions (below),
  and its inheritance carries **no polymorphism** (below). **Its state is written
  `var`, and it has no synthesised properties** (decided, 2026-09): a struct has
  no `@property` machinery to synthesise storage with, so `property x: Float32` —
  whose entire content is "auto-synthesis gives the ivar" — has nothing to
  synthesise. A struct's properties are therefore the **accessor** forms it writes
  itself, over the `var` fields beside them; §7.25 has the lowering.

  ```sterling
  struct Point {
      var x: Float32
      var y: Float32
      readonly property isOrigin: Bool { return x == 0 && y == 0 }
      method length() -> Float32 { … }
      method moveTo(x: Float32, y: Float32) { … }
  }

  struct Point3: Point {
      var z: Float32
      method moveTo(x: Float32, y: Float32, z: Float32) { … }
  }
  ```
  ```objc
  typedef struct Point {
  	float x;
  	float y;
  } Point;

  float Point_length(const Point *self);
  void  Point_moveTo(Point *self, float x, float y);

  typedef struct Point3 {
  	struct Point;			/* -fms-extensions: an anonymous tagged member */
  	float z;
  } Point3;

  void Point3_moveTo(Point3 *self, float x, float y, float z);
  ```

  **The superclass is an anonymous member at offset 0**, which is what makes
  this inheritance rather than a naming convention. Measured on clang-19: the
  base's fields sit at `offsetof == 0`, so `((Point *)&p3)` is valid — a
  `Point3 *` is usable wherever a `Point *` is, and a method the derived struct
  does not declare is found on the base and called through a cast (`p3.length()`
  → `Point_length((const Point *)&p3)`). The base's fields are also **promoted**,
  so `p3.x` reaches `Point`'s field with no `.base.` in between. A derived struct
  may not redeclare an inherited property name — the two would be ambiguous.
  - **It requires `-fms-extensions`.** Without the flag clang reports
    `declaration does not declare anything` and then `no member named 'x'`
    (measured): both the promotion and the inheritance disappear. With it, the
    only cost is `-Wmicrosoft-anon-tag`, which the build suppresses. The flag is
    **not local** — a derived struct's definition lives in a generated *header*,
    so every translation unit that includes it needs the flag (§7.16).
  - **No polymorphism.** Struct methods are ordinary functions, so there is no
    dispatch: a call through a `Point *` reaches `Point_…` and never a `Point3`
    version. "Overriding" is therefore not dynamic — §9.12 asks whether a
    same-named method in the derived struct is an error or plain shadowing.
    Inheritance here is **layout plus upcasting**; behaviour is chosen
    statically. §8 keeps protocol conformance out for the same reason: a dispatch
    table is a mechanism, not a re-spelling.

  A struct's state is a `var` field — a plain C member, with no `@property`, no
  accessors and no auto-synthesis — and its properties are the accessor forms it
  writes itself. **There is no stored struct property** (decided, 2026-09), and two
  independent reasons say so: there is no `@property` machinery to synthesise one,
  and a `const` member would break the value copy §4 promises. Two property rules
  then *stop* applying, both for the same reasons:
  - A class-typed property is already excluded.
  - **`(readonly)` has nothing to attach to.** A `var` field is directly assignable,
    and making one read-only would need that `const` member. On a *computed* struct
    property `(readonly)` is fine and means what it says: a getter function, and no
    setter function.
- **Struct method** — `method name(l: T, …) -> R` emits a **C function** whose
  first parameter is `self`, named `StructName_name`. There is no selector, so
  the **labels are just the C parameter names** and §7.1's composition rule does
  not apply — the same treatment a C function gets in §6. Inside the body `self`
  is that pointer, and a field goes through it (`self.x` → `self->x`; for an
  inherited field the promotion makes that `self->x` too). A
  `method … -> Self` on a struct is therefore a function returning the struct
  **by value**.
  - **A method that assigns to a property takes `Point *self`**, where an ordinary method takes
    `const Point *self` (§7.14): **the emitter infers which from the body**, because whether a
    method mutates is a fact the body already states — and **C enforces the consequence for
    free**: a `let` binding is a `const Point`, so calling a mutating method on it is clang's
    "discards qualifiers" error. `mutating method` still parses, and is ignored (§7.14).
- **…and the same rule covers an enum's methods** (decided, 2026-09). An enum is a
  value like a struct, so `method name(…) -> R` on it is likewise a C function
  with `self` first, named `EnumName_name` — the receiver being the enum itself,
  so for a plain enum `*self` is the value and for a tagged union the body reaches
  fields through `self` exactly as a struct method does. Mutation works the same
  way on both kinds, with the same `const` enforcement and the same inference.
  - **There is no `class method` on a value type** — a struct or an enum. A class
    method is a message to a *class object*, and a value has none: the same
    absence that keeps struct inheritance layout-only and protocol conformance out
    (§8). A type-level operation is still expressible, as a plain `func`
    (§5, §7.56), so only the spelling is lost — and writing `class method` inside a
    struct or an enum is a compile-time error.
- **Enum** — two kinds (decided, 2026-09), and **which kind you get is decided by
  the members, not by a keyword**: an enum whose members carry **no associated
  values** is a plain C enum — a bare name, or a name with an explicit value —
  while an enum with **one or more members that carry associated values** is a
  **tagged union**.

  - **Members are written `case name` — DECIDED (2026-09), superseding the bare
    names the earlier text used.** Swift's spelling, so what was `enum Name { a
    b c }` is now `enum Name { case a case b case c }`. The keyword is purely a
    marker: it emits nothing, and members are still one per line with no
    separators. An enum may also declare methods, and those carry no `case`.
  - **Plain** — `enum Name { case a case b case c }` →
    `typedef enum Name { a, b, c } Name;`, and a member may **pre-set its
    value** with a number (decided, 2026-09): `enum Name { case a = 4 case b }` →
    `typedef enum Name { a = 4, b } Name;`, where C's own rule makes `b` 5 — an
    explicit value seeds the ones after it, and that rule is inherited whole
    rather than tightened, so the values need not ascend: `{ case a = 4 case b =
    2 case c }` gives `a` 4, `b` 2, `c` **3** (measured).
  - **…and its underlying type may be declared** (decided, 2026-09):
    `enum FooBar: UInt8 { case a case b }` → `typedef enum FooBar : uint8_t { a, b }
    FooBar;`. That `: T` is the same one an enum gets in C++ and C23, so **no
    `NS_ENUM` macro is needed** — and this Foundation has none to use anyway
    (measured). **Any integer type in §4's table may serve, `Bool` included**,
    which emits as `BOOL` (§4) and so is an `unsigned char` base, one byte
    (measured). The width is otherwise real: `sizeof` is 1 for a `UInt8` base, 8
    for an `Int64` (measured). And the choice does more than size the enum — **a
    value that does not fit is an error** (*"enumerator value is not
    representable in the underlying type"*, measured), where a default-`int` enum
    quietly widens instead. It is a clang extension in pre-C23 modes, and
    `-pedantic` warns `-Wfixed-enum-extension` for every form of it (measured), so
    a build that ever goes pedantic needs that suppression — the way struct
    inheritance needs `-Wno-microsoft-anon-tag` (§3.15).
    **Either kind may declare one.** For a plain enum it is the enum's own width;
    for a tagged union it is the **tag**'s, leaving the union untouched (below,
    and §7.17).
  - Either way the `typedef` is the emitter's, so the name works bare exactly as
    it does for `struct` — the tag and the typedef share a name, which is legal in
    C because tags and ordinary identifiers are separate namespaces. Members are
    written **one per line with no separators** — the line ends the member,
    exactly as it ends a statement (§6) — and the emitter supplies the commas,
    just as it supplies a statement's `;`.

  - **Associated values** — syntactic sugar for a tagged union, so the emission
    is a tag plus a union holding one payload struct per case:

    ```sterling
    enum MyOtherEnumType {
        case valueOne(associateValue: Int32) = 4
        case valueTwo(associatedValue: Float64)
        case valueThree(associatedValueOne: Bool, associatedValueTwo: Int64)
    }
    ```
    ```c
    typedef struct MyOtherEnumType {
    	enum {
    		MyOtherEnumType_valueOne = 4,
    		MyOtherEnumType_valueTwo,
    		MyOtherEnumType_valueThree
    	} tag;
    	union {
    		struct { int32_t associateValue; } valueOne;
    		struct { double  associatedValue; } valueTwo;
    		struct { BOOL associatedValueOne; int64_t associatedValueTwo; } valueThree;
    	} value;
    } MyOtherEnumType;
    ```

    A case's **tag value may be pre-assigned**, exactly as a plain member's may
    (decided, 2026-09): `valueOne(associateValue: Int32) = 4` sets the *tag* to 4,
    where that `4` is **not** a default for `associateValue` — the payload is
    still whatever the construction passes, and the two are separate. The rule
    is the plain enum's rule inherited whole, so it seeds the ones after it
    (`valueTwo` becomes 5 above) and the values need not ascend. It matters for
    interop: the tag is the enum's on-the-wire form, so pinning it is how a
    Sterling enum meets a C API's numbering.

    The two member rules that matter here are settled, and they hold for both
    kinds: **a name may appear only once** in an enum (decided, 2026-09) — C's own
    rule for enumerators — while **two members may share a value**, as
    `enum Foo { bar = 0, baz = 0 }` shows: an alias C allows, and the language
    keeps it (decided, 2026-09).

    For a *plain* enum that is the whole story — `Foo.bar == Foo.baz` is true, as
    in C. For a tagged union the permission reaches the **tag**, and there it is
    conditional (decided, 2026-09): **cases may share a tag only if their payloads
    are identical** — the same field names with the same types — because the tag is
    also the union's *discriminant*, and two cases that share it cannot be told
    apart when reading. Identical payloads make the arms interchangeable, so the
    read is well defined and the aliased cases are genuinely one case under two
    names. A merely *same-size* payload would not do: reading an arm as the other's
    type is a lie the union cannot detect. Aliased cases may therefore share one
    union arm in the emission, and C accepts the duplicate tag values (measured).

    Three consequences, and the last is the value rule again:

    - **The case names are prefixed** in the emitted enumerators
      (`MyOtherEnumType_valueOne`), because C puts enumerators in the enclosing
      scope.
    - **A member with no associated values contributes no union member.** A
      tagged union exists only because some member has a payload, so the union
      always has at least one arm, and this keeps an empty `struct { }` out of
      the emission — which C does not allow anyway.
    - **An associated value cannot be a class type.** ARC forbids Objective-C
      objects in a struct or union, and this union is inside a struct, so a
      payload is a scalar, a struct, or another such enum — never an object. That
      is the fourth time the value rule has decided something (§4).

  - **Access is qualified, and the shorthand needs a known type** (decided,
    2026-09). A case is named `MyEnumType.valueOne` — for either kind — and may
    be written `.valueOne` wherever the type is already known: a `let`/`var`
    initializer whose type is written **or supplied by its initializer** (§5's
    Local, below), a `switch` case pattern (§6), or an argument whose parameter
    type is known. The shorthand is never inferred from nothing, because in every
    one of those positions an expected type is already in hand.
    What the qualification maps to is the emitter's, and **both kinds now prefix**:
    a **plain** member emits `MyEnumType_valueOne` and a **tagged-union** case
    `MyOtherEnumType_valueOne` (decided, 2026-09, §9.14). The qualification is
    therefore sugar the C never sees *and* a guarantee it cannot be broken: with the
    bare spelling, two plain enums sharing a member name collided as C enumerators —
    invisibly, since the source is qualified in both cases.
- **Method** — `method name(label: T, …) -> R { … }`, or `class method` for
  `+`. **The `-> R` may be omitted, and the method then returns `Void`** —
  stated here (2026-09) rather than left to the examples, because until it was
  written down the document only *demonstrated* it: the `struct` example below
  writes `method moveTo(x: Float32, y: Float32) { … }` with no arrow, and a
  parser could contradict that while both looked self-consistent. **The same
  rule covers a `func`.** Body rules are C's. **Either kind may be preceded by a visibility marker** — `public`
  (the default), `private` (this file only) or `internal` (this project, but not the library's
  public header) — written before the rest: `private class method foo() -> Void`. One marker
  at most; §7.57 has the emission and the measurements behind it.
  - **A class method is spelled in full `class method foo(bar baz: Type) -> Void` (confirmed,
    2026-09)** — the same parameter pair as any method, so the external name `bar` builds the
    selector and the internal name `baz` is the body's `const` local (§7.1, §7.2). It emits
    `+ (void)fooBar:(Type)baz`, and a Cocoa `+fooWithBar:` is written
    `foo(withBar bar: Type)` — the labels are named after the selector's pieces. **The call
    needs nothing separate**: a class is a receiver (§6), so it is `Foo.foo(bar: value)` §7.58.
  - **A parameter has an external and an internal name** (decided, 2026-09), and
    writing one name gives both:
    `method object(atIndex index: Int32) -> AnyObject` is *called*
    `object(atIndex: 4)`, and inside the body the argument is the `const` variable
    **`index`**. So the **external** name is what a call site writes and what the
    selector is built from (§7.1), while the **internal** name is what the body
    sees — the same `const`-local treatment an enum case's associated values get
    (§6), so a parameter cannot be assigned and a `var` local is how one works on a
    copy.
    - **The body's `const` is emitted, in §5's placement**: a scalar parameter as
      `(const int32_t)index`, a class-typed one as `(NSString * const)thing` — both
      verified through this tree's wrapper. It is the locals' rule applied a third
      time (locals, binding temps, parameters), and it is what makes the promise
      true at the C level rather than only in the source.
    - **No suppression form is needed**, because call labels are always required
      (§7.2): there is no `_` to spell, and every call site names its arguments.
    - **It is what lets an imported selector round-trip.** A Cocoa method's
      selector pieces and its header's parameter names come from *different*
      sources — `- (id)objectAtIndex:(NSUInteger)index` has the piece `AtIndex` and
      the parameter `index` — so a single name could not express both. With the
      pair, the external name comes from the selector and the internal from the
      header, and the two agree by construction.
    - **A parameter may be declared `var`** (decided, 2026-09):
      `method object(atIndex: var Int32) -> AnyObject` exposes the argument as a
      *writable* variable inside the body, where the default is the `const` one
      above. The difference is exactly the keyword — a by-value C parameter is
      already a writable local, so the default *adds* the `const` and `var` is the
      spelling that omits it: `(int32_t)index` where the default emits
      `(const int32_t)index`. It is a local's `let`/`var` distinction (§5's Local)
      applied a fourth time. **An explicit `let` is accepted and ignored** (decided,
      2026-09): it states the default rather than contradicting it, so it is a way
      to *document* that a parameter is not writable, and it emits the same
      `const int32_t` the default does.
      - **It is a copy, never an out-parameter.** Writing to it changes the
        method's own copy and nothing the caller can see — for a class type it is a
        reassignable pointer to the *same* object, exactly as `if var x = y` binds a
        mutable copy of a reference (§6). Write-back has two other spellings, and
        neither is this one: a method that mutates `self` (§5), and a pointer
        parameter for anything else (§4).
  - **An initializer is `init(arg: T) { … }`** — the `method` keyword **and** the `-> Self` return
    implied and not written (decided, 2026-09), an ordinary method named `init` in every other
    respect
    (§7.8, §7.49). It is what `T(arg: v)` calls, and **its body returns `self` implicitly**:
    no `return` is written, and the emitted ObjC supplies `return self;`. **A subclass's
    initializer must chain with `self = Superclass()`** — the one place `self` is writable —
    which emits `self = [super init]` and never a fresh `alloc`. **And a class must declare one
    to be constructed at all** (decided, 2026-09): nothing is synthesised, so `T()` is an error
    where no initializer is written, even though ObjC would have inherited one (§7.49).
- **Property** — `[modifiers] property name: T`, optionally with `{ get { … } set { … } }`.
  A modifier is **any bare `@property` attribute**, written as a keyword before `property` —
  `readonly`, `copy`, `weak`, `unowned`, `strong`, `assign`, `atomic`, and `class` for a class
  property — and that is the **preferred** spelling (decided, 2026-09). The parenthesised form,
  `property (readonly) name: T`, mirrors ObjC's `@property (…)` attribute list faithfully and
  stays valid; its only *necessary* use is a **parameterised** attribute (`getter=`,
  `setter=`), which has no bare keyword (§7.15, §7.52, §7.53). So read-only is written
  `readonly property dynamicValue: Float32 { return 0.1 }` → `@property (nonatomic,
  readonly) float dynamicValue;` plus a getter and **no ivar** — a computed property declares
  no storage — and there is no *implicit* read-only form: the keyword has to say so. **A
  readonly property's body may be the getter directly** (`{ … }`), or the named form
  `{ get { … } }` — but a readonly property with **no getter** is a stored one, and it **must
  carry its value in the declaration**: `readonly property x: Int32 = 3` (decided, 2026-09,
  §7.54). Nothing else could ever give it one, which is the whole reason for the requirement.
  **A `set` block takes no
  parameter list**: its argument is implicit — one value of the property's type, called
  `newValue`, and *writable* so the setter can normalise it (§7.55) — and a `set` block adds
  the setter, after which `readonly` is an error. The
  qualifier is otherwise **inferred from the type** (a class type is `strong`, a scalar or
  struct is `assign`).
- **Protocol** — `protocol C: A, B { … }`; the list is the protocols it inherits, and a
  *class's* list is the same syntax with the superclass first and conformances after it
  (§7.45). A protocol name is a **type** — `let x: C`, with `C?` for the nullable form —
  which emits `id<C>`. Members are **required by default** — ObjC's own default — and
  `optional` is a prefix keyword: `optional method m(…) -> R`, `optional property x: T`,
  the same shape as §5's other prefix modifiers; §7.48 has the emission.
  - **A protocol carries requirements and no implementations — DECIDED (2026-09).**
    Every member is a *signature*: `method m(a: T) -> R` with **no body**, since a
    protocol has no implementation to hold one and whatever conforms supplies it
    separately. **A body written in a protocol is an error, not something ignored** —
    the same reason §5's `case` is required in an enum: a rule that is not enforced
    cannot be measured, and a parser that quietly accepted a body would let the corpus
    look conformant while carrying code that could never run.
- **Extension/category** — two forms (decided, 2026-09, §7.4): **`extension X { … }`** is ObjC's
  **class extension** (`@interface X ()`) — unnamed, storage allowed, and only where the unit also
  defines `X` — while **`category X (Name) { … }`** is the **category** (`@interface X (Name)`) —
  named, no storage, and the one usable on a class the unit does not own. Either may carry a
  conformance list: `extension X: P { … }` and `category X (Name): P { … }`.
- **Function** — `func name(a: T) -> R { … }`; a **bare function**: callable, not bound to a
  type, and with **no implied `self`**. The argument syntax is §5's Method's — labels,
  external/internal names, `_` suppression, `var` — except that a C function has no selector,
  so labels are checked against the declaration and then **dropped** (§2). It emits a plain C
  function, declared in the generated header just as a class is, and it takes the same
  **visibility markers** a method does (decided, 2026-09, §7.57) — `public` by default, with
  `private` emitting a C `static`. Zero arguments emit `(void)` rather than
  `()` — measured, not for a warning (`-Wstrict-prototypes` is off here, so clang is silent) but
  because `()` in C is an *unprototyped* declaration, which would switch off clang's own
  argument checking on the generated code (§7.56).
- **Local** — `let name: T = e` (constant) and `var name: T = e` (writable) — **and these are
  locals only — with **one second home: a struct's fields** (decided, 2026-09, §5's Struct). A
  **class** body declares no `let` or `var` at all: its state is its properties, which manage the
  internal variables auto-synthesis provides. A **struct** has no synthesised storage, so its
  state is written `var` and its properties are the accessors it writes itself. Swift's
  convention (decided, 2026-09) — preceded by `weak` or `unowned` for a **class type** whose
  reference should not retain: `weak let w: T = e` / `weak var w: T = e` for the nilling one,
  `unowned let u: T = e` for the one that is not nilled (§7.52, §7.53) — and
  **the `: T` may be omitted whenever
  the initializer carries the type** (decided, 2026-09, §7.19): `let p =
  Point(x: 0, y: 0)`, `let s = "text"`, `let b = true` and `let x = 3` are all
  fine — the last because an unsuffixed integer literal *is* an `Int`
  (`NSInteger`) and an unsuffixed float literal a `Float64` (§4). Where an
  expected type is in hand the literal takes **that** rather than the default, so
  `let n: Float32 = 0.1` emits `float n = 0.1f;`. This is the *same*
  expected-type mechanism the `.case` shorthand uses (above), pointed the other
  way — one contextual-typing rule, used in both directions.
  The difference between `let` and `var` is C's `const`, and **where the `const`
  goes depends on the type**:
  - a **scalar** is `const T name` — `let n: Int32 = 3` → `const int32_t n = 3;`;
  - a **class type** is `T * const name`, **not** `const T *name` — `let s:
    MutableString = …` must still allow `[s appendString:…]`, so the *pointer*
    is const and the object is not. The naïve `const` + type is the wrong
    constness, and clang says so ("discards qualifiers").
  - a **struct** — and an associated-value enum — follows the scalar rule
    (`const Point p = …;`), and *that* is what makes a mutating call on it
    an error (§5).

  `var` emits neither `const`. The same rule governs a binding temp in §6, and
  the type — written or inferred — decides which form is emitted.

## 6. Expressions and statements

- **Message send** — calling a method *is* sending an Objective-C message, and
  the dot is the whole of the spelling: `receiver.sel(label: arg, …)` →
  `[receiver sel:arg …]`. **The bracket form is never written in Sterling** — it is
  emission only, so there is no second call syntax to keep in step.
  - **A no-argument message writes its parentheses — the omission rule is withdrawn
    (2026-09, §7.60).** `receiver.sel()` is the send; `receiver.sel` without them would
    be indistinguishable from a bare name, which is the ambiguity `for item in items
    { … }` walks into. The reasoning that once made the omission look safe — that a
    *message* has no reference form, unlike C's `myFunc` versus `myFunc()` — is true and
    beside the point: the cost lands on the *grammar*, not on the semantics.
  - **The receiver may be a class**, and then it is a class-method send:
    `MyClass.baz(arg1: 1)` → `[MyClass baz:1]`, the class object being the
    receiver exactly as in ObjC. (The specimen *declares* a `class method` but
    only ever calls a C function, so it leaves this case unshown.)
  - **The labels are the author's; the selector is the emission's.** In
    `myObject.methodName(with: arg)` the `with` names the parameter, and §7.1
    decides where a *later* label goes — so that one line emits `methodName:`
    under §7.1's default and `methodNameWith:` under the Swift-style
    alternative. **The choice is visible only in the emitted selector, never in
    the source**, which is why it is worth settling even though nothing an author
    writes would change.
  - **A trailing block may follow the call** when the last parameter is a function
    type: `foo() (bar: Int32) { return false }` rather than the block sitting inside
    the parentheses. Its parameter list is the closure's own — one name per
    parameter and no label, since a block has no selector — and its types come from
    the parameter's function type. The rule, and the consequences of it, are §7.33.
  - **The parentheses stay, even when the block is the call's *only* argument.**
    §7.60's omission rule is **withdrawn** (2026-09): the shape is `foo (bar: Int32)
    { … }`, where the closure's parameter list *is* the call's parentheses. Writing
    `foo { … }` would be indistinguishable from a bare name followed by a statement's
    block — which is the ambiguity `for item in items { … }` walks straight into. A
    block's parameters are still named by its list or not at all: `(bar)` and
    `(bar: Int32)` are the two spellings and there is no third.
- **Force unwrap** — `x!` on a `T?` yields the raw value and **traps if it is
  `nil`**. It is the first of the language's three *trapping* operations — `as!` (§7.46)
  and arithmetic overflow (§7.40) are the others — which are collectively §0's
  exception: ObjC has no "crash if null", so `x!` is compiled to a null check that
  aborts. Postfix, binding tighter than the message send, so
  `x!.foo` is `[(x!) foo]`; `x!` on a non-optional is an error. The emitted shape
  (provisional; K1/K2 settles it) is a **header-only** macro rather than a
  library function, so the plan's "no runtime library to stage" still holds:

  ```objc
  #define STERLING_UNWRAP(v) \
      ({ __typeof__(v) __sterling_v = (v); \
         if (!__sterling_v) sterlingc_trap_null(); __sterling_v; })
  ```

  It must **not** be a conditional assert: an `NDEBUG`-stripped `NSAssert` would
  silently make `!` non-trapping in an optimised build.
- **Null-safe binding** — `if let` / `if var` and `guard let` / `guard var`
  (decided, 2026-09). All four bind the unwrapped value and narrow it to
  non-optional, and all are pure re-spellings of the C nil test — so unlike `!`,
  §0 needs no exception for them. `let` binds a constant, `var` a writable copy.
  **The bindings may be a comma-separated list** (decided, 2026-09, §9.7):
  `if let a = x, let b = y { … }` and the same on `guard`, each binding independent
  of the others and each narrowing its own name:

  ```sterling
  if let name = maybeName {
      use(name);                  // name: String, non-optional, constant
  } else {
      // maybeName was null
  }

  if var name = maybeName {
      name = other;               // allowed: the binding is writable
  }

  guard let name = maybeName else {
      return;                     // the else must leave the enclosing scope
  }
  use(name);                      // non-optional to the end of the block
  ```
  ```objc
  NSString * const __sterling_name_1 = (maybeName);
  if (__sterling_name_1 != nil) {
      use(__sterling_name_1);
  } else {
  }

  NSString *__sterling_name_2 = (maybeName);        /* no const: bound with var */
  if (__sterling_name_2 != nil) {
      __sterling_name_2 = other;
  } else {
  }

  NSString * const __sterling_name_3 = (maybeName);
  if (__sterling_name_3 == nil) {
      return;
  }
  use(__sterling_name_3);
  ```

  Three things the emitter has to carry, all consequences of C rather than
  choices:
  - **A rename map.** C cannot redeclare a name in the same scope and `let` is
    immutable, so `guard let x = x` cannot emit a second `x` — the binding gets a
    fresh C name (`__sterling_x_1`) and the *source-level* name maps onto it for the
    remainder of the scope. Subsequent uses of `x` emit the fresh name, which is
    also why the unwrapped value needs no second declaration.
  - **Temps need a counter.** Two binding forms in one block would collide on a
    fixed name, hence the `_1`/`_2`/`_3` suffixes.
  - **`var` binds a copy of the *reference*, not of the object.** `if var x = y`
    gives `x` a writable binding to the same object: assigning `x` does not
    change `y`, but sending a mutating message does. In C that is simply the same
    local without `const` (§5).
  - **`guard`'s `else` must `return` — DECIDED (2026-09), narrowed from "leave the scope".** A
    `return` must be written on every path out of the block: `break`, `continue` and a `throws` path
    are no longer sufficient, and an implicit exit — reaching the end of the block — is an error. The
    narrowing is a *restriction* of the kind §7.24 and §7.67 already make: one exit form to lower
    instead of four, and it removes the awkward case where a `guard`'s `else` would be leaving a
    *loop* rather than the enclosing function. It remains a diagnostic rather than an emission rule —
    the C simply falls through if the body does not return.
- **Null-coalescing (`??`)** — `lhs ?? rhs`, where `lhs` is a `T?` and `rhs` a
  `T`, yields a `T`: the unwrapped `lhs` when it is non-null, `rhs` otherwise. It
  is the **substituting** way out of an optional — `!` asserts, the binding forms
  branch, and this one has an answer ready. Two properties are not incidental:
  - **`rhs` is evaluated only when `lhs` is null**, exactly as `&&`/`||` skip
    their second operand. That is what makes `myVar ?? T()` mean "a new `T` only
    if there was nothing", and it is why the right side is a *lazy* operand
    rather than an ordinary argument.
  - **`lhs` is evaluated once**, which the obvious lowering does *not* give:
    `(lhs != nil ? lhs : rhs)` reads it twice, so an `lhs` with a side effect
    comes out wrong. The emitter hoists it, as it does for `!` — a header-only
    statement-expression macro, so the plan's "no library to stage" still holds:

    ```objc
    #define STERLING_COALESCE(l, r) \
        ({ __typeof__(l) __sterling_l = (l); __sterling_l ? __sterling_l : (r); })
    ```
  Both operand types are **checked, not coerced**, and each mismatch is a
  **compile-time error** (decided, 2026-09): the left must be a `T?` — a
  non-optional left is an error, since its right operand could never be used —
  and the right must be a `T`, so an optional right (plain `nil` included) is an
  error too. The **result is always non-optional**, which is the point: `??` is
  the one way out of an optional that *produces* a plain value, and it produces
  it unconditionally. Two things follow, and they are the rule rather than
  details of it:
  - **No chain through optionals.** `a ?? b ?? c` would need the middle to be
    non-optional (to be a `T` for the first `??`) *and* optional (to be a `T?`
    for the second) — so the chain is impossible, not merely useless, and `??`
    does not compose the way a reader arriving from Swift might assume.
  - **`a ?? nil` is an error**, for the same reason. The language cannot be told
    to fall back to null, so the result is a *guarantee* rather than a claim —
    which is exactly what makes it the trap-free, branch-free narrowing.
  It binds looser than the comparisons but tighter than `?:`, so `a ?? b < c`
  parses as `(a ?? b) < c`; that precedence rule is the only part still to
  confirm (§7.22).
- **Struct literal** — `Name(field: v, …)` → a C compound literal
  `(Name){ .field = v, … }`. Using an imported struct is the same construct:
  `NSMakeRange(0, 3)` is a C function, callable as written, but
  `Range(location: 0, length: 3)` is the literal form.
- **Tagged-union value — decided (§7.35).** `Name.case(label: v, …)` → a compound
  literal, each label being the payload's own field name. The **qualified spelling is
  decided** (§7.18):
  `MyOtherEnumType.valueOne(intValue: 44)` →
  `(MyOtherEnumType){ .tag = MyOtherEnumType_valueOne, .value.valueOne = {
  .intValue = 44 } }`. The shorthand applies here too, because the expected type is
  known — `let e: MyOtherEnumType = .valueOne(intValue: 44)`. A member with no
  associated values is written with no arguments:
  `MyOtherEnumType.valueZero` → `(MyOtherEnumType){ .tag =
  MyOtherEnumType_valueZero }`.
- **Enum matching** — `switch` with case patterns and a **braced block** per case
  (§7.24, §7.35), and the same form serves both kinds because a tag test is a tag
  test (decided, 2026-09):

  ```sterling
  var someTaggedEnum = MyOtherEnumType.valueOne(intValue: 44);

  switch someTaggedEnum {
      case .valueOne {
          // "intValue" is in scope in this block, and equals 44.
      }
  }
  ```

  A `default`, and a plain enum's case, take the same shape — and so do several
  patterns sharing one body, `case .a, .b { … }` (that spelling is §7.24's remaining
  open). **A `default` brings no associated values into scope** (§7.36): it matches
  any tag, so there is no type for a name to have — the same absence that leaves the
  exhaustive case as the one way to read a payload.

  **A case's associated values are already in scope in its body**, as `const`
  variables named and typed by the declaration — there is no binding syntax,
  because the pattern has nothing to bind: `associateValue` *is* the field, and it
  arrives const. The emission is a C `switch` on the tag (on the value itself, for
  a plain enum), each case body a **block** whose opening lines hoist the fields —
  `case MyOtherEnumType_valueOne: { const int32_t associateValue =
  e.value.valueOne.associateValue; … }` — and that block is also what lets a field
  name shadow an outer variable of the same name, since C scopes the declaration
  to the braces instead of colliding with it.

  **The switch must be exhaustive, and nothing falls through** (decided,
  2026-09). Every case must be covered or a `default` supplied — the compiler
  knows the case list, so it can insist — which is what makes a match a complete
  decision rather than a hopeful one. And each case *exits* after its body, so the
  emitter supplies the `break` the way it supplies a statement's `;` and an enum's
  commas. Three things follow:
  - **No fallthrough means grouping needs its own spelling.** C's idiom — an empty
    `case` falling into the next — does not exist here, so several patterns
    sharing one body are written as a pattern *list* (§7.24).
  - **An aliased case is covered by any of its names.** A `switch` over
    `Foo { bar = 0, baz = 0 }` is satisfied by `.bar` alone — and must be, because
    C rejects two `case` labels carrying the same value, so there would be nothing
    to emit for `.baz` (§5's aliasing rule).
  - **A `default` is required whenever the subject is not a finite case set.**
    An `Int` can never be covered explicitly, so it always needs one (§7.24).
- **Struct method call** — `p.name(l: v, …)` → `Point_name(&p, v, …)`: the
  receiver becomes the **first argument, by address**, and the labels are
  dropped. An inherited method is the same call with an upcast —
  `p3.length()` → `Point_length((const Point *)&p3)` — and **`super`** on a
  struct is that same static choice made explicit:
  `super.moveTo(…)` → `Point_moveTo((Point *)self, …)`. There is no dispatch to
  consult, so `super` is a cast, not a lookup. One emitter wrinkle follows from
  C: `&` needs an *lvalue*, so a call on a temporary — `Point(x: 0, y: 0)
  .length()` — must first be materialized into a local, because a function's
  return value is not addressable.
- **Labels** — every call names its arguments. The name is checked against the
  callee's declaration: for a method it composes the selector; for a C function,
  a struct method, or a tagged-union case it is dropped (a case's labels are its
  payload fields, checked all the same). This is the only "extra" the language
  adds to calls, and it adds no runtime.
- **Boolean and comparison operators** — the C/ObjC set (decided, 2026-09):
  `!`, `&&`, `||`, and the comparisons `==` `!=` `<` `>` `<=` `>=`. `&&` and
  `||` **short-circuit** as C's do, so the guarded idiom holds —
  `if p != nil && p.ready` never evaluates the second operand when `p` is null.
  Their result is a **`Bool`**, not C's `int`: that is what lets a comparison be
  a condition (§7.20) with no conversion, and it is why one cannot be used as a
  number (`b + 1` is an error). In the *emitted* C the difference is invisible —
  `(a < b)` is an `int`, and assigning it to a `BOOL` is fine — but in the source
  it is the type.
  **The bitwise operators do not take a `Bool`.** `&` `|` `^` `~` are C's
  *bitwise* operators, not its logical ones, and admitting them here would
  resurrect exactly the hazard §7.20 removed: `~YES` on this target's
  `unsigned char` carrier is 254 — truthy, and not `NO`. `b1 && b2` and `!b` are
  the spellings (§7.21).
- **Statements end at the newline, and a `;` only ever separates two on one
  line** (decided, 2026-09). Nothing needs a terminator, so `let x = 3` and
  `return false` are complete as written; two statements may share a line when a
  `;` divides them (`let x = 3; let y = 4`); and a trailing `;` with no second
  statement is accepted — a statement may be empty, the specimen writes them, and
  it stays valid.
  - **The emitter supplies the `;`**, as it supplies an enum's commas: C wants
    one on every statement, so each unit is terminated on the way out. The rule
    belongs to the source and the semicolons to the emission.
  - **A statement continues while its expression is incomplete** — a newline
    inside unclosed brackets, or immediately after a binary operator, does not end
    it, so a call whose arguments wrap over lines reads naturally. The precise
    rule is §7.23.
- `true`/`false`/`nil`, `self`/`super`, `try`/`catch`/`finally`,
  `autoreleasepool { }`, `synchronized (o) { }`, `if`/`while`/`for`/`switch`,
  and C operators are as written — **except in the two things the language does not
  inherit from C**: the numeric conversions behind them are not C's (operands do not
  promote, a conversion must be written, and it may only go up — §7.39, §9.17), and
  **overflow traps rather than wrapping**, signed or unsigned, with `&+` / `&-` / `&*`
  as the deliberate-wrapping operators (§7.40). So `a + b` of two `Int8`s is an `Int8`
  — and if their sum does not fit in one, the program stops.

## 7. Decisions — proposed, confirm or amend

These were the places the specimen did not settle, each starting as a proposed default. Most are
now **DECIDED** — every item says which — and where a decision left a detail open, the item names
that detail rather than leaving it to a reader to find.

1. **Selector composition — DECIDED (2026-09): every parameter's *external* name
   is in the selector.** The first piece is the method name with the first
   parameter's external name capitalized onto it, and every later piece is that
   parameter's external name as written (§5's Method is where a parameter gets its
   two names) — so `foobar(argname: Int32, arg2: Bool)` is
   `- (BOOL)foobarArgname:(int32_t)argname arg2:(BOOL)arg2`, selector
   `foobarArgname:arg2:`. The default that stood here (method name alone as the
   first piece) **cannot** be right: it would make `init(foo: Int32)` and
   `init(bar: Float32)` both `init:`, and clang rejects exactly that with
   *"duplicate declaration of method 'init:'"* (measured). Two consequences, the
   first being why the rule had to go this way:
   - **Overloading is by name, never by type** (§7.27) — the only kind an
     Objective-C selector can express.
   - **Cocoa's own selectors fall out of it.** `object(atIndex: Int32)` is
     `objectAtIndex:`, and `replaceObject(atIndex: Int32, withObject: AnyObject)`
   is `replaceObjectAtIndex:withObject:` — the convention is reached by naming the
   labels after the selector's pieces, capitalization included. So an imported
   Cocoa selector is reproducible exactly, and an exported one can read like Cocoa
   without the compiler inventing anything.
2. **Call labels — required, and they are the parameter's *external* name — DECIDED
   (2026-09), and revised by §7.50.** A call must name every argument, and the name is
   checked against the declaration's external name (§5's Method), which is also what the
   selector is built from (§7.1). What is *not* in v0 is a positional **call** form — a call
   does not decide the labels — but a **declaration** may suppress one by naming it `_`
   (§7.50), which is how a one-piece Cocoa selector such as `addObject:` is written. The
   line that stood here, "a required label leaves nothing to suppress", was wrong: the
   one-piece selector is exactly what needed suppressing.
3. **Nullability — DECIDED (2026-09).** Every type is non-nullable by default;
   `T?` is the nullable form. §4 states the rule and its consequences.
4. **Categories — DECIDED (2026-09): two words, `extension X { … }` and `category X (Name) { … }`.**
   The exploration that decided it: `extension X { }` stood as the default with `category X { }` as
   an alternative, but the two ObjC constructs differ in ways a program can observe.
   **What ObjC offers is two constructs, and Sterling's one keyword has to cover both:**
   - a **class extension** (`@interface X ()`) — the unnamed form, what `extension X` means when
     a unit extends *its own* class;
   - a **category** (`@interface X (Name)`) — the same thing with a **name**, and the only one
     usable on a class the unit does not own.
   **Measured, on this toolchain:**
   - **A category may not add an ivar.** `@interface X (Extra) { int32_t n; }` is an error —
     *"instance variables may not be placed in categories"* — while the same ivar in a **class
     extension** compiles. So a *stored* property (§7.54) is legal only in the extension form.
   - **Neither form can be defined against a forward declaration.** `@class X;` followed by
     `@interface X () …` is *"cannot define class extension for undefined class 'X'"*, and the
     category spelling gives the identical error with *"category"* where *"class extension"* was.
     Both need the class's `@interface` **visible**, which in Sterling means importing its unit
     (§7.9) — the `@class` forward declaration the emitter writes is not enough.
   - **A category may declare conformance** (`@interface X (Extra) <P>`), so whichever spelling
     wins, `extension X: P { … }` has somewhere to land.
   **The options, with their costs:**
   - **(a) one keyword, `extension X { … }`, and the emitter picks the form** — a class extension
     when the unit defines `X`, a category *named after the unit* otherwise. Nothing becomes
     unexpressible, and two units extending one class get two distinct names.
     - **The rule it would need is *not* ObjC's, which is the problem with (a).** Measured: a
       **class extension with an ivar, in a unit that does not implement the class, compiles
       clean** — clang says nothing at all. Nothing checks it, and the consequence is an ABI one,
       because that unit's view of the class's layout is not the class's. So the language would
       have to *invent* a rule — storage only in the class's own unit — and then apply it to a
       distinction the author never saw, having written one keyword for both forms.
   - **(b) keep both words** — `extension X { … }` for the class extension, `category X (Name) { … }`
     for the category. The author states which construct they mean, the storage rule becomes
     statable against a *named* intent rather than an inferred one, and the category's name is the
     author's — which is the identifier the emitted ObjC will carry.
   - **(c) one keyword, always a category, named after the unit** — simplest emitter, but it gives
     up storage in an extension entirely, which is a real capability rather than a corner.
   **The decision (2026-09): (b), two words.** The argument is §0's: ObjC has **two** constructs
   here, their difference is **observable** — storage, and a category's name — and this language's
   job is to translate the *semantics*, not to find the smallest surface that can compile them. A
   file-layout convenience is not worth an unexpressible distinction, and an author who writes an
   extension already knows which class is theirs.
   **And "is this a mapping problem?" has a precise answer: it is a question about *which*
   semantics are being translated, and §0 answers it.**
   - **What a surface may merge is what carries no difference.** §7.59 does unify `nil`, `Nil` and
     `NULL` into one word — and that works because the *meaning* is the same in all three places:
     absence. The C differs by position; the intent does not. `extension` is the opposite case:
     the two constructs differ in what a *program can do* — storage or not — and in an identifier
     the emitted ObjC carries. Merging them would hide a distinction rather than relocate one.
   - **So the test is: does the merge lose an observable difference?** Here it does, twice, which
     is why (b) wins even though it costs a keyword. The `nil` table is therefore not a precedent
     for merging *anything* — it is a precedent for merging things whose difference is only
     spelling.
   - **The genuinely lossy direction is *import*.** An ObjC category's methods arrive as the
     class's ordinary methods, because the runtime merges them — so an *imported* category leaves
     **no trace of its name**, only of its methods. A *declared* Sterling `category`, on the other
     hand, keeps its name on the way out — which is the direction a reader of the emitted ObjC
     sees, and the one (b) preserves.
     - **One hazard either form keeps, worth naming.** A category may *override* an existing
       method, which §7.43's principle says must stay expressible. **Measured, and it is a warning
       rather than silence**: clang reports *"category is implementing a method which will also be
       implemented by its primary class"*. So the hazard is visible to clang, and the language
       could go further and refuse it — the same question §7.45 asks about `-Wprotocol`.
     - **And a duplicate category name is measured too.** Two categories with the same name on one
       class give *"duplicate definition of category 'Same' on interface 'X'"* — another warning —
       and a shared name is harmless **unless the methods collide**, which the method rules already
       catch. So an author-chosen name is not the hazard it looks like; it is a *name*.
   **The case for two words, which (b) accepts.** The name is a real token — `NSString
   (NSURLUtilities)` is documentation as much as plumbing — and more than that it is an identifier
   the emitted ObjC **carries**: a reader of a Sterling unit's `.m` sees it, and an ObjC consumer of
   the generated header sees it. `extension` would give that up in exchange for a derivation the
   compiler can perform, which is a real convenience but not a semantic, and the trade this
   language makes is to keep the semantics.
     - **Its cost, stated plainly**: the author types a keyword and a name they would otherwise not
       type, and must know which construct they mean. That is what "translate the semantics" asks
       of them — and it is a fact they already have, in whether the class is theirs.
   **And the two in use — two files, because separate units are the whole point of them.**
   ```sterling
   /* Point.ag — the class and its own extension, one unit */
   class Point: Object {
       property x: Int32 = 0
       property y: Int32 = 0

       method magnitudeSquared() -> Float64 {
           return Float64(x * x + y * y)
       }
   }

   extension Point {
       property label: String = "origin"      /* storage — only your own class can gain it */
       method describe() -> String {
           return label
       }
   }
   ```
   ```sterling
   /* StringGeometry.ag — a category on a class this unit does not own */
   import Point

   category String (Geometry) {
       readonly property isPointLiteral: Bool {   /* computed, so a category is fine */
           return false
       }

       method pointValue() -> Point? {
           return nil
       }
   }
   ```
   ```objc
   /* Point.m — the extension is the unnamed form, and it is where the extra storage lands */
   @interface Point ()
   @property (nonatomic, assign) NSString *label;    /* synthesised in this file */
   - (NSString *)describe;
   @end
   ```
   ```objc
   /* StringGeometry.m — the category carries the name the author wrote */
   @interface NSString (Geometry)
   - (BOOL)isPointLiteral;
   @end
   @implementation NSString (Geometry)
   - (BOOL)isPointLiteral { return NO; }
   - (Point *)pointValue { /* … */ }
   @end
   ```
   **Three things the example shows, all measured.** A class extension may hold a stored property —
   `@property` with auto-synthesis, in the same unit as the `@implementation`, compiles and works —
   while the same property in a **category** is *unimplementable*, because a category has no ivar to
   synthesise into: clang's best case is *"property 'n' requires method 'n' to be defined — use
   @dynamic or provide a method implementation in this category"*. And the category's unit needs
   `import Point`, since **both** constructs require the class's `@interface` to be visible.
5. **Closures — DECIDED (2026-09): one shape, and the inline form is the trailing form.** The
   shape a block uses is `(a: Int32) [weak self] { … }` — a parameter list, an optional **capture
   list**, then a body (§7.33, §7.51) — and that is now the *only* closure syntax: a block written
   *inside* the parentheses uses it too, so `foo((a: Int32) { return a > 0 })` replaces the
   standing default `{ (a: Int32) -> Bool in … }`. The `in` form is retired, which is what leaves
   one place to put a capture list instead of two.
6. **Errors.** `throws -> T` lowers to a trailing `NSError **` parameter, hidden
   from the source. **DECIDED (2026-09): the default stands** — the selector gains Cocoa's
   `…error:` piece, so a throwing `method f(a: Int32) -> Bool` is `- (BOOL)f:(int32_t)a
   error:(NSError **)error`. Hiding the parameter is the whole of the translation, and the
   selector carries it as Cocoa's does, so an imported `…error:` selector round-trips unchanged.
7. **Class prefix — DECIDED (2026-09): none.** The specimen says `MyClass`, and the only
   constraints are the runtime's reserved names (`Object`, `Protocol`, `ProtocolGCC`,
   `ProtocolGSv1`, `__IncompleteProtocol`, `_NSConcrete*Block`) — the same class of collision that
   forced the Foundation's `NS` prefix. A mandatory module prefix is rejected: it would rename
   every class in the language to guard against a collision the runtime's own list already names.
8. **`init` — DECIDED (2026-09): an initializer is written `init(arg: T)` — the `method` keyword
   and the `-> Self` return both implied — and it is called `T(arg: v)`.** The declaration
   emits `[[T alloc] initArg:…]`; the return is `instancetype` (§4), and Cocoa's `initWith…:` comes
   from naming the label `with…` (§7.49). **Its body writes no `return`** — the emitter supplies
   `return self;` — and **a subclass's initializer must chain with `self = Superclass()`**, which
   emits `self = [super init]` rather than a fresh `alloc`. On a struct it is a function returning
   the struct by value (§5) — the same call form as §6's literal.
9. **`import` — DECIDED (2026-09): the keyword is `import`, and it names a *module*, not a file.**
   **Target emission: a module import** — `import Foundation` should emit `@import Foundation;` —
   with the file form as the fallback this tree can build today. Naming a *module* is also the
   answer to the granularity question below: a module is what the emitter groups a generated
   header set into, one level above a source file.
   - **Measured (2026-09), and it is why the module form is a *target* rather than the emission.**
     Four spellings tried, all four refused on this tree: `@import Foundation;` → *"use of
     '@import' when modules are disabled"*; the same **with `-fmodules`** → *"fatal error: module
     'Foundation' not found"*, because enabling the flag is not enough without a **module map**;
     and `#import <Foundation/Foundation.h>` / `#import <Foundation.h>` → *"'…' file not found"*,
     the Foundation's directory being on no angle-bracket search path.
     - **A fifth try, with a real map, got further and still failed.** A hand-written
       `module.modulemap` naming the Foundation as an umbrella directory was *accepted*, and
       `@import Foundation;` got as far as **building** the module — where it failed with *"could
       not build module 'Foundation'"*. **That failure is diagnosed now (2026-09) and it was never
       about modules**: beneath the summary line the real error is
       `Foundation.h:21:9: fatal error: 'foundation/NSObjCRuntime.h' file not found` — the header
       imports its siblings as `<Foundation/…>`, so *any* modular build of it needs the same include
       path its importers need. Add `-Iuserland` and the module builds and the probe exits 0. Nothing
       inside the headers had to change.
     - **And the file form is not as available as it sounds either.** Measured: `#import
       "Foundation.h"` *also* fails — *"'Foundation.h' file not found"* — so the Foundation's
       directory is on no default search path at all. `#import "file.h"` compiles when the header
       is *findable*, which for the Foundation means an explicit `-I` the tree does not pass today.
     **So the target needs three things, not two** — all three now measured, and the third is
     precisely what was missing: a `module.modulemap`, `-fmodules` in the build, and `-I` for the
     Foundation's headers.
   - **Any `.h` file can still be imported**, not a fixed set: until the module map exists, the
     surface names a module and the emission is the file import standing in for it.
   - **"No preprocessor" is the part with reach.** No `#include`, no `#define`, no `#if`: the
     surface has exactly one way to bring declarations in, and conditional compilation is not
     in the language. That is also why §8 can say "no macros" — the preprocessor is a
     translation phase the language does not borrow, rather than a feature withheld from an
     otherwise faithful re-spelling.
10. **Leaving an optional — DECIDED (2026-09): `!`, and the four binding
    forms, and `??` substitutes.** `x!` asserts and traps; `if let` / `if var`
    branch; `guard let` / `guard var` is the early exit; `lhs ?? rhs` yields the
    unwrapped `lhs` or the non-null `rhs`, with `rhs` evaluated only when it is
    needed and `lhs` evaluated once (§6, §7.22). All are v0.
    What is deliberately **not** in v0, and does not need to be: **general
    narrowing** of a bare `if x != nil { … }`. That would require a dataflow
    pass; the binding forms narrow *structurally* — the binding's own scope —
    so the compiler needs scoped bindings, not dataflow.
11. **Does the compiler *verify* non-null? — DECIDED (2026-09): when it can, and it says which.**
    A `nil` literal in a non-null position is an **error**, as the default here already said — and so
    is a non-null property left unassigned across `init`, *where the compiler can see the whole
    initialization*. `return nil;` in a `-> String` method is the same class of check and needs no
    dataflow at all; a property's definite initialization does, which is the same dataflow capacity
    §7.14's struct-mutation inference needs. The rule is §7.38's and §7.40's, applied to nullability:
    **refuse what can be proved, and never assert what cannot** — which is also why §9.5 reads an
    unannotated import as nullable rather than assuming.
12. **Locals — DECIDED (2026-09).** `let name: T = e` / `var name: T = e` is
    Swift's convention, and **the `: T` may be omitted when the initializer
    carries the type** (§7.19). `let` emits `const T` for a scalar or a struct
    and `T * const` for a class type; `var` emits neither, and which form is
    emitted follows the *type*, whether it was written or inferred. The width a
    literal falls back on is `Int` (`NSInteger`) for integers and `Float64` for
    floats, and only where there is no expected type (§4).
13. **References and values — DECIDED (2026-09).** A class instance is a
    reference (an ObjC object pointer, `id` at the runtime level); a struct, a
    scalar and an enum are values. §4 states the consequences of the value rule —
    no `StructName?`, no class-typed struct property, no class-typed associated
    value — and §5 the second difference: **a struct's methods are C functions**,
    `self` being the first parameter.
14. **A struct method may mutate `self` implicitly — DECIDED (2026-09): no keyword, and the
    emitter infers it.** A method that assigns to a property takes `Point *self`; one that does not
    takes `const Point *self` (§5). With the `mutating` keyword gone, **the body is what decides**,
    so the emitter runs the dataflow pass the alternative reading once priced — the cost is real,
    and it is the price of not making an author write a fact the body already states. `const` still
    earns its keep: it is what makes calling a mutating method on a `let` an error.
    - **`mutating method` is accepted and ignored — DECIDED (2026-09).** The keyword is redundant
      now rather than wrong: it states what the body already says, so it joins the tolerance family
      — an explicit `let` on a parameter (§7.28), `required` (§7.48), `method` on an initializer and
      `-> Self` (§7.49). Nothing is rejected, and no author has to unlearn the word.
15. **Every bare `@property` attribute also has a keyword form before `property` — the
    placement is DECIDED, and now general (2026-09).** `readonly property x: T` is the
    **preferred** spelling and `property (readonly) x: T` the alternative: the parenthesis
    mirrors ObjC's `@property (…)` attribute list one-to-one (§5), and the keyword form is the
    same attribute written as a modifier in the declaration — which is where `weak` and
    `unowned` landed (§7.52, §7.53). The rule this item was groping for is simply **if it can
    go in the parentheses, it can go before `property`**; three consequences, one boundary, and
    one preference.
    - **`readonly`, `copy`, `nonatomic`, `strong`, `assign`, `atomic` and the rest are all
      selectable as keywords.** `strong` and `assign` were the *inferred* pair and were never
      written (§5) — the inference is unchanged, but it is no longer the only spelling when an
      author wants to say it out loud.
    - **A class property is reachable the same way.** Measured: `@property (class, readonly,
      nonatomic)` is a real attribute list, so `class property x: T` is its keyword form — and
      it joins `class method` (§5), which the modifier shape already covers.
    - **The boundary is the *parameterised* attribute.** `getter=isDone` and `setter=setDone:`
      carry a value, so no bare keyword exists for them (measured: the parameterised form is
      legal in the list). They stay in the parenthesis — which leaves the parenthesis exactly
      one job rather than deprecating it.
    - **The document's house style is keywords, always** (decided, 2026-09). The parenthesised
      form is never *wrong* — it is the faithful transcription — but the examples here are
      being swept to keywords and new text should be written that way. Several attributes
      accumulate before `property` in any order (`readonly copy property x: T`), because the
      emitted attribute list is a *set* whose order carries no meaning — which also settles
      §9.11, where the parenthesis's ability to take a *list* was the open question.
16. **Struct inheritance — DECIDED (2026-09), and the flag's placement is a *documented
    requirement*.** `struct D: Base` lowers to an anonymous tagged member at offset 0, which
    needs `-fms-extensions` and the suppression of the resulting
    `-Wmicrosoft-anon-tag` (§5). **The flag can only go in the ObjC wrapper** — the shape lives in
    a generated header, so it is not a per-file choice — and enabling it there enables MS
    extensions for every ObjC translation unit in the tree. That is the requirement, recorded so
    it is not rediscovered: the build passes the flag, and the cost is the dialect, tree-wide. *Recorded alternative, measured equivalent:*
    the same layout with a **named** first member — `typedef struct Point3 {
    Point base; float z; } Point3;` — needs no flag and no warning, the upcast is
    equally valid (`base` is at offset 0), and only the *emitted* field access
    differs (`p3.base.x`, which the emitter writes, so a Sterling author never sees
    it). The MS form buys nicer generated code; the named form buys no dialect
    change. The MS form is chosen; this is the trade-off.
17. **Enums — the two kinds are DECIDED (2026-09), as are the case name (§7.18)
    and an explicit value (§5).** Which kind you get is decided by the members,
    not by a keyword: a plain C enum when they carry no associated values —
    written `case name`, or `case name = n` to pre-set one — and a tagged union
    when one or more carry
    associated values. **A switch extracts them** (decided, 2026-09): the matched
    case's associated values are in scope in its body as `const` variables, named
    and typed by the declaration, with no binding syntax (§6). **Both things this bullet used to
    leave proposed are now decided**: a case's payload *arguments* are the qualified, labelled
    construction (§7.35), and several patterns share one body as a comma-separated pattern list —
    `case .a, .b { … }` (§7.24).
    **The underlying type may be declared** — `enum FooBar: UInt8 { … }` (§5) —
    which closes the `NS_ENUM` gap I had left here: a fixed width, no macro
    needed, and the value range checked against the type that was asked for.
    **`Bool` is admissible as a base** (decided, 2026-09), and it emits as `BOOL`
    (§4), so the enum is `unsigned char`-backed and one byte (measured).
    **A tagged union may take one too**: `enum E: UInt8 { … }` fixes the *tag*'s
    type, emitted as an anonymous `enum : uint8_t { … } tag;` (measured) — and it
    costs nothing, since the payload dominates the struct's size in every case
    where an `int` tag would have been the larger member.
    **A tagged-union case's tag may be pre-assigned** as well
    (`valueOne(associateValue: Int32) = 4`, §5) — that value is the *tag*, not the
    payload. **Two member rules hold for either kind** (decided, 2026-09): a
    **name may appear only once** — C's own enumerator rule, and the source is
    where it should be reported, since a duplicate name failing in the *generated*
    C is one an author never reads — and **two members may share a value**, so
    `enum Foo { bar = 0, baz = 0 }` is valid: an alias C allows, and the language
    keeps it. (The earlier "duplicated cases are a compile-time error" was wrong
    and is struck.)
    **A shared tag is allowed only when the aliased cases' payloads are
    identical** (decided, 2026-09) — identical meaning the same field names and
    types, so the union arms are interchangeable and the read is well defined. That
    is the one condition that makes sharing meaningful where the value is *also*
    the discriminant: the cases are then genuinely one case under two names, and
    anything weaker (the same *size*, say) would let a read reinterpret a payload as
    the wrong type, which no union can detect. §5 states the rule and the
    emission's freedom to give the aliases one arm.
18. **Enum access is qualified — DECIDED (2026-09).** A case is named
    `MyEnumType.valueOne`, for either kind, with `.valueOne` as the shorthand
    wherever the type is already known (§5). The qualification maps to the bare C
    enumerator for a plain enum and to the prefixed one for a tagged union — so
    it is sugar the C never sees, and it is why the source cannot show the
    collision C would report (§9.14).
19. **A declaration's type may come from its initializer — DECIDED (2026-09), for *any*
    initializer.** `let p = Point(x: 0, y: 0)`, `let s = "text"`, `let b = true` and `let x = 3`
    all need no written type, and **neither does `let v = makeThing()`**: the initializer's type
    supplies it wherever the expression has one (§9.15, decided 2026-09 — this item first read
    the rule as literal-only). An unsuffixed integer literal's type is `Int` (`NSInteger`) and a
    float literal's is `Float64` (§4), and the literal default applies **only where there is no
    expected type** — in `let n: Float32 = 0.1` the literal *is* a `Float32` — so the two halves
    are one mechanism: the expected-type machinery the `.case` shorthand uses (§5), run in the
    other direction. Where the expression has no type at all — `nil`, an empty collection literal
    — the annotation is still required, which is that same rule rather than an exception to it.
    §4 states it; the plan's K2 carries the type checking.
20. **A condition is always a `Bool` expression — DECIDED (2026-09).** `if`,
    `while`, the `?:` condition and the operands of `&&`/`||`/`!` all require a
    `Bool` (§4's Booleans). So `if n` is an error where C would accept it — write
    `if n != 0` — and C's `if (ptr)` idiom is `if p != nil`, a nil comparison
    being one of the things that *does* yield a `Bool`. This is also what makes
    the `unsigned char` carrier safe: a `BOOL` can only come from a boolean
    expression, never from a truncating cast of an arbitrary integer.
21. **Boolean operations are C/ObjC's — DECIDED (2026-09).** `!`, `&&`, `||`, the
    comparisons, and C's short-circuit semantics; the result type is `Bool`
    rather than C's `int`, and the bitwise operators are deliberately *not*
    among them, for the `~YES` reason §6 gives.
    - **Bitwise operators are numeric-only — DECIDED (2026-09).** `&`, `|`, `^` and `~` are
      therefore **not admitted on a `Bool`**, which settles the first of the two C habits this item
      left open: a `Bool` takes part in `!`, `&&`, `||` and the comparisons and in nothing else.
    - **Assignment is an expression — DECIDED (2026-09)**, as in C, so `if (x = f())` type-checks.
      It passes here only when `f` returns `Bool`, which is what makes it a better failure than C's:
      a condition is a `Bool` expression (§7.20), and an assignment to a `Bool` is one.
22. **Null-coalescing `??` — DECIDED (2026-09).** `lhs ?? rhs` takes a `T?` on
    the left and a `T` on the right and yields a `T` — **always non-optional**.
    Both operand types are checked rather than coerced: a **non-optional left**
    and an **optional right** are each **compile-time errors** (§6), which is why
    a chain through optionals is impossible rather than merely useless, and why
    `a ?? nil` is rejected. The right operand is evaluated only when the left is
    null, and the left exactly once. It is the fourth way out of an optional and
    the only one that *produces* a plain value (§4's Nullability, §7.10).
    **Its precedence is confirmed (2026-09)** — looser than the comparisons, tighter than `?:`,
    right-associative — which is Swift's shape, as §6 states it.
23. **Statements end at the newline — DECIDED (2026-09) in full.** A `;` is never required; it
    only separates two statements on one line, and a trailing one is accepted, because a statement
    may be empty (§6, and the specimen writes them). The emitter inserts the `;` that C needs.
    **The continuation rule is accepted (2026-09)**: *an expression that is syntactically
    incomplete continues* — an unclosed bracket or a trailing binary operator — which covers a
    wrapped argument list without asking for a visible continuation character. The stricter rule
    (Go's shape, deciding operator-last-on-the-line explicitly in every case) is rejected: it buys
    less room for surprise than it costs in ceremony.
24. **`switch` is exhaustive, does not fall through, and each case is a block —
    DECIDED (2026-09).** Every case must be covered or a `default` given, and each
    case exits after its body, so the emitted C gets the `break` (§6). **A case's
    body is a braced block** (§7.35): `case .valueOne { … }`, and `default { … }` for
    the catch-all — which brings no associated values into scope (§7.36). That is *why*
    the no-fallthrough rule needs no extra syntax to
    state — there is nowhere for control to fall to, and the braces say so where an
    author reads it rather than in a rule they must remember. A case that does
    nothing is written `{ }`, not omitted.
    **Several patterns sharing one body are accepted (2026-09)**: a comma-separated pattern list
    in front of the same shape — `case .a, .b { … }`.
    **Range patterns were added by §7.65 (2026-09)** — `case 1...45`, `case 1..<10` — the first
    pattern beyond a single value, and *patterns* rather than a new expression type.
    - **The subject may be any type — DECIDED (2026-09)**, not only an enum: a `switch` on an `Int`
      — or on any other type — matches **specific values of that type**, with `default` covering
      everything else. That is what keeps the exhaustiveness rule affordable off the enum case,
      where the members are knowable and a scalar's values are not.
25. **A value type's methods are functions, and it has no class methods —
    DECIDED (2026-09).** An enum's instance methods lower exactly as a struct's do: `self` first,
    `const EnumName *` ordinarily and `EnumName *` when the method mutates — **which an enum's
    method may do implicitly, exactly as a struct's may** (decided, 2026-09, §7.14) — named
    `EnumName_name` (§5). `class method` is a
    compile-time error on either kind of value type, because a class method is a
    message to a class object and a value has none — the same absence behind
    layout-only struct inheritance and the exclusion of protocol conformance
    (§8). A type-level operation on a value type is therefore a plain `func` (§7.56) — a `class`
    is the type that *does* have class methods, which is the difference this error marks out.
    - **A value type's properties lower the same way, and it has no synthesised ones — DECIDED
      (2026-09).** A struct has no `@property` to synthesise storage with, so `property x: Float32`
      is not a struct shape at all: the fields are `var x: Float32` — a C member (§5's Struct) —
      and a property is an *accessor pair* the author writes, lowering to the same
      `TypeName_name(...)` functions as a method, with the getter's `self` `const` and the
      setter's not. So everything on a value type is a function, which is the same family §7.8's
      "a value type's initializer is a function returning the struct" belongs to.
26. **Generics are supported, through ObjC lightweight generics — DECIDED
    (2026-09).** A class may declare type parameters (`class Box<T> : Object`),
    the parameter being a compile-time annotation with no runtime and no ABI. **A
    type argument must be an *object* type for *this mechanism*** — a scalar cannot
    be one, and the runtime cannot hold a struct or an enum — but that is the limit
    of *lightweight generics*, not of the language: an argument the runtime cannot
    hold is **monomorphised** at compile time instead (§7.63), so neither a struct
    nor an enum is barred from being generic. This reverses the "no generics" line
    that used to stand here, and it does *not* reach the raw pointers, which are
    not class types (§9.18).
27. **Method overloading is by name — and that is what supplies "operator
    overloading" — DECIDED (2026-09); §7.72 later added a second route.** Two methods are distinct when their
    *selectors* differ, and a selector is made of names, so `init(foo: Int32)` and
    `init(bar: Float32)` are `initFoo:` and `initBar:` — two methods (§7.1). The
    corollary is a rule rather than a nuance: **an overload differing only in
    parameter types is a compile-time error**, being one selector with two bodies
    (clang words it *"duplicate declaration of method 'init:'"* — measured). And
    the capability people reach for operator overloading to get — polymorphic
    operations on one's own types — is what named methods supply, which is why §8
    can still list operator overloading as absent: there is no operator to
    overload, and nothing missing.
28. **A parameter may be `var`, and only `var` needs writing — DECIDED
    (2026-09).** `method object(atIndex: var Int32)` exposes the argument as a
    writable variable in the body, the default being the `const` one; the whole
    difference is whether the emitter writes the `const` (§5's Method). It is a
    copy and never an out-parameter — `mutating method` and a pointer parameter are
    the write-back spellings. **An explicit `let` is allowed and ignored** (decided,
    2026-09): it restates the default, so it is a *documentation* affordance — a way
    to write "this one is not writable" — and it emits the same `const` the default
    does.
    - **One place the default does not apply: a `set` block's implicit argument**
      (decided, 2026-09). `newValue` is emitted *without* the `const`, because a setter
      normalises what it is given — `newValue = clamp(newValue)` — and there is no
      declaration for an author to write `var` on. §7.55 has the reasoning; the point
      here is that this item's rule is a *default*, not a law.
    *The pattern this is the third instance of:* the language tolerates what is
    **redundant** and rejects what is **false** — hence a trailing `;` (§7.23), a
    `default` on a switch already exhaustive by cases (§7.24), and this; against a
    type-only overload (§7.27) or a non-optional left to `??` (§7.22), which
    contradict and are errors.
29. **The raw pointer takes a pointee, and that is the whole of C's pointer
    surface — DECIDED (2026-09).** `UnsafeMutablePointer` / `UnsafePointer` are its
    *pointee-less* case (`void *` / `const void *`), and adding one makes it typed:
    `UnsafeMutablePointer<Int32>` is `int32_t *`, `UnsafeMutablePointer<Error?>`
    is `NSError * _Nullable * _Nonnull`, and nesting gives `T **`. It is a
    *compiler-owned* bracket rather than a lightweight generic (§7.26), because
    that mechanism parameterizes class types only. Two consequences are codegen
    rules rather than surface ones: **the emitter inserts `__autoreleasing` when
    the pointee is a class type** — ARC *requires* an ownership qualifier on the
    inner pointer and errors on the plain spelling (measured) — and **each level
    carries its own nullability**, so the common out-parameter needs only the inner
    `?`. Ownership stays unspellable (decided), and an **object-pointer table** is
    out of scope: its elements are `__strong`, not `__autoreleasing`. §9.18 holds
    the full table and the rejected alternative.
30. **C's `char` is `Character`, and it emits `char` — DECIDED (2026-09).** A third
    name beside `Int8`/`UInt8`, because C's `char` is a third type; it exists so an
    imported `char *` signature accepts it with no cast (measured: `unsigned char *`
    is *not* accepted for a `char *` parameter — an error, not a warning). Its
    measured consequence is that `char` is **signed** on this target, so a UTF-8
    byte ≥ 0x80 reads negative and decoding goes through the byte conversion
    (§9.17) rather than a bare compare. §9.19 holds the reasoning and the rejected
    alternative.
31. **`String` is `NSString`, and every prelude class drops its `NS` in Sterling —
    DECIDED (2026-09).** `NSString` ⇄ `String`, `NSArray` ⇄ `Array`, `NSError` ⇄
    `Error`, `NSObject` ⇄ `Object`, `NSNull` ⇄ `Null`, and the rest by that one rule — with one
    refinement for the last: **`NSNull` is a class whose *value* is never written**, because the
    language spells its null `nil` and the emitter converts it (§4, §7.59). The mapping is
    **transparent in both directions**: the Sterling name *is* the class at runtime,
    so nothing converts, nothing is copied, and a Sterling `String` may be handed to a
    C function that wants an `NSString *` with no ceremony. (`NSInteger` /
    `NSUInteger` are typedefs rather than classes and keep their names — their
    Sterling names are `Int` / `UInt`.)
    Three consequences follow from `String` being a **class**:
    - It is a **reference** (§4): two bindings of one literal name the same object,
      and it is nullable-capable, so `String?` is a type.
    - It may be a **lightweight-generic argument** — `Array<String>`,
      `Dictionary<String, Number>` — which is the structural payoff the renaming
      buys beyond brevity (§7.26).
    - A literal is a `String` (§4's initializer rule) and emits the same constant
      `@"…"` the ObjC side already writes.
    And C strings get their own pair: **`CString` is `const char *` and
    `MutableCString` is `char *`** — the plain name is the read-only one, exactly as
    `UnsafePointer` is `const void *` beside `UnsafeMutablePointer`. §9.19 holds the
    element type, `Character`.
    *Swept, 2026-09:* the doc's examples now spell these classes the Sterling way
    throughout. The `NS` names that remain are the C side — the type table's right
    column, the emitted `@interface` / `+ (void)…` signatures, the
    `NSInteger` / `NSUInteger` typedefs, `NSMakeRange`, `NSAssert`, header paths —
    plus the deliberate `NS…` ⇄ `name` mapping statements, such as this item.
32. **`==` on a class-typed value emits `[a isEqual:b]` — DECIDED (2026-09).**
    Otherwise `String`, `Array`, `Number` and `Data` would compare by *pointer*
    identity while *reading* like value equality — false for two equal strings, and
    silently. `!=` is the negation. It needs no new mechanism: the prelude's `Object`
    declares `isEqual:`, and it is pointer identity unless a class overrides it
    (measured — `foundation/NSObject.h:145`; a receiver whose chain lacks the
    declaration is a warning, not an error). §9.20 holds the reasoning and the rejected
    alternative, and the one part that *was* open — `==` on a **struct**, which C does
    not have at all — is now **§7.34's decision: a compile-time error** (2026-09).
33. **A trailing block may supply the final function-typed argument — DECIDED
    (2026-09).** When a method's last parameter is a function type,
    `method foo(bar: (Int32) -> Bool) -> Void` may be called as
    `foo() (bar: Int32) { return false }`: the block follows the call's own
    parentheses instead of sitting inside them. The shape is the language's own —
    **a parameter list, a capture list, then a body** — the middle slot optional, needed only
    to name a capture that differs from ARC's default (`(bar: Int32) [weak self] { … }`,
    §7.51) — exactly as a `method` is written — which is
    what makes it readable where `^{ … }` is not; and it is a pure re-spelling,
    because the emission is the same block literal in the selector's last piece:
    `[o foo:^BOOL(int32_t bar) { return NO; }]` (verified), a label-less `^{ }` for a
    no-argument `Void` block included.
    - **The closure's parameters are its own**, one name each: `(bar: Int32)` names
      the parameter the body sees and the C parameter that carries it. A block has no
      selector, so there is no external/internal pair here (§5's Method) and this
      name is **not** an argument label.
    - **So the trailing argument's label is not written** — the one exception to
      "every call names its arguments" (§7.2). It needs none to be unambiguous: the
      position is fixed (last) and the block declares its own parameters. Every
      *other* argument keeps its label: `go(n: 1) () { … }` when the last parameter is
      a `Void` block. The *call's* parentheses are not omitted even when the block is
      the only argument: §7.60's rule permitting that is withdrawn (2026-09), since
      `foo { … }` cannot be told from a bare name followed by a statement's block.
    - **The closure's parameter list is part of the notation and is always written
      — DECIDED (2026-09), superseding this item's earlier reading.** `(foo: Bar)
      [weak self, baz] { … }` is the *only* closure notation, inline or trailing:
      there is no bare `{ … }` closure form anywhere. This item previously allowed the
      bare form for a block taking nothing, and that is withdrawn — a `Void` closure is
      written `() { … }`, with the empty list written out. What the list may still omit
      is each parameter's *type* (§4's expected-type rule, next bullet), never the list
      itself.
      - **That is also what removes an ambiguity the parser hit.** With a bare `{` no
        longer a closure, `for item in items { … }` puts its brace unambiguously on the
        statement, and a closure is recognised by a `(` … `)` followed by `[` or `{`.
        An attempt to read a trailing `{` as a closure swallowed a `for`'s body and
        broke a file that had been parsing; the rule above is why that reading was
        wrong rather than merely inconvenient.
    - **The parameter types come from the parameter's own type** (§4's expected-type
      rule), so `(bar)` may be written for `(bar: Int32)` — and where they *are*
      written they are checked against it. The **return type is never written**: it is
      the function type's, which is why the specimen call reads `{ return false }`
      with no `-> Bool`.
    - **The space is required**, as written above. Without it the parser cannot tell a
      block's parameter list from a parenthesised expression in argument position,
      and there is no reason to make it guess.
    **And the inline form is now this same shape — settled (2026-09, §7.5).** A block written
    *inside* the parentheses is `(a: Int32) { … }`, with the `in` spelling retired, so there is one
    closure syntax rather than two — and one place to put a capture list.
34. **`==` on a struct is a compile-time error — DECIDED (2026-09).** C has no `==`
    for a struct at all — both operands would be aggregates — so the honest
    re-spelling is to refuse rather than to invent memberwise equality, which the
    language would then have to define recursively (through nested structs, arrays
    and unions) and justify nowhere in the C. It also **closes §9.13's equality
    sub-item**, because a tagged-union enum *is* a struct (§5) — and there the
    refusal is stronger than a convention: the payloads carry padding, so even a
    memberwise compare would need per-case rules.
    *What the diagnostic is for matters, so it is written down:* the fix is the
    exhaustive `switch` (§6, §7.24) — designed to be the one way to read a payload —
    or, for a plain struct with no union inside, comparing the members the author
    actually cares about. The error should name that rather than only say no.
    With this, `==` is complete across the four type families: C's `==` for scalars
    and plain enums, `[a isEqual:b]` for class types (§7.32), and an error here.
35. **Enum access, as written — DECIDED (2026-09).** One form, three things now
    settled rather than proposed:

    ```sterling
    enum MyOtherEnumType {
        case valueOne(intValue: Int32)
        case valueTwo(floatValue: Float64)
        case valueThree(boolValue: Bool, intValue: Int64)
    }

    var someTaggedEnum = MyOtherEnumType.valueOne(intValue: 44);

    switch someTaggedEnum {
        case .valueOne {
            // "intValue" is in scope in this block, and equals 44.
        }
    }
    ```

    - **The construction is qualified and labelled** —
      `MyOtherEnumType.valueOne(intValue: 44)` — each label the field's own name
      (§6, §9.13). That was only proposed before; it is now the decision, and the
      plain-function-per-case alternative is dropped.
    - **The pattern is bare.** `case .valueOne` lists no fields, because there is
      nothing to bind: `intValue` *is* the field, and it arrives in the block as a
      `const` variable named and typed by the declaration (§7.17). So the language has
      no binding syntax, and — the same absence — no `if case` (§6).
    - **A case's body is a braced block** (§7.24). The old sketch wrote
      `case .valueOne: use(x);` — a colon and bare statements — and the braces are the
      better rule for the reason §7.24 gained this turn: with no fallthrough there is
      nowhere for control to fall to, and `{ }` says so where an author reads it
      instead of in a rule they must remember. `default`, a plain enum's case, and the
      not-yet-settled multi-pattern case all take the same shape — **though `default`
      brings no associated values into scope**, matching any tag as it does and so
      having no type to name (§7.36).
    Verified for K1's sake, since the shape is decided but its emission is not free:
    it is a C `switch` on the tag with a block per case whose opening lines hoist the
    fields as `const` locals — `case MyOtherEnumType_valueOne: { const int32_t
    intValue = e.value.valueOne.intValue; … }` — and that whole skeleton, tag enum,
    payload structs, union and all, compiles clean through this tree's wrapper
    (measured).
36. **A `default` case brings no associated values into scope — DECIDED (2026-09).**
    A `default` matches *any* tag, so the exact type is not known at compile time and
    there is nothing for a payload name to mean. It is not an extra restriction laid
    on top of the design — it *is* the design: the emission hoists a matched case's
    fields by naming that case (`e.value.valueOne.intValue`), and a `default` has no
    case to name, so there is nothing to hoist.
    Two things follow, and the first is a pressure rather than a lack:
    - **To read a payload, the cases must be enumerated** — which the exhaustiveness
      rule (§7.24) makes cheap, since a case needs no binding syntax to be written
      (§7.35). So `default` is for coverage, not for reading, and the language has
      exactly one way to read a payload in either kind of enum.
    - **It is vacuous for a plain enum**, which has no associated values at all — so
      the rule reads the same for both kinds without being a special case of either.
    For a `switch` whose subject is not an enum — §7.24's other open, where `default`
    is the only case there can be — this stays consistent by construction: an `Int`
    has no payloads to reach for either.
37. **Numeric literals: underscores are elided, and the radix prefixes are
    `0x` / `0b` / `0o` — DECIDED (2026-09).** `1_234` and `1234` are the same
    literal. The grouping underscore is a *surface* device that the emitter removes,
    and that is not a cosmetic choice — **measured: `_` is a digit separator in
    neither C nor C++.** Through this tree's wrapper `1_234` is a C++ *user-defined
    literal* (`operator""_234`), and in C it is an invalid suffix. C23, like C++14,
    spells its separator `'` instead; the language prefers `_` and pays nothing for
    it, because the number is emitted with no separator at all.
    - **An underscore may only sit between two digits.** `_1`, `1_` and `1__2` are
      errors — and measured, each is a *different* C/C++ error (`undeclared
      identifier '_1'`, `operator""_`, `invalid suffix '__2'`), which is precisely why
      the surface has to define the placement instead of letting the C decide it.
    - **The prefixes are `0x` hex, `0b` binary, `0o` octal, and their emission is not
      uniform** — measured: `0xFF` and **`0b1010`** are C as written (clang accepts
      `0b` here, and C23 standardised it), while **`0o17` is not C at all**
      (*"invalid suffix 'o17' on integer constant"*). So `0o755` emits as C's own
      leading-zero octal, `0755;` — the surface says which radix it means, and the
      emission uses the only spelling C has.
    - **A bare leading zero is therefore not writable.** `0755` is an error, so that
      C's silent octal trap cannot be entered by accident — C half-guards it itself
      (`08` is *"invalid digit '8' in octal constant"*, measured) and the surface
      closes it. *Confirmed, 2026-09.*
    The literal's **type** is untouched by any of this: unsuffixed is `Int` for
    integers and `Float64` for floats, with the expected type winning where there is
    one — and there are **no width suffixes**, because a declaration writes its width
    (§4). Where no declaration supplies it, an **explicitly typed literal** does
    (§7.38).
38. **A literal's type is written explicitly as `Type(value)` — DECIDED (2026-09).**
    `Int8(12)`, `Int16(450)`, `Int32(180000)`, `Int64(47528946234536)`, `Int(123242)`
    — and the same for `UInt`, `Float`, `Float32`, `Float64`. This is what completes
    the "no width suffixes" rule above: a *declaration* supplies the width when a
    declaration is what you are writing, and this supplies it when it is not — inside
    an expression, or under an inference (`let x = Int8(12)`).
    - **The value must fit, and a value that does not is a compile-time error.**
      `Int8(300)` is refused. C is not enough here and is actively unhelpful:
      measured, `int8_t a = 300;` and `return 300;` each *warn* (*"changes value from
      300 to 44"*, `-Wconstant-conversion`) — while an **explicit cast is silent**,
      and a cast is the natural emission. So the check has to be the language's. It is
      a *refusal* rather than a new meaning, so §0 needs no exception for it: a typed
      literal whose value cannot survive its type has no C spelling at all.
      (Emission, for K1: the value with the type's C form applied where it is needed —
      a cast, or the `f` suffix for a `Float32` literal, which §2 already shows.)
    - **`Float` is `Float32` and `Double` is `Float64`** — the short names beside the
      explicit pair (§4), playing the role `Int` plays for `NSInteger`. A declaration
      writes its width (§4), and these exist because the C side writes them, exactly as
      `Int`/`UInt` exist for `NSInteger`/`NSUInteger`. `Double` is confirmed
      (2026-09); it confirms `Float` by symmetry too.
    - **It is a constructor call, not a conversion (§7.47).** Applied to something that is
      not a literal, `T(x)` is still `T`'s initializer — valid for the numeric types
      exactly where a representable conversion exists (`Int32(anInt16)` valid,
      `Int32(aFloat64)` a compile error, since no such initializer is declared). That is
      the half of §9.17 this settles, and the reading is no longer in doubt: the language
      never *forces* a conversion, it calls something. For a non-numeric operand it is not
      this form at all — a `String` to number is a message send, and a number to `String`
      is a `String` initializer if one is declared.
    - **§9.19's "how is a `Character` written" is *not* an instance of it — decided (2026-09):
      it is `'a'`, read as a `Character`.** That was this bullet's guess, and it is superseded: a
      character literal takes C's spelling and the language's type, emitting `(char)'a'`. So
      `Type(value)` stays exactly what this item says it is — a constructor call, and the numeric
      family's way in (§7.37, §7.38).
39. **Numeric conversions go up only, and they are always written — DECIDED
    (2026-09).** `Int16(anInt8)` is valid; `UInt32(aUInt64)` is a compile-time
    error. And there is **no implicit conversion in either direction**, which is the
    other half of the same rule: `let a: Int64 = anInt32` must be written
    `Int64(anInt32)`, and C's usual arithmetic conversions do not apply — so `x + y`
    of two `Int8`s is an `Int8`, not the promoted `int` C would have produced. *(That
    second half is read from "do not promote", which is the only way to take it as a
    statement about this language rather than about C. If the intent was instead that
    *implicit widening* is fine and only narrowing is refused, this paragraph is the
    one to change and the rest of the item stands either way.)*
    **What "up" means, precisely: the target can represent every value of the
    source.** That is the reading that is sound, and it is what makes the rule a
    *check* rather than a mechanism — no runtime work, no new semantics, just a
    compile-time comparison of two ranges:

    | from → to | |
    |---|---|
    | `Int8` → `Int16` | valid — the case the rule was stated with |
    | `UInt64` → `UInt32` | error — the case the rule was stated with |
    | `UInt32` → `Int64` | valid — wider *and* signed enough |
    | `Int32` → `UInt64` | **error**, though it is wider: `UInt64` cannot hold a negative |
    | `Int64` → `UInt64` | error — same width, cannot hold a negative |
    | `Int32` → `Float64` | valid — 53 bits of mantissa cover 32 |
    | `Int32` → `Float32` | **error** — 24 bits of mantissa do not |
    | `Float32` → `Float64` | valid; `Float64` → `Float32` is an error (precision) |
    | `UInt32` → `Float64` | valid — the same 53 bits, unsigned source |
    | `Int16` → `Float32` | valid — 24 bits cover 16 |
    | `UInt32` → `Float32` | **error** — 24 bits do not cover 32 |
    | `Int64` → `Float64` | **error**, and it is the one to look at: 53 bits do not cover 64 |

    The four bold rows are where "wider" and "representable" part company, and the
    rule is *representable*: a width-based reading would quietly accept `Int32(-1)`
    as a `UInt64`, which is the exact class of bug the rule exists to stop. The same
    test crosses the integer/float boundary, and the last four rows are where it
    reaches furthest — **`Int64` → `Float64` is an error even though both are 64
    bits wide**, which is precisely the silent precision loss C permits and this rule
    refuses; `UInt64` → `Float64` follows from the same reason. **Confirmed (2026-09)** — the
    int-to-int rows are the decision, the float-boundary ones are derived from it, and the four
    that extend it across the boundary are the derivation's furthest reach.
    - **The emission is free.** Where a conversion is valid, C's conversion is itself
      value-preserving, so `Int64(anInt32)` emits the operand and nothing more — the
      conversion is a *check*, not code. Casts appear only where an expression's
      *type* must be pinned against C's promotion (the `Int8 + Int8` case above).
    - **The adjacent gap is §7.40's**: arithmetic that overflows its own type —
      `Int8(100) + Int8(100)` keeps the type `Int8` and has no room for the answer. It
      **traps**, signed or unsigned, and `&+` is how an author asks for the wrap
      instead.
    - **And §7.44 is the counterpart this rule does *not* govern.** The up-only rule
      bounds a *conversion* — `T(x)`, where failure has no value — so the compiler
      refuses a down conversion outright. `as?` is a different construct with a defined
      failure: `x as? Int32` converts when the value fits and is nil when it does not.
      That is the only spelling this language has for a *checked narrowing*, precisely
      because the rule above refuses the unchecked one.
40. **All arithmetic overflow traps — DECIDED (2026-09).** `Int8(100) + Int8(100)` is a
    runtime error, not `-56`. The language does what Swift does: overflow and
    underflow **stop the program**, signed and unsigned alike. This reverses the
    C-wrap reading that briefly stood in this item's place and in §7.41 — see the
    tombstone below.
    - **Deliberate wrapping is written, not implied**: `&+`, `&-`, `&*`. Without them
      the language could not express a checksum, a hash, or a ring index at all —
      §7.39's up-only conversions close the unsigned detour (`Int32` → `UInt32` is a
      *down* conversion), so arithmetic that may legitimately wrap needs its own
      operators rather than a cast.
    - **The emission is a header-only checked helper, never `-ftrapv`.** Every
      operation goes through clang's overflow builtins —
      `if (__builtin_add_overflow(a, b, &r)) sterlingc_trap_overflow();` — which need no
      runtime library at all (measured: the form compiles to an object through this
      tree's wrapper). `-ftrapv` was rejected for two reasons rather than one: it is a
      *global* flag, so it could not coexist with `&+`, and it covers signed only. The
      trap is the same header-only kind as `!`'s null trap (§6), so the plan's "no
      runtime library to stage" still holds.
    - **Compile time refuses what it can prove** — §7.38's out-of-range typed literal —
      and **everything else traps at runtime**. Those two are one stance: nothing in
      this language computes a wrong answer silently. **Its neighbours are §9.22** —
      division or modulo by zero, an out-of-range shift count, `INT_MIN / -1` — which
      are decided the same way and for the same reason. The only difference is
      mechanical: clang supplies overflow builtins for this item's arithmetic and
      **none at all** for division or shifts, so those three emit guards.
    - **Unsigned no longer wraps**, which is the part a reader arriving from C will not
      expect: the text that stood here said modulo 2^8 was the author's responsibility.
      It is now the `&+` family's, and plain `+` stops.
41. *(Superseded in the same session — kept as a tombstone.)* This item decided that
    signed overflow **wraps**. The decision above reversed it one turn later, and the
    numbering is referenced from §9.21 and §9.22, so it is not deleted. The reversal is
    worth knowing: the C-wrap answer was chosen for its *cost* (free, and measured so)
    and the trap then won on *meaning* — a stop beats a wrong answer. That measurement
    stands; it is simply no longer where the language wants to be.
42. **An unqualified call in a method resolves to a method first, a global function
    last — DECIDED (2026-09).** Written inside a method, `callSomeFunc(arg: arg1)` is:
    1. `self.callSomeFunc(arg: arg1)` when the name is a method — **this class's or an
       inherited one** — which is the ordinary case, and emits `[self callSomeFunc:arg1]`;
    2. otherwise a **global C function** of that name, emitting the plain
       `callSomeFunc(arg1);` with the label dropped (§2).
    One thing about the middle of that ordering, because it is subtler than it reads:
    - **An inherited method is found through `self`, so it is not a third step.** The
      resolution has two outcomes, not three: a method (own *or* inherited) is a send
      through `self`, and everything else is the global. ObjC's lookup already walks the
      chain. Writing `super.…` for the inherited case would mean something *different* —
      it starts at the superclass and so bypasses an override — and the language already
      spells that explicitly (§3's map: `super` is ObjC's). An unqualified call never
      has to mean it. *(If the intent was the static reading — an inherited-only method
      called with `super` dispatch, overriding bypassed — that is a deliberate
      divergence from ObjC and worth stating as one, because nothing else in the
      language behaves that way.)*
    - **A class method resolves the same way**, `self` there being the class object.
    **And the shadowing is total — DECIDED (2026-09).** A global function with the same signature as
    a local one is **shadowed**: the local wins and the global is **not reachable** by an
    unqualified call. No qualifier is introduced to get back to it — the module qualifier `import`
    names (§7.9) is not that mechanism — so an author who wants both writes different names.
43. **If it is valid in Objective-C, it is valid in Sterling — DECIDED (2026-09), and
    `AnyObject` is what it settles first.** The type is authorable — a local, a
    parameter, `Array<AnyObject>` (the last measured to compile as a
    lightweight-generic argument) — and **arbitrary message sends through it are
    valid**: `respondsToSelector:`, `performSelector:`, KVC, and any other selector,
    exactly as ObjC allows. The dynamic layer is *in* the language rather than behind a
    wrapper.
    - **The cost is named rather than hidden.** A send on `AnyObject` cannot be checked
      against a declaration, so the checking promise ends at `AnyObject` — the emitter
      is in `-Wobjc-method-access` territory there (measured this session for
      `isEqual:`), and the answer is the one used everywhere else: emit the send and let
      the runtime be the authority.
    - **It makes a downcast mandatory, and the language has none.** A cast is valid ObjC
      (`isKindOfClass:` plus a C cast), so it must be valid here, or an authorable
      `Array<AnyObject>` would be readable and unusable. The spelling first proposed here
      — §7.38's `Type(value)`, `MyClass(x)` — was **wrong**, and §7.47 is the correction:
      that form *constructs*, and no class declares an initializer taking an `AnyObject`.
      The cast is `x as? MyClass` (§7.44) or `x as! MyClass` (§7.46), and nothing else.
    - **Scope, stated because the principle cannot be universal.** It governs the
      *object model and its dynamism*: sends, casts, the runtime's own surface. It does
      not reach C's arithmetic and conversion looseness, because the language has
      already refused parts of that by decision — §7.39 refuses a mixed-type expression
      C accepts, and §7.40 makes overflow trap where C wraps. Read universally, this
      principle would reverse §7.40's unsigned half a third time.
44. **`x as? T` yields a `T?` — nil when the conversion is not possible — DECIDED
    (2026-09).** It is the *attempt*, and its sibling is §7.38's `T(x)`, which traps:
    `as?` is the form whose failure has a value. The examples that define its scope are
    deliberately two that can never work in C — an `Int` to an `UnsafePointer`, an
    `Array` to a `Bool` — and they yield **nil** rather than an error. That is the rule
    rather than an oversight: a construct whose result is well defined is never a
    compile error in this language. The same line makes an out-of-range typed literal an
    error — its operation *traps*, so the compiler may refuse what it can prove — while
    a failing `as?` is simply a nil.
    - **For a class it is the downcast** — `x as? MyClass`, checked with
      `isKindOfClass:` and yielding nil on a mismatch. This is what §7.43's principle
      required: without it an `Array<AnyObject>` would be readable and unusable.
    - **For a numeric it is the checked narrowing, which is where it earns its keep** —
      §7.39's up-only rule otherwise leaves *no* spelling for a down conversion at all.
      `x as? Int32` converts when the value fits and is nil when it does not. Measured:
      the check is `__builtin_add_overflow(v, 0, &narrow)` — the pointee type *is* the
      result type — so it rides the same header-only builtin family as the trap (§7.40)
      and needs no runtime library.
    - **Where even a dynamic check cannot help, the compiler may still say so.** A
      *statically* impossible `as?` yields nil, and a warning is the right company for
      it, because the author has almost certainly mistyped a type. The rule is nil; the
      warning is a recommendation rather than a refusal.
    - **`as!` is the third form (§7.46).** The reading that stood here — that `as?` under
      `!` makes a separate operator unnecessary — was superseded: composing does work,
      but the explicit spelling is in the language. So `T(x)` traps, `as?` yields a nil,
      and `as!` traps.
45. **A protocol is declared with the class syntax, and may inherit from protocols —
    DECIDED (2026-09).** `protocol C: A, B { … }` — a colon and a comma list, exactly as
    a class is written. The difference is what the list *means*: for a protocol every
    entry is a protocol it inherits, where for a class the first entry is the superclass
    and the rest are conformances. So the surface is uniform and the meaning is
    contextual, the same division §5 already uses for a class's comma list.
    - **The emission is ObjC's other bracket**: `@protocol C <A, B>` — measured to
      compile, multi-inheritance included. The colon is the surface's and the angle
      brackets are the emission's, so nothing new is emitted.
    - **A protocol name is a type.** In ObjC a protocol is not a type and the qualified
      form `id<C>` is required; here the name alone works — `let x: C`, and `C?` for the
      nullable form — which is what keeps the "declared like a class" promise whole: a
      class name and a protocol name are both type names. The emitter writes `id<C>`,
      and §5's forward-declaration rule covers protocols the same way.
    - **Conformance checking arrives free, and is worth knowing about.** clang checks
      the members itself: a class conforming to `C` without implementing `c` draws
      `-Wprotocol` (*"method 'c' in protocol 'C' not implemented"*, measured). That is
      the "second pair of eyes" §9.8 argues for, arriving without work — but it is a
      *warning*, so promoting it to an error is a decision rather than an inheritance. See the
      first of the two checks below.
    - **Member visibility is decided in §7.48** — `required` by default, matching ObjC, with
      `optional` as the prefix keyword. It is noted *here* because this bullet exposed the
      need: an optional member has to be expressible under §7.43's principle, and it is,
      since arbitrary sends and `as?` exist to check for one at runtime. Only the spelling
      was missing — and which of the two words gets marked had to be decided too, which is
      where the argument for matching ObjC won.
    - **Two checks, both decided (2026-09)** — and they land on *different* sides, which is the
      interesting part. They are recorded here because this is the item where protocols are argued.
      - **`-Wprotocol` is promoted to an error — DECIDED.** Measured, a class conforming to `C`
        without implementing a required member draws *"method 'must' in protocol 'P' not
        implemented"*, and that is only a warning. The language makes it a **compile-time error**,
        because it can *prove* the failure: it has the class's body and the protocol's required
        members, and nothing about the runtime can rescue it. It is the same reasoning that makes
        storage in a `category` a language rule rather than a clang one (§7.4).
      - **An unguarded send to an `optional` member is a warning, not an error — DECIDED.**
        Measured, `void use(id<P> p) { [p may]; }` compiles with **no diagnostic at all**, and traps
        at runtime when nothing implements it. The language warns at the call site because it
        *cannot* prove the failure: `p`'s runtime class may well implement `may`, and the
        declaration says only that it need not. §7.43's arbitrary sends remain how one checks —
        `respondsToSelector:` — so the warning points at a guard that already exists rather than at
        a new construct. **A warning where the compiler cannot prove, an error where it can** is the
        same division §7.38 and §7.40 already work by.
    - **A protocol's `NS` prefix drops exactly as a class's does** (§7.31): `@protocol NSCopying` is
      `Copying`. **The one place the rule meets itself is `NSObject`**, which Cocoa declares as
      *both* a class and a protocol and which would therefore map to `Object` twice. Measured: this
      Foundation declares only the class, so the collision is not present — but the rule is worth
      writing down before a Cocoa-shaped header arrives.
46. **`as!` is `as?` that crashes — DECIDED (2026-09).** The same conversion attempt, the
    same permitted pairs (any two types), with the failure being a **trap** instead of a
    nil: `x as! MyClass` stops the program if `x` is not one. It supersedes the reading
    in §7.44 that `as?` under `!` makes a separate operator unnecessary — composing does
    work, but the explicit spelling says what it does, and it is Swift's, so it costs
    nothing in familiarity.
    - **`T(x)` is not nearby at all (§7.47).** The split this bullet used to describe —
      two trapping conversions, one compile-checked and one asserted — rested on the wrong
      reading of `T(x)`: that form is a *constructor*, valid only where `T` declares an
      initializer, so it never converts an object that already exists. `as!`/`as?` are the
      only conversions there are, and the verbs differ: `T(x)` **constructs**.
    - **It joins the trap family, which is now three**: `x!` for a null (§6), `as!` for a
      conversion, and arithmetic overflow (§7.40). All three are header-only traps with
      no runtime library behind them, and all three are the same kind of thing — an
      assertion the compiler cannot prove, admitted because it *removes* a case rather
      than adding a capability (§0).
    - **A statically impossible `as!` still gets the warning §7.44 recommends.** The rule
      is that it crashes; the warning is the compiler being useful about a certain crash.
47. **`T(x)` calls an initializer; it is never a forced conversion — DECIDED (2026-09).**
    `T(x)` is valid **only if `T` declares an initializer taking a value of `x`'s type**,
    and it is a **compile-time error** otherwise. The language does not try to force a
    conversion it would have to invent: the set of valid `T(x)`s *is* the set of declared
    initializers. That settles what the construct is — a **constructor**, not a cast — and
    it re-founds §7.38 and §7.39 on a better footing than "a conversion the compiler
    range-checks".
    - **For the numeric types that set is the language's own**, and it is exactly §7.39's
      table: `Int8`, `Int64`, `Float32` and the rest are built-in types with a
      compiler-known initializer list — one for each *representable* conversion and for no
      other (`Int8(anInt16)` valid, `UInt32(aUInt64)` a compile error). The emission is
      unchanged and still free: a valid conversion is value-preserving, so C's own
      conversion is the whole of it.
    - **Those are not user calls, so §7.2's label rule has no exception to make here.**
      The unlabelled `Int8(12)` is the built-in conversion, not a call with a suppressed
      label: §7.2 keeps its single exception (the trailing block, §7.33) and this does not
      become a second. A *user-declared* initializer is an ordinary call, and carries its
      labels.
    - **The correction it forces: `T(x)` is not the downcast.** No class declares an
      initializer taking an `AnyObject`, so `MyClass(x)` is a compile error — §7.43's
      proposed spelling for the cast was wrong, and the cast is **only** `as!`/`as?`
      (§7.44, §7.46). That split is better than the one it replaces: these are different
      verbs, not two spellings of one — `T(x)` **constructs**, `as?`/`as!` **converts an
      object that already exists**.
    - **For a value type the same rule is §6's literal.** A struct's initializer is its
      field list, so `Point(x: 1, y: 2)` constructs and a memberwise mismatch is a compile
      error — which is what §6 already says, now as an instance of the general rule.
    **§7.49 closes the open that stood here** — how a user-declared initializer is
    *called*. §7.8's "an ordinary `method … -> Self`, no special form" turned out to be the
    whole answer: `init` is the name, and `T(arg: v)` is the call.
48. **A protocol member is `required` by default, and `optional` is a prefix keyword —
    DECIDED (2026-09), reversing the optional-by-default reading that briefly stood here.**
    `optional method m(…) -> R` and `optional property x: T`; an unmarked member is required,
    which is ObjC's default. The keyword stays a *prefix modifier* — the shape §5 already
    uses for `class method` and `mutating method` — so the reversal changes which word is
    written, not what kind of thing it is.
    - **The reversal's reason is stronger than the argument for the other reading.**
      Optional-by-default has real appeal: the *informal* delegate protocol, all-optional,
      is the dominant Cocoa shape and would need no markers. But it changes what a marker
      *means* — and a re-spelled Cocoa protocol would then read backwards, with
      `NSTableViewDelegate` needing `optional` added to forty methods and `required` to two.
      Matching ObjC means a marker means the same thing on both sides of the translation,
      which is the whole point of §7.43's principle.
    - **It also aims the free conformance check at what a protocol is *for*.** §7.45 records
      that clang checks conformance itself, and that check fires on required members. With
      ObjC's default it lands on the protocol's essence rather than on whichever members an
      author happened to mark, so the *contract* is what gets checked.
    - **Both halves of the check are now decided, and the second lives at the *call site***
      (§7.45): a class missing a required member is a **compile-time error**, while a send to an
      `optional` member with no guard is a **warning**. So `optional` is not only a word on a
      declaration — it changes what a *caller* is told, which makes it the first marker whose
      effect at the call site is a **diagnostic** rather than a visibility rule (§7.57's markers
      are the ones that say a caller may not call at all).
    - **The emission still groups, but the common case writes nothing.** Measured: `@required`
      and `@optional` are *sections* — running modes, not per-member markers — with `@optional`
      then `@required`, clang checks the required run's members only (`-Wprotocol` named
      `must` and never `maybe`, and the `@property` in the optional run escaped with it). So
      the emitter sorts members into runs and emits `@optional` for the optional one; an
      all-required protocol — most of them — gets no marker at all, and the generated header
      reads like a hand-written one. Reordering stays free: a protocol declares no layout.
    - **`required` is accepted and ignored — confirmed (2026-09)**, being the default written out
      loud, the same tolerance §7.28 gives an explicit `let` on a parameter. That confirmation
      reaches past this item: §7.49's explicit `method` on an initializer and its explicit
      `return self` are the same pattern, so the tolerance is now a family whose head is settled.
49. **An initializer is `init(arg: T)`, and it is called `T(arg: v)` — DECIDED (2026-09).**
    **Both the `method` keyword and the `-> Self` return are implied and are not written**
    (decided, 2026-09): the declaration reads `init(value: Int32) { … }`, and either of them
    spelled out explicitly is accepted and ignored — the same shape as an explicit `let` on a
    parameter (§5). Beyond that it is an ordinary method named `init` (§7.8), which is what makes
    the call form fall out of rules already in place: `T(…)` is a class-receiver message send (§6),
    the argument carries its label (§7.2), and the return is `instancetype` (§4) without being
    said. So `init(value: Int32) { … }` is called `Number(value: 3)` and emits
    `[[Number alloc] initValue:3]` — measured, `alloc` and `instancetype` included.
    - **The body returns `self` implicitly — DECIDED (2026-09).** A Sterling initializer writes no
      `return` at all: the language supplies it, and it is the *emitter* that needs the statement —
      ObjC's `- (instancetype)init` has to return the object, so the generated body ends in
      `return self;` whatever the author wrote. An explicit `return self` states the default and is
      accepted and ignored, the same shape as an explicit `method` above. It holds for a value type
      too, where `self` is the struct the function returns by value.
    - **A subclass's initializer must chain explicitly: `self = Superclass()` — DECIDED
      (2026-09).** Assigning to `self` is the form, and it is the one place `self` is writable;
      the receiver names the **superclass**, so the emitter writes `self = [super init]` and *not*
      `[[Superclass alloc] init]` — a fresh object would discard the one being initialized, which
      is the opposite of chaining. Measured, the emitted form compiles clean under ARC. A labelled
      chain is the same call with its labels: `self = Superclass(value: 3)` emits
      `self = [super initValue:3]` (§7.1). **It is a requirement rather than a convention** — a
      subclass initializer that does not chain is the thing the rule exists to catch — and a
      **root class** is the one that has nothing to chain to.
    - **And the emitted body has a middle step: the class's synthesised property defaults**
      (§9.16). The order is chain → defaults → the author's statements, so a default can be
      written to a `readonly` property — which is the point of it — while an explicit assignment
      in the body still wins. The chain has to come first because an ObjC initializer may return a
      *different* object, and a default written before it would be written into a discarded one.
    - **The name `init` is the whole convention, which is what closes §7.47's open.** That
      item asked how a user-declared initializer is *called*; §7.8's "no special form" is
      the answer, now that there is a call to write.
    - **A declared initializer is required — DECIDED (2026-09).** Nothing is synthesised, so a
      class that declares none cannot be constructed: `Sub()` resolves no initializer and is an
      error. Measured, the C would have allowed it — ObjC *inherits* `init`, so `[[Sub alloc]
      init]` compiles — which is why this is the compiler's rule to make rather than the emitter's
      to leave alone (§9.16).
    - **Cocoa's `initWithFoo:` is reached by naming the label `withFoo`.** §7.1's rule already
      does this — `init(withValue: Int32)` emits `initWithValue:` — so initializers need no
      selector rule of their own.
    - **`alloc` must be in scope, and that is a prelude obligation.** Measured: a root class
      that does not declare `+alloc` makes the emitted `[[T alloc] …]` warn
      (`-Wobjc-method-access`, *"class method '+alloc' not found"*), exactly as a chain
      without `isEqual:` warns (§9.20). The prelude's root supplies it; the language emits
      the call either way.
    - **A value type's initializer is a function returning the struct** (§7.8), so
      `Point(x: 1, y: 2)` is both §6's literal and an `init` call. One form, which is the
      consistency this rule was for.
50. **`_` as an external name writes the argument without its label — DECIDED (2026-09).**
    `method foo(_ arg: T)` is called `foo(someValue)`, and inside the body the parameter is
    `arg` as usual. This **revises §7.2**, which listed `_` suppression as *not* in v0 — and
    the reason it is wanted is worth recording: it is how a *one-piece* selector is written.
    §7.1 makes a method's first piece the method name with the first parameter's external
    name attached, so `addObject(_ object: AnyObject)` emits
    `- (void)addObject:(id)object` — Cocoa's own spelling — where a named label would have
    produced `addObjectObject:`.
    - **A per-declaration choice, not a positional call form.** §7.2's rejection of "an
      optional or positional form" stands: the *declaration* decides the labels, not the
      call. What is suppressed is one name, at one parameter, because a declaration said so.
    - **The first parameter is the case §7.1 leaves room for.** For a *later* parameter a
      suppressed name would emit an empty selector piece (`fooA::`) — legal-ish ObjC and
      nothing anyone wants — so that corner is left open rather than specified.
    - **It composes with the trailing block** (§7.33), which also writes no label: the
      trailing position already puts the block's own parameter list where a label would go,
      and `_` is the general form of the same idea.
51. **A closure captures `self` strongly by default — ARC's rule — and a *capture list* names
    the exceptions — DECIDED (2026-09), reversing the weak-by-default reading that briefly
    stood here.** So `self` inside a closure is an ordinary strong capture and stays
    **non-optional**, and the retain cycle is the author's to avoid again — which is what the
    capture list is for: `[weak self]`, between the parameter list and the body.
    - **The reversal makes the emission simpler, and the measurement is why.** The strong
      `self` capture is exactly what plain ARC emits — `objc_retain` plus the block's
      `objc_storeStrong` copy helper, measured — so with this default the emitter writes the
      block and does nothing else. The *weak* case still needs the work the other reading
      needed everywhere: ObjC has no per-capture marker, so `[weak x]` emits a synthesized
      `__weak` local the block then refers to (the `objc_initWeak` /
      `objc_loadWeakRetained` machinery, measured in §9.4). The cost moved from *every*
      closure to the ones that ask for it.
    - **A `weak` entry makes that name optional inside the closure, and only that entry.**
      `[weak self]` means `self` is `Self?` in the body — branch with `if let` / `guard let`,
      or assert with `!` — while `self` in a closure without the list is the plain `Self`. The
      discipline the cycle bug teaches is now something the author *asks for*, and the type
      says which one they asked for.
    - **It is a list of captures.** `[weak self, someVar]` takes `self` weakly and `someVar`
      strongly — which is also the default, so naming it is documentation rather than a
      change. **There are three qualifiers that mean something, and each is the word for what it
      does differently from the default**: `weak`, **`unowned`** (§7.53) — which §7.43's
      principle required, since `__unsafe_unretained` is valid ObjC — and **`var`** (decided,
      2026-09, §9.4), which emits `__block` and so *shares* the variable with the closure instead
      of copying it. `[unowned self]` is the non-retaining capture that is not nilled — `self`
      stays non-optional in the body, unlike under `weak` — and `[var count]` is the mutable one
      an accumulator needs.
    - **`var` is a *strong* capture of an object under ARC — measured, because the folklore says
      otherwise.** `__block Thing *shared` compiled with `-fobjc-arc` carries `objc_retain` and
      `objc_storeStrong`; with `-fno-objc-arc` neither appears. So the pre-ARC trick of using
      `__block` to break a retain cycle does not work here: for an object, `[var …]` shares the
      variable *and* keeps it alive, and `[weak …]` remains the cycle-breaker.
    - **The list sits between the parameter list and the body** —
      `(bar: Int32) [weak self] { … }` for a trailing block (§7.33), the one closure shape the
      document has settled. That is also an argument for finishing §7.5's open the way it
      leans: one closure shape means one place to put a capture list.
52. **`weak` is a prefix keyword on all three — `weak let`, `weak var`, `weak property` —
    DECIDED (2026-09).** A variable is `weak let w: T = e` / `weak var w: T = e`; a property
    is `weak property x: T`. One modifier, one shape, wherever a *reference* is declared — and
    a **class type is required** in every case, since a scalar has nothing to weaken.
    - **What this superseded, twice over.** The first reading here was that the two shapes
      deliberately differ — the property's qualifier *is* ObjC's attribute list, so its
      parenthesis is a transcription, while a local gets a chosen form. The second was a line
      drawn from that: shared modifiers are prefixes, property-only ones stay in the
      parenthesis. §7.15 then generalised past both — **if an attribute can go in the
      parentheses, it can go before `property`** — so the second reading is superseded as
      well, and what remains is the plain fact that `weak` can be written either way, with the
      keyword form being where this item settled it.
    - **Exactly one ownership attribute per property**, which is derived rather than added:
      ObjC's `weak`, `copy`, `strong` and `assign` are mutually exclusive, so
      `weak copy property x: T` is an error — two of them at once, and the parenthesis form is
      no better. `strong` and `assign` are the *inferred* pair, and since §7.15 they may be
      written too, which changes only whether the author says out loud what the inference
      already decided.
    - **The emission is direct, and measured**: `weak let` is `__weak Thing * const w`, and
      `weak var` is `__weak Thing *w` — both accepted under ARC, which is required anyway
      (a `__weak` reference does not exist outside it, and ARC is the language's default).
      The `const` is §5's rule for a class-typed `let` — the *pointer* is const, not the
      pointee — and weak is orthogonal to it, as the measurement confirms.
    - **A class type is required, and *that check is the language's*, not clang's.**
      Measured: `__weak int n` is only a **warning** (`-Wignored-attributes`, *"'__weak' only
      applies to Objective-C object or block pointer types"*) with exit 0 — so a weak scalar
      would emit and compile rather than fail. Refusing it is the same shape as §7.38's
      out-of-range literal: the check has to be ours, because clang will not make it.
    - It is meaningless for a **scalar or a struct** at all — there is nothing to weaken and
      ARC has no weak scalar — which is why it is a rule here rather than an emitter detail.
    **And `weak` is *not* allowed on a parameter — DECIDED (2026-09).** §7.28 lets a parameter be
    `var` (and tolerates an explicit `let`), so the modifier slot exists there — but a parameter's
    lifetime is the call, which makes a weak one useless, and this language makes that an **error**
    rather than leaving a spelling with no meaning. `weak let` / `weak var` are for locals and
    `weak property` for properties; a parameter takes `var` and nothing more.
53. **`unowned` is `__unsafe_unretained` — DECIDED (2026-09).** The non-retaining reference
    that is *not* nilled, joining `weak` as a prefix modifier wherever a reference is
    declared: `unowned let u: T = e`, `unowned var u: T = e`, `unowned property x: T`, and
    `[unowned self]` in a capture list (§7.51).
    - **It is the *unsafe* one, and that should be said where someone from Swift will read
      it.** Swift's `unowned` traps on a dead reference by default and spells *this* variant
      `unowned(unsafe)`; here the name maps straight to `__unsafe_unretained`, so a use after
      deallocation is not caught. That is not a defect — it is the qualifier ObjC has, which
      §7.43's principle requires to be expressible — but the divergence is worth naming,
      because the same word is safer in the language the syntax resembles.
    - **Both qualifiers are prefixes, and only one may be written.** `weak` and `unowned` are
      mutually exclusive, as ObjC's attributes are, so `weak unowned let x` is an error — the
      one-ownership rule §7.52 states for a property, reaching a local.
    - **The emission is direct, and measured**: `__unsafe_unretained Thing * const u` for
      `unowned let`, `__unsafe_unretained Thing *u` for `unowned var` — both accepted under
      ARC and both usable as a captured local. `unowned property x: T` emits
      `@property (nonatomic, unsafe_unretained) T *x;`, the attribute spelled without the
      leading underscores, which is how ObjC writes it inside that list.
    - **A class type is required, and again the check is the language's.** Measured:
      `__unsafe_unretained int n` is only a **warning** (`-Wignored-attributes`, whose text
      names `objc_ownership` because the qualifier is a macro) with exit 0 — identical in
      shape to §7.52's `__weak int`, so the same rule holds for the same reason.
    - **Unlike `weak`, it does not need ARC to exist** — `__unsafe_unretained` is valid under
      manual reference counting too. Not a feature to exploit, since the language is ARC, but
      it is the reason the two qualifiers are not two spellings of one thing.
54. **A `readonly` property may carry a bare block, which *is* its getter — DECIDED
    (2026-09).** `readonly property foo: Int32 { return 3 }` — no `get` keyword and no setter,
    because a readonly property has no setter to name. The long form with named accessors
    (`{ get { … } }`, §5) remains, so a property now has three shapes and the choice is the
    author's:
    - **stored** — `property myValue: Int64 = 0` (§2: the `@property` plus auto-synthesis gives
      the ivar). **The declaration carries the starting value** (decided, 2026-09, §9.16), and a
      **`readonly` stored property must carry one** — `readonly property x: Int32 = 3` — because
      with no setter and no getter nothing else could ever give it a value. That is also the
      answer to whether an initializer's body may assign a `readonly` property: **it may not**
      (§9.25) — the declaration is the only place that value comes from.
    - **computed, named** — `property x: T { get { … } set { … } }`,
    - **computed, shorthand** — `readonly property x: T { … }`.
    - **A `class` declares no `var` or `let`; a `struct`'s state *is* `var`** (decided, 2026-09,
      §5's Struct). A class has no fields to write — its properties manage the variables
      auto-synthesis provides — so the *stored* shape above is a class shape. A struct has **no
      synthesised property at all**: its state is the `var` fields beside it, and its properties
      are the accessor forms (§7.25).
    - **It is a *spelling*, not implicit read-only-ness.** §5's rule stands unchanged — there
      *is* no implicit read-only form — so the shorthand still says `readonly` out loud; what
      it drops is the redundant `get`, the absence of a setter being already stated by
      `readonly`. A bare block on a property that is *not* readonly is therefore an error
      rather than "a getter whose setter is missing", which keeps the two decisions from
      contradicting each other.
    - **The emission is the pair §2 already describes, and it is measured**: a
      `@property (nonatomic, readonly) int32_t foo;` in the header and `- (int32_t)foo { … }`
      in the implementation, with no ivar — a computed property declares no storage.
    - **The block's return type is the property's type** — the same expected-type rule §2 uses
      for `return 0.1;` in a `Float32` getter — so `return 3` in an `Int32` property is an
      `Int32` and nothing has to be written.
    **And the shorthand is the house style — DECIDED (2026-09): the document prefers it**, the way
    it prefers keywords over parentheses. Both spellings stay valid; what changes is which one
    examples use, which is why §1's specimen now carries the shorthand rather than the long form.
55. **A `set` block's argument is implicit — one value of the property's type, called
    `newValue` — DECIDED (2026-09).** The block is written `set { newValue … }` and never
    `set(newValue: T) { … }`: the property already states the type and the name is fixed. It is
    the setter's counterpart to §7.54's getter shorthand — the shape of the block comes from
    the property's declaration rather than being repeated inside the block.
    - **`newValue` is the internal name, and there is no external one.** A block has no
      selector, so §5's external/internal pair has no counterpart here — the same absence
      §7.33 records for a closure's parameters — and the name is what the body sees and what
      the emitted C parameter is called.
    - **The emitted setter is `- (void)setFoo:(int32_t)newValue { … }`** — measured, beside its
      readwrite computed declaration and with no ivar. That implies something worth saying
      about the *accessor selectors*: they are ObjC's property convention (`foo` and `setFoo:`),
      not §7.1's method-name-plus-first-label rule, which is what an ordinary method would have
      produced. `getter=` and `setter=` are how a different pair is asked for (§7.15).
    - **The asymmetry with §7.54 is necessary, not an oversight.** A *readonly* property may
      drop `get` because `readonly` has already said there is no setter. ObjC has no
      `writeonly`, so no marker could make a bare block mean "this is the setter" — which is
      why the getter has a shorthand and the setter does not.
    - **The implicit `newValue` is writable — DECIDED (2026-09), a deliberate exception to
      §7.28.** A setter often normalises what it is given (`newValue = clamp(newValue)`), so the
      emitter writes the parameter **without** the `const` that §7.28's default carries — and
      the measurement is that it matters: `- (void)setFoo:(int32_t)newValue { newValue = … }`
      compiles, while the `const` form fails with *"cannot assign to variable 'newValue' with
      const-qualified type"*. The inherited default would therefore have forbidden the
      normalising setter outright rather than merely documenting it.
    - **What does *not* change: it is still a copy.** §7.28's "a copy, never an out-parameter"
      holds — assigning `newValue` changes the value this setter stores and nothing the caller
      can see — so writability leaks no authority; it only drops a `const` a setter has no
      reason to want.
56. **A bare function is `func`, it is not bound to a type, and it has no implied `self` —
    DECIDED (2026-09).** `func myFunc() -> Void`: Swift's keyword, with the same argument syntax
    as a method (§5) and one removal — labels are checked against the declaration and then
    dropped, because a C function has no selector (§2).
    - **"Not bound to a type" is the declaration half, and it is the whole difference from
      `method`.** The same `name(a: T) -> R` shape appears in two places for two different
      things: inside a class/struct/enum/protocol body it is a method; at the file's top level it
      is a function. Nothing else about the shape changes.
    - **"No implied `self`" is the semantic half, and it has one consequence worth naming.**
      §7.42 resolves an unqualified call through `self` first — and a bare function has no `self`,
      so inside one there is only the last step left: an unqualified name is a global function
      call, full stop. It is also the check that separates the two things, since `self` in a bare
      function is an error rather than a silent no-op.
    - **It emits a plain C function, declared in the generated header just as a class is, and it
      takes the same visibility markers a method does (§7.57)** — `public` by default, with
      `private` emitting a C `static`. "Bare" means *unbound*, not private.
    - **A zero-argument one emits `(void)`, not `()`.** Measured, the reason is *not* a warning —
      `-Wstrict-prototypes` is off in this tree, so clang says nothing about `void f();` — it is
      that `()` in C is an **unprototyped** declaration, which switches off clang's own argument
      checking on the generated code. The same shape as §7.38 and §7.45: the rule has to be the
      language's, because clang will not make it.
    - **A `func` is *not* the spelling of a class method — CORRECTED (2026-09).** An earlier
      version of this item said the language has no class methods and that the prelude reached
      ObjC's `+` methods through a `func`. That was a misreading of §7.25, which forbids
      `class method` on a **value type**; §5 declares it for a `class`, where a `+` method *is*
      written `class method`. A `func` is a different thing — a name at the file's top level — and
      nothing else in this item depended on the error.
57. **Visibility markers: `public` (the default), `private` (this file), and `internal` (this
    project, but not the library's public header) — DECIDED (2026-09).** They prefix an
    **instance or class method** (§5), one at most: `private class method foo() -> Void`.
    - **`public` as the default is ObjC's actual behaviour, not a preference.** An ObjC method
      declared in a header is visible to anyone who imports it, and there is no way to say
      otherwise — so the silent default re-spells what the C already does, which is §0 applied to
      a modifier. **It is a deliberate divergence from Swift**, whose default is `internal`:
      a method meant to stay inside its library has to say so here.
    - **ObjC cannot express any of it — measured, and it is an error rather than a warning.**
      `@private` before a method is *"illegal interface qualifier"*. (ObjC's
      `@public`/`@protected`/`@private`/`@package` are **ivar** qualifiers; a method has never had
      a visibility.) So the rule is wholly the language's to carry.
    - **The mechanism is *where the declaration is written*, and clang then does the enforcing:**
      - `public` — the unit's header, as the library's installed API (§7.9's per-unit leaning).
      - `internal` — the unit's header, absent from the public umbrella header: visible to the
        project, not part of the library's API. That is the definition's whole content.
      - `private` — the `.m` only: a **class extension** (`@interface X ()`) for a method, and a
        plain **`static`** for a bare `func` (measured: accepted silently, and C's own file-scope
        rule is the same rule).
    - **A caller in another file fails to compile — measured, and that is the marker's teeth.**
      *"no visible @interface for 'Foo' declares the selector 'secret'"*. The precision worth
      recording: that is the **error** on a statically-typed receiver, which §4's typing makes the
      ordinary case, while on an `id` receiver it degrades to the warning §7.32 measured (*"may
      not respond to selector"*). Typing is what makes the marker hold.
    - **It does not reach the runtime.** A `private` method still exists and is still reachable
      through `performSelector:`; the marker governs what a *compile* can see, which is exactly
      what "not in the public header" can mean.
    - **A bare `func` takes the same markers — DECIDED (2026-09), confirming what symmetry already
      forced.** `private func`, `internal func`, `public func`; and the C spelling is the reason
      the answer had to be yes — `private` needs a file-scope form and **`static`** is the only one
      C has (measured: accepted silently, and C's own file-scope rule is the same rule).
    - **Properties, initializers and types remain unstated.** The decision named methods and
      functions; nothing here says a property or a type takes a marker, and nothing says it may
      not. Asked when one of them needs it rather than guessed now.
58. **A class method is `class method foo(bar baz: Type) -> Void`, and its *call* was never open
    — CONFIRMED (2026-09).** The declaration is §5's `class method` with §5's parameter pair: the
    external name `bar` builds the selector and the internal `baz` is the body's `const` local
    (§7.1, §7.2). That specimen emits `+ (void)fooBar:(Type)baz`, and a Cocoa `+fooWithBar:` is
    written `foo(withBar bar: Type)` — the labels named after the selector's pieces, which is what
    lets an imported `+` method round-trip.
    - **The call is §6's class-receiver send: `Foo.foo(bar: value)`.** §6's second bullet already
      says the receiver may be a class, and §3's map carries the same row (`[MyClass baz:1]` →
      `MyClass.baz(arg1: 1)`), so no new spelling was needed and §9.24 was asking a question §6 had
      settled before it was asked. The item is kept there as a settled pointer, because the
      mistake is instructive: a class method *looks* like the one thing the call syntax cannot
      express, and it is the one thing §6 already covered.
    - **Both wrong turns are now closed by name.** §7.56's `func` bridge was a misreading of
      §7.25 (which is about *value* types), and §9.24's missing-receiver theory was a misreading of
      §6 (whose first line says the dot is the whole of the spelling). What survives is the plain
      rule: `class method` declares it, `Type.method(label: value)` calls it, and a `class` is the
      only kind of type that has one.
    - **The zero-argument call is `ClassName.classMethod()`, parentheses included —
      re-confirmed (2026-09).** This bullet previously called them optional, leaning on §7.60;
      that rule is withdrawn, because `ClassName.classMethod` without them is indistinguishable
      from a bare name. So a class method has exactly one spelling at the call site.
59. **`nil` is the only visible null value, and the emission converts it — DECIDED (2026-09).**
    One word in the surface; the C gets whatever its context needs. The table is §4's, and three
    of its four rows are *required* rather than stylistic:
    - **A class type → `nil`, a raw pointer → `NULL`.** Either spelling compiles in either
      position (measured), so this row is legibility: the emitted code reads like the ObjC it is.
    - **A collection element → `[NSNull null]`.** An object pointer in an `NSArray`/`NSDictionary`
      slot cannot be null, which is the whole reason `NSNull` exists. This is what makes an
      optional element expressible — and **it is a re-spelling, not the bridge §9.23 feared**: the
      author writes one word, the C gets the singleton, and no semantics is added. The same shape
      as `0o755` emitting `0755`, so §0 is intact.
    - **`Bool` → `false` — and this row is a necessity, measured.** `BOOL b = nil;` is not a
      warning but an **error** (*"incompatible pointer to integer conversion … [-Wint-conversion]"*,
      which clang promotes by default here). The single spelling only works because the emitter
      converts it.
    - **A scalar takes `nil` only through an optional — superseded by §7.62 (2026-09).** This bullet
      used to say that scalars do not take `nil` at all, because nullability was a reference-type
      property. Scalars *are* optional now: `Int32?` exists, `let n: Int32 = nil` is still a
      compile-time error (the `?` is missing), and what the table emits in that context is §7.62's
      pair-struct rather than a pointer.
    - **The conversion is outbound only, and that is worth saying out loud.** The emitter turns a
      written `nil` into a slot's singleton; nothing turns a singleton *back* into `nil`, because
      that would need a runtime test — a semantic rather than a re-spelling. A legacy collection
      read through an untyped API therefore hands back an `NSNull` object, and the typed Argentum
      collections are where the inbound direction is handled: in their own accessors, as ordinary
      library code.
    - **`NSNull` still has to exist for the third row**, and the Foundation is adding it (2026-09).
      §7.31 names it `Null` — a type a declaration may mention and a value an author never writes
      (§4).
    - **`NULL` is not a reserved token — it is an ordinary identifier** (decided, 2026-09). The
      language does not spell its null that way (§4), and it does not forbid the name either: a
      `NULL` that resolves is one the user or an imported header defined, and it means whatever
      that definition says. The lexer has no case for it.
    - **The emitter's own `NULL` needs a header in scope — measured.** With no includes at all,
      `NULL` is *"use of undeclared identifier"*: a macro, not a builtin. So the generated `.m`
      depends on one arriving, and **`<objc/runtime.h>` alone brings in `NULL`, `nil` and `Nil`** —
      a header the prelude includes anyway, so the generated files need nothing extra of their own.
      It is the same footing `nil` itself stands on: all of these are macros the prelude supplies,
      and the *language* is what gives `nil` its reserved meaning.
60. **A message always writes its argument list — WITHDRAWN (2026-09).** This item allowed the
    parentheses to be omitted in two cases; **both are withdrawn.** It is kept as a record because
    the reason is worth having.
    - **What it said.** `receiver.sel()` and `receiver.sel` were declared the same send, and
      `foo { … }` was declared the whole send when a message's only argument is a function type.
    - **Why both go.** A send with no parentheses and a send whose argument is a trailing closure
      are each *syntactically indistinguishable* from their surroundings: a bare name, and a
      statement's block. `foo { … }` cannot be told from `foo` followed by a brace, and
      `for item in items { … }` shows the cost — the collection's expression and the statement's
      block have the same shape. §7.33 settles it: a closure carries its parameter list, so a
      closure begins `(`, never `{`. Once that is true, dropping the message's own list buys
      nothing and costs the parser a real ambiguity.
    - **What stands.** Argument labels are still always written (§7.2); §7.33's trailing closure is
      still `foo (bar: Int32) { … }`, the closure's list *being* the call's parentheses; and
      `ClassName.classMethod()` is the spelling for a class method (§7.58).
    - **And the part of the last bullet that survives.** A block's parameters are named by its list
      or not at all — `(bar)` and `(bar: Int32)` are the two spellings and there is no third. That
      was about the *block's* list rather than the *message's*, so the withdrawal does not touch it.
    - **The emission is unchanged either way.** Both spellings emitted the same message send, so
      nothing about the output moves; this is a surface rule that was buying a saving the grammar
      could not afford.

61. **`CArray<T>` and `MutableCArray<T>` — SUPERSEDED (2026-09) and *deleted*; see §7.63.** This item
    defined the language's type for a C array, and there is no such type any more: `Array<Int32>`
    **is** `int const *` and `Array<Object>` **is** `NSArray<Object>` (§7.63), so the name resolves
    to the C type or to the ObjC type rather than introducing one. Everything this item decided about
    *behaviour* was about C itself and carries over unchanged — the extent is not part of the type
    (`int x[10]` and `int y[15]` are the same type), indexing is unchecked, nothing resizes. What
    this item called the declaration's size is §7.64's `[N]`: a sized declaration allocates real
    storage and `let`/`var` supplies element writability, so only *allocation* remains with
    `UnsafeMutablePointer<T>` (§7.29). Its "still to settle" question is closed — the size is written
    where C writes it, after the name.

62. **`?` extends to scalars — DECIDED (2026-09): a scalar or C struct may be optional, with a
    synthesised pair-struct as its representation.** `Int32?`, `Bool?`, `Float64?` and `Range?` are
    types, spelled exactly as the object form is, and **the surface gains nothing new**: §7.10's
    four ways out — `if let`, `guard let`, `!`, `??` — apply unchanged, because they are defined
    against `T?` and not against a representation.
    - **What is emitted is a per-type struct**, `{ T value; BOOL hasValue; }`, one for each scalar
      and each imported C struct the program actually uses. Nothing generic is involved, which is
      what makes it expressible at all: a generic enum is blocked by §7.26 (a type argument must be
      an object type) *and* by §7.35 (an associated value cannot be a class type) — two independent
      walls, so the enum spelling of `Optional` is not available even in principle.
    - **`nil`'s conversion table (§7.59) gains a row**: in a scalar-optional context it emits that
      struct's zeroed form. One word in the source and the representation the context needs — the
      pattern the table already establishes, and the reason no new syntax is required.
    - **The emitter's new rules are the pointer case's, unchanged in shape**: `if let` compiles to a
      `hasValue` test, `x == nil` to `!hasValue`, and `??` to a select.
    - **It costs what a real absence costs.** `Int32?` is **not** an `int32_t` — it is a struct, so
      it is not accepted where the scalar is — and a `Bool?` is two bytes rather than one. A
      *sentinel* was rejected as the alternative: indistinguishable from a real value, and exactly
      the silent-wrong-answer class the language refuses everywhere else.
    - **`Bool?` is three-state** — true, false, absent — and §7.20 already keeps that honest: a
      condition is a `Bool`, so a `Bool?` cannot be used as one without unwrapping.
    - **Interop sentinels stay library business.** A C function signalling `NSNotFound` is wrapped by
      a `func` returning `Int32?`, which is the division §7.59 gives the inbound `NSNull`: the typed
      layer absorbs it and the language stays out of it.

63. **Generics: erase where the runtime can hold the argument, instantiate where it cannot —
    DECIDED (2026-09).** The rule is about the *type argument*, decided **per instantiation and not
    per declaration**: an argument the runtime has a representation for — an object, which is `id`
    — uses **ObjC lightweight generics**, one erased class for the whole program; anything else (a
    scalar, struct or enum, which the runtime cannot hold) is **monomorphised** at compile time. So
    `Box<String>` is erased and `Box<Int32>` is generated from the *same* declaration.
    - **§7.62 is the precedent, not a special case.** A scalar optional was decided as a synthesised
      pair-struct per type used — instantiation, for a built-in. This generalises it to user types
      rather than introducing a second mechanism.
    - **`Array<T>` is not a type of its own — it is two spellings that already exist** (decided
      2026-09; this supersedes §7.61's `CArray` and `MutableCArray`, which are **deleted**):
      `Array<Int32>` **is a C pointer**, `int const *`, and `Array<Object>` **is** `NSArray<Object>`.
      Nothing is introduced — the name resolves to the C type or to the ObjC type, chosen by the
      argument — so §0 is satisfied by an *alias* rather than by a construct, which is the strongest
      form this feature could have taken.
    - **Ownership and length belong to C, because a pointer carries neither.** A scalar `Array<T>` is
      the *view* form — what a C function takes and returns — not a container: it cannot be built,
      cannot grow, and cannot be iterated, since there is no count to iterate against. Code needing
      storage or a length uses `UnsafeMutablePointer<T>` (§7.29) and C's own arithmetic, and its
      loop is a C loop. Element writability lands there too, which is the job `MutableCArray` used
      to name.
    - **An object `Array<T>` is exactly `NSArray<T>`, erasure and all** — which is what lets it be
      handed to an ObjC method declaring `NSArray`, and what makes `for`-in and element absence work
      through §7.59's `NSNull`. The two forms differ in every way an author can observe, because the
      *type argument announces the world*; that is what lets one name pass §7.4's test where
      `extension` could not.
    - **Total monomorphisation was refused**, and the reasons are structural. A generated *class*
      must be defined exactly once in a program, but the emitter compiles one unit at a time: emit
      it per consumer and the symbols duplicate; emit it in the author's unit and that unit cannot
      know the consumer's arguments — the only escape is whole-program compilation, which the
      `.h`/`.m` + system-clang model does not have. And monomorphising the *classes* would make
      `Array<String>` stop being `NSArray`, breaking §7.31's guarantee and requiring a bridge.
    - **Costs recorded**: a scalar `Array<T>` is a *view*, so it carries no length — it cannot be
      iterated, grown or built — and a program wanting storage or a count falls back to
      `UnsafeMutablePointer<T>` (§7.29) and C arithmetic. The name says "array" while the type is a
      pointer; the argument tells an author which world they are in, but not that there is no length,
      so the name is the place to revisit if that proves misleading.
    - **The price is front-end work**: monomorphisation is a real commitment for `sterlingc`, which
      has no front end yet.

64. **A sized `Array<T>` declaration — DECIDED (2026-09): the declaration allocates, `let`/`var`
    decides element writability, and a brace list initialises.** `var myArray[10]: Array<Int32>`
    emits `int32_t myArray[10]`; `let myArray[15]: Array<Int64>({1, 2, …})` emits
    `int64_t const myArray[15] = {1, 2, …}`.
    - **It brings back what §7.61 called "the declaration carries the size"** — the one thing a
      pointer cannot do — so deleting `CArray` is now complete rather than lossy.
    - **`Array<T>` reads two ways, and the position decides.** As a *parameter* it is §7.63's view,
      `int const *`. In a declaration with `[N]` it is real in-place storage: the elements, not a
      pointer to them. With neither, it is the pointer spelling §7.29 already provides.
    - **`let`/`var` carries element writability**, which is exactly §7.61's `T x[N]` versus
      `const T x[N]` — so deleting `MutableCArray` cost nothing, since the language said it already.
    - **The `[N]` may be omitted when a brace list follows**, by C's own rule that the count comes
      from the list. A list shorter than the size zero-fills the remainder and a longer one is an
      error, both as C defines them. `{…}` is free syntax: §6 has no brace-list expression, unlike
      `[…]`, which is indexing.
    - **The brackets take more than one dimension — DECIDED (2026-09).** `var m[3][4]: Array<Int32>`
      emits `int32_t m[3][4]`, and `m[1][2]` emits `m[1][2]`: indexing is C's own and nothing is
      rewritten. Note the element type stays `Array<Int32>` — the *rank lives in the brackets*, exactly
      as C puts it.
    - **That is a different thing from `Array<Array<Int32>>`, which is also legal.** The bracketed form
      is contiguous storage; the nested form is `int const * const *`, a pointer to pointers. C has
      both, they are not interchangeable, and it is the distinction C programmers already trip over.
    - **One gap this leaves, worth recording.** C decays a two-dimensional `m` to `int (*)[4]` — a
      pointer to an array — and neither `Array<T>` nor `UnsafeMutablePointer<T>` spells that type, so a
      C function taking `int (*)[4]` cannot be called as things stand. Passing the first row is the
      workaround until a spelling exists.
    - **With an initialiser, follow C.** Only the first `[N]` may be omitted, when the count comes from
      the list: `var m[][4]: Array<Int32> = ({{1,2,3,4}, {5,6,7,8}})` is legal, and omitting any later
      one is an error. Zero-initialisation is the rule above, applied per dimension.
    - **This is a declaration form, not a constructor call.** §7.38's `T(x)` is a call on a type, and
      `Array<Int64>` is an alias with no type behind it — so the brace list belongs to the
      declaration, while the emission is C's aggregate initialiser either way.
    - **A bare `[N]` with no initialiser is implicitly initialised to all-zero — DECIDED (2026-09).**
      This is not a new rule but the *same* one taken to its limit: a shorter initialiser list already
      zero-fills the remainder, and an absent list is the shortest list of all. The emission is C's
      `{0}`, and it lands *with* the language's grain rather than against it — §4 and §7.11 want
      definite initialization, and this defines what C left undefined. Zero is safe for every element
      type §7.63 admits precisely *because* class types are excluded: a zeroed plain C pointer is
      `NULL`, and a zeroed §7.62 pair-struct is `.none`, so a fresh optional array is all-`nil`.
      Zeroing does work a large array would pay for, and the escape hatch is deliberate —
      `UnsafeMutablePointer.allocate` (§7.29) still means "storage, and I will initialise it".
    - **`Array<Int64?>` follows from §7.62** — an array of pair-structs — and unlike the pointer form
      it has an extent, because the declaration carries one.

65. **Range patterns in `case` — DECIDED (2026-09): `case 1...45 {}` matches a scalar subject
    inclusively.** This is the first thing to give §7.24's `switch` a pattern beyond a single value.
    - **It is a *pattern*, not a value — DECIDED (2026-09), and there is no range type.** A range
      exists only in a `case`, because C's case range is the only range construct there is. A range
      *value* — one that could be stored, passed, or iterated by `for i in 1..<count` — would be a new
      construct with nothing in C to re-spell, which §0 does not admit. So `for` over a range does not
      exist, and neither does a `Range` in the Swift sense: the imported C struct (§9) is a plain pair
      of numbers — a location and a length — and has nothing to do with patterns.
    - **Two spellings, both inclusive at the bottom** (decided 2026-09): `1...45` is every value from 1
      to 45 inclusive, and `1..<10` is every value from 1 to 9 — the upper bound excluded. Both are
      legal in a `case`, and `..<` is the form a loop counter wants.
    - **`..<` lowers by subtracting one, because C's case range is inclusive only**: `case 1..<10`
      emits `case 1 ... 9`. That makes an empty case reachable — `0..<0`, or any range whose low bound
      exceeds its high — so the emission must produce a case that matches nothing rather than one
      clang rejects. It is a detail of the emitter and not of the surface.
    - **The subject must be a scalar.** §7.24 lets a `switch` subject be any type, so the check is
      per-case: a range case requires an orderable scalar, and a class subject with a range case is a
      compile error. Strings are not orderable here, so `case "a"..."z"` does not exist.
    - **Bounds must be constant, because the emission is C's case range.** Clang accepts
      `case 1 ... 45:` (warning `-Wgnu-case-range`), which is exactly the construct and costs one
      line; the alternative is lowering the whole `switch` to an if-chain, which is portable but stops
      being a `switch`. A *non-constant* bound, which Swift allows, cannot be a C case label at all —
      if that is wanted it forces the lowering and has to be decided separately.
    - **Exhaustiveness and `default` are unchanged** (§7.24): a range is an additional pattern, and a
      `switch` that does not cover everything still needs its `default`.
    - **What this leaves:** patterns are now single values, ranges, and §7.35's union payloads. There
      is still no *conditional* pattern — no `where` clause — which is the last gap between this and
      a modern `switch`.

66. **The only `for` construct is `for [var|let] name in collection [where condition] {}` — DECIDED
    (2026-09); the `where` clause was added later by §7.73.** There is no C-style three-clause `for`; a
    counting loop is written with `while`.
    - **The binding carries `let` or `var`** — and it is a per-iteration *binding*, not a capture
      (§9.4's `__block` is a different thing). `let` makes it read-only, `var` makes it assignable.
      Swift removed `for var`; this language keeps it, because the emission is ObjC's fast
      enumeration, whose loop variable is assignable anyway.
    - **`var` rebinds a copy, so it never writes back into the collection.** An object element is a
      reference (§7.31), so `var` there rebinds the reference; a struct or scalar element is a value
      (§4), so `var` shadows a copy. Neither alters what the collection holds.
    - **A collection is anything enumerable** — in emission terms, ObjC fast enumeration over an
      `NSArray` or anything conforming to `NSFastEnumeration`. That is exactly what excludes a scalar
      `Array<T>`: §7.64's pointer has no count and nothing to enumerate, so `for`-in over one is a
      compile error and a loop over it is a C loop.

67. **`if` is `if [boolean expression] { } else if [boolean expression] { } else { }` — DECIDED
    (2026-09).** Braces are mandatory, the parentheses are not, and `else if` is written with two
    words — which is what C requires and what the emission is, minus the parentheses.
    - **The condition is a `Bool`** (§7.20), so there is no truthiness and no implicit comparison: the
      emitter's `if (expr)` is exactly what the surface said.
    - **There is no brace-less body.** `if x return` is a compile error, as is an `else` followed by a
      bare statement. That is a *restriction* rather than an addition — the same shape as §7.24's
      no-fallthrough — because it removes a spelling without giving control anywhere to go.
    - **`if` is a statement, not an expression.** C has no `if` expression, so neither does this, and a
      conditional *value* stays `?:` (§7.20). Swift's value-returning `if` would be an addition.
    - **The binding forms are unaffected.** §7.10's `if let` / `if var` and its comma list remain part
      of `if`, and they chain into `else if` like any other condition. So `if` has a boolean form, a
      binding form and a binding chain — and this item fixes the first.

68. **`guard`'s condition may be a plain `Bool` — DECIDED (2026-09).** `guard a == b else { }` runs the
    braced scope when the condition fails and returns from the outer context, exactly as the binding
    forms already do (§6, §7.10).
    - **The list mixes forms**: `guard let x = maybe, x > 0 else { }` is one condition list, because it
      is the same list `if` takes (§7.67) and §6 already carries it on `guard`.
    - **Everything else about `guard` was decided earlier and is deliberately not restated.** The
      `else` is mandatory, its block must `return` — explicitly, on every path (§6, narrowed
      2026-09) — and a `guard` binding is visible after the guard, unlike `if let`'s. This item exists
      only to record that the *condition itself* need not be a binding.

69. **`while [boolean expression] { }`, and there is no `do while` — DECIDED (2026-09).** The condition
    is a `Bool` (§7.20), braces are mandatory and parentheses are not — the same form §7.67 gives `if`.
    - **`do` does not exist as a keyword.** C's `do { … } while (…)` is not re-spelled, and the
      removal is justified by another decision: `do…while` exists in C so that a multi-statement macro
      can be used as a single statement, and there is no preprocessor here (§7.9).
    - **A loop that must run its body at least once needs nothing new**: `while true { … ; if !done {
      break } }` — `true` is a `Bool`, and §6's `break` leaves the loop. What is given up is a spelling
      rather than a capability, the same shape as §7.24's no-fallthrough.

70. **`with [struct|instance] { }` puts the target's members in scope — DECIDED (2026-09).** Inside the
    block a member name means the target's member, as a plain variable, and assigning to it writes the
    member: `with p { x = 5 }` emits `p.x = 5`.
    - **It is admitted because it is *only* a rewrite.** The target's type must be statically known, so
      its member list is known at compile time and the emitter resolves every in-scope name
      syntactically — the same property that lets §7.65 lower a range pattern to a case label. No
      runtime lookup, no scope object, no dynamic dispatch: the block is C's own `{ }`.
    - **The target must be a declared type**, a struct or a class. An `id` or `AnyObject` target has no
      member list to rewrite against, so it is a compile error.
    - **Only members and properties enter scope — not methods** (§6's message send is unaffected), and a
      local declared inside the block *shadows* a member of the same name. Nested `with` blocks resolve
      innermost first, exactly as ordinary scoping does.
    - **Writing through a name writes the target**, which is what makes the form worth having for a
      struct: `with p { x = 5 }` is `p.x = 5`, and for a class instance the same rewrite emits the
      setter message. Reading an object-typed member is §7.31's reference, as always.

71. **`defer { }` runs at scope exit, in reverse order, on every path out — DECIDED (2026-09).**
    Swift's semantics exactly: several `defer`s in one scope run last-registered-first, and they run
    whether the scope exits by `return`, by `break` or `continue`, or by falling off its end.
    - **A `defer` belongs to its *block*, and that is what makes the lowering static.** Nested blocks
      mean nested ownership: a `defer` in a loop body runs at the end of *each iteration*, and one
      inside an `if` block runs when *that* block exits rather than the function's. So there is never a
      question of whether a defer was "registered" — the block whose exits must run it is known at
      compile time, and no runtime flag or list exists.
    - **The block rule settles what looks like a special case and is not: a `defer` inside another
      `defer`'s block runs immediately.** Its own block *is* the deferred body, which exits the moment
      that defer finishes, so the inner call fires on the spot. That follows from the block rule rather
      than needing a rule of its own — which is the sign the rule is the right one.
    - **And the same rule fixes what the emission costs.** An exit inside nested blocks carries the
      deferred list of *every* scope enclosing it, so a deeply nested body with many exits duplicates a
      growing list at each one. That is the price of static resolution and readable output, and it is
      worth knowing before writing a deep nest with many returns.
    - **The emission duplicates the calls at each exit path**, innermost scope first, instead of
      introducing a `goto` to a single exit label. That costs code size where a scope has several exits
      and buys the one thing this document keeps asking of the emitter: output that still reads as
      hand-written C.
    - **`return` computes its value first, then the defers run.** The emitter stores the result in a
      temporary, runs the scope's deferred blocks, and returns the temporary — so a `defer` cannot
      change what a `return` already produced. That is Swift's rule and it is visible: for a
      class-typed value the object is shared and its state *is* affected, while a struct or scalar
      result is already fixed.
    - **`return` is an error inside a `defer`.** The construct describes a scope being exited, so it has
      no result of its own to produce; `break` and `continue` stay legal only where they target a loop
      that encloses the `defer`'s own scope.
    - **Errors are not an exit path here.** §7.6's `throws` is an out-parameter convention — the
      selector gains `…error:` and the caller reads the `NSError` — not an unwinding mechanism, so
      there is nothing beyond the ordinary returns to run defers on.

72. **Custom operators may be defined — DECIDED (2026-09).** `operator @ (lhs: Int, rhs: Int) -> Point`
    declares `@` for that pair of operand types, and `a @ b` is a call to it.
    - **It emits a free function**, not a method: `a @ b` becomes a plain C call to a function named by
      mangling the operator and its operand types. That is §7.27's rule applied to a symbol — two
      declarations of `@` over different operand types are two functions distinguished by name — and it
      is also what lets the emitted C parenthesise every custom application freely.
    - **Precedence follows the symbol — DECIDED (2026-09), and it is purely lexical.** An operator that
      already exists takes **its existing precedence**: `Point + Point` binds exactly as `+` binds,
      whatever the operand types, because the *symbol* decides and not the type. Any symbol that is not
      an existing operator takes the **lowest** precedence — looser than `?:` and tighter than `=`, so
      `x = a .:. b` parses as `x = (a .:. b)`. Nothing depends on declaration order, and two
      declarations of one symbol share one level.
    - **The rule is a parser rule only.** The emitted C parenthesises every custom application, so a
      mistake here changes how an expression *parses*, never what the runtime does.
    - **Arity and side come from the parameter names — DECIDED (2026-09).** An operator takes **one or
      two** arguments, and `lhs` / `rhs` say where the operand sits rather than being decorative:
      - **`rhs: T` alone** is a *prefix* operator, matching `-x` — the operand is on the right, as in
        `operator -(rhs: Foo) -> Foo`.
      - **`lhs: T` alone** is a *postfix* operator, matching `x++` — the operand is on the left, as in
        `operator ++(lhs: Bar) -> Bar`.
      - **`lhs:rhs:`** is binary, which is the original example.
      No `prefix`/`postfix` keyword is needed: the name *is* the syntax, and one symbol may therefore
      carry all three forms at once, since arity and side are part of the mangled name.
    - **A custom unary operator's precedence — DECIDED (2026-09).** The symbol rule above settles binary
      operators, but its "lowest" is a *binary* level and means nothing for a unary form. A new prefix
      operator takes the level of C's prefix operators (`!`, `~`), and a new postfix operator the tighter
      level of C's postfix forms.
    - **Why those two defaults differ, since it could look arbitrary.** A *new binary* operator gets the
      loosest level so it cannot silently capture precedence from the operators around it. A *new unary*
      one has to be *tight* for the opposite reason: any level looser than `*` would make `-a * b` parse
      as `-(a * b)`, which is never what the author meant. C already gives one symbol two levels this
      way — `++x` and `x++` do not bind alike — so a new symbol used both ways takes its prefix level in
      front and its postfix level behind, exactly as C's operators do.
    - So `-a .:. b` cannot parse two ways, and the rule stays a parser rule only: the emitted C
      parenthesises every custom application.
    - **`[]` is an operator — DECIDED (2026-09), and it is the one exception to the set below.** It is
      written `a[i]`, and it is a special case in one respect: **it is declared with one argument, not
      two, and it must be declared inside the type whose elements are being reached** —
      `operator [](i: Int32) -> Foo`. The container is `self`, exactly as in C++, so there is no
      left/right question and the parameter name is the author's (`i` above), unlike `lhs` / `rhs`. It
      takes no prefix or postfix form: `a[]` means nothing.
      - **It is a *delimiting* operator, so the lexer never munches it.** In a *declaration*, `[]` is
        the operator; everywhere else `[` and `]` are indexing and stay punctuation. There is no
        ambiguity to resolve because the context is the declaration, not the run of characters.
      - **The redefinition rule applies unchanged, and it is what makes this safe.** `[]` already works
        for arrays and pointers (§7.64), so it can only be declared for a type that has *not* got it —
        a class or a struct. An existing subscript is never displaced.
      - **Because it is a member, its emission is a method rather than a free function** — the one custom
        operator that is not a plain C call, and that exception follows from `self` being the container.
        ObjC already has the selector for it, `objectAtIndexedSubscript:`, so that is the natural
        emission in place of a mangled name — and it means `a[i]` reaches an ObjC class carrying no
        Sterling declaration at all.
      - **What the body outputs is what `a[i]` is**, per the return type written on the declaration.
      - **Writing through a subscript is a *second* operator, `[]=` — DECIDED (2026-09).** `a[x] = y` is
        the `[]=` declaration, not an assignment to whatever `[]` returned. The two are independent, so a
        type may have a read-only subscript, a write-only one, or both, and `[]=` is likewise only
        declarable where the type has not already got it. It takes the index and the value, and it is a
        member like `[]`, so `self` is the container once more.
      - **Its emission is ObjC's other subscript selector**, `setObject:atIndexedSubscript:`, the pair to
        `objectAtIndexedSubscript:` — and the same lowering clang applies to a C object subscript. The
        declaration returns `Void`, yet `a[x] = y` still has a value: §7.21 makes assignment an
        expression, and that value is the assigned `y`.
      - **The parameter names follow the *value*, not the sides.** `[]`'s index was `i` rather than
        `rhs`, and `[]=`'s parameters are named by the author the same way — the `lhs` / `rhs`
        convention belongs to the infix forms, where a side is genuinely ambiguous.
    - **No new symbols — AMENDED (2026-09, superseding the arbitrary-set rule).** An author may define an
      operator **the language already has** for a type that does not yet support it — unary `-` for a
      `Point`, say — and **may not invent one**. `::~` is not an operator and cannot be made one.
      The definable set is closed, and it is the one §7.22's precedence table already names:
      - **Arithmetic** `+ - * / %`
      - **Comparison** `< <= > >= == !=`
      - **Logical** `! && ||`
      - **Bitwise** `~ & | ^ << >>`
      - **Assignment and coalescing** `= ??`
      - **The subscript pair** `[]` and `[]=`, the member-only exception described above.
      Nothing outside that list is definable. `(` and `)` are not in it, so `()` can never be an
      operator, and neither can `()=`. There are no one-to-three character runs to munch, because there
      is no longer a character set to draw them from.
    - **What this buys, and why the earlier rule was wrong.** §7.72 previously allowed any one-to-three
      character sequence drawn from `! @ # $ % ^ & * - = + : < > ? / \ .`. The consequence was ambiguity
      no scanner could settle: with `>`, `:` and `=` all being symbol characters, **`>:` lexed as one
      token**, so in `class Box<T>: Object` the type argument's closing bracket took the superclass colon
      with it. The same shape gave `?>` inside `Array<Int32?>`. Both readings were legal under the old
      rule, so neither was a bug in the parser — the rule was wrong. With the set closed, neither token
      can form and both spellings have exactly one reading.
    - **An operator may not be redefined where a type already has it.** `+` can be defined for a type
      that has no `+`, and cannot replace one for a type that does — so `Int + Int` is untouchable while
      `Point + Point` is fine. The rule is about *operators on types*, not about symbols, which is why
      `-` may still mean subtraction for `Int` while meaning something new elsewhere.
    - **Precedence follows the symbol, from §7.22's table.** The earlier clause giving a brand-new symbol
      the loosest level is gone with the symbols that needed it, and its disappearance removes a real
      hazard: at the loosest level a custom operator could reach across a line break for an operand.
    - **The mangled C name has to encode the symbol.** `<<`, `>=` and `[]` are not identifier
      characters, so the emitter maps each symbol to a name rather than embedding it: the function for
      `[]` over `(Int, Int)` is a valid C identifier, not something the compiler has to be taught about.
    - **It contradicted two items, and both were amended the same day (2026-09).** §8 now carries this
      as its one declared exception, and §7.27's head records that overloading *by name* is no longer
      the only route — while everything §7.27 says about selectors and their names still holds.

73. **A `where` clause on `case` and on `for` — DECIDED (2026-09).** It attaches a condition to a
    pattern or an iteration, and it is a rewrite in both places rather than a new semantic: §8 gains no
    exception for it.
    - **On `case`, the condition is evaluated *after* the pattern matches**, so a payload is bound before
      it runs:
      ```
      case .ok(let code) where code >= 200 && code < 300 { handleSuccess(code) }
      case .ok(let code) where code >= 500              { handleServerError(code) }
      case .ok(let code)                                { handleOther(code) }
      ```
    - **A failing `where` skips the *case*, not the `switch`** — the next alternative is tried. That is
      what makes it more than sugar: an `else` cannot fall through to a later case without duplicating
      it, so several cases sharing one pattern under different conditions genuinely need the clause.
    - **A `where`-guarded case does not count toward exhaustiveness** (§7.24). Being conditional, a
      `switch` whose last alternative is guarded still needs its `default`.
    - **It forces the if-chain lowering.** §7.65's case-range emission cannot carry a condition, because
      a C `case` label is a constant, so a `switch` containing a `where` lowers as an if-chain instead.
    - **On `for`, the condition is evaluated per element, before the body**:
      `for order in orders where order.total > 100 { ship(order) }` lowers to one added
      `if (!(cond)) continue;` inside the loop, and §7.66's signature gains the optional clause.

74. **Default argument values — DECIDED (2026-09).** A parameter may carry `= expression`, and a call may
    omit a trailing run of them: `method add(item which: Int32, scale: Float32 = 1.0) -> Bool` is
    callable as `add(item: 3)` or as `add(item: 3, scale: 2.0)`.
    - **The emission is ordinary selector siblings**, which is why this is a re-spelling rather than a
      new semantic. A method with a defaulted tail gains one extra method per omitted suffix —
      `addItem:` and `addItem:scale:` both exist — each produced by §7.1's selector rule with the
      omitted parameters filled from the default expressions. That is precisely the ObjC convention
      (`-init` beside `-initWithFrame:`), so the short form is *`@selector`-able* and callable from ObjC
      like any other method, and §7.27's "overloading is by name" already describes the result.
    - **Defaults fill from the right, so a parameter without one may not follow one that has one.** Two
      defaulted parameters give three selectors, not four: the omitted run is a *suffix*, never a hole in
      the middle. C++ and Swift use the same rule, and it is what keeps the sibling count and the
      generated selector names mechanical.
    - **A default behaves as if the caller had written it**, so its expression is evaluated per call —
      `= Date()` yields a fresh value each time rather than one shared at the declaration. That is the
      observable semantics; the emission simply places the expression in the sibling's body.
    - **A generated sibling may not collide with a declared method.** If `addItem:` is also written by
      hand as well as derived from a default, that is an error rather than a silent override — §7.27's
      duplicate-selector rule applied to a selector the author did not literally write.
    - **Functions take them too** (§7.56), where the siblings are plain C functions sharing the full
      form's name — the same rule, since a `func` is not bound to a type.

75. **A semicolon separates statements that share a line; it does not terminate one — DECIDED
    (2026-09).** A statement ends at the end of its line, or at the `}` closing the block. `;` is
    required only when a second statement follows on the same line, and a trailing `;` is always
    allowed because it separates from nothing.
    - **The lexer already carries what this needs.** Every token records its line, so the rule is a
      comparison: after a statement, if the next token is on the same line a `;` must separate them, and
      if it is on a later line none is required. No new token, and no line-sensitivity in the lexer.
    - **It matches the specimen** (§1), which is the authority: `property myValue: Int64` ends at its
      line with no `;`, while `return 0.1;` inside a body carries one — harmlessly, since a `;` before a
      newline separates nothing.
    - **The emission always writes the terminator.** C requires it, so every emitted statement gets its
      `;`; the rule above is a surface convention with no counterpart in the output.
    - **A consequence worth stating**: two statements sharing a line with no separator between them is
      an error rather than a silent splice — the same class of rule as §7.24's no-fallthrough, a
      restriction that removes an ambiguity rather than adding a spelling.

## 8. Out of scope (v0)

**No new semantics, with one declared exception: §7.72 lets an author define an operator the language
already has for a type that does not support it.**
Everything else follows — no computed
inheritance, no macros — because there is no preprocessor (§7.9), which is a *reason*
rather than a withheld feature — and no reflection beyond what the ObjC runtime already
exposes. No signals or notifications *as language features* — `Notification`
and blocks are callable, which is the whole of what is needed. **No protocol
conformance on a struct** — or on a tagged-union enum, which is one (§5): it
needs a dispatch table, which is a mechanism rather than a re-spelling, the same
line that makes struct inheritance *layout only*. No FFI generator: C and ObjC
declarations are imported from headers (the plan's open item).

## 9. Open questions

1. **Confirm §7.1** (selector composition) — **CONFIRMED in both its cases (2026-09).** §7.1 is
   DECIDED, and §7.27 and §7.50 have since been built on it, so the confirmation this item
   asked for arrived with the decisions that followed rather than as an answer of its own. The
   confirmation covers both positions the rule speaks to — the *first* piece, which is the
   method name with the first parameter's external name attached, and the *later* pieces, each
   a selector piece of its own — which is what settles §6's "Swift-style alternative" for a
   later label: the default stands.
2. **Is `callSomeFunc(arg: arg1)` a C function or a method on `self`? — DECIDED
   (2026-09, §7.42): both, resolved in that order.** An unqualified call in a method
   body is a **message send** when the name resolves to a method — this class's or an
   inherited one — and falls back to a **global C function** otherwise. The specimen is
   the second case, `MyClass` having no such method, so it emits the plain
   `callSomeFunc(arg1);` §2 shows.
3. **Where does `AnyObject`/`id` stop? — DECIDED (2026-09, §7.43): nowhere.** The
   type is authorable — a local, a property, a parameter, `Array<AnyObject>` — and
   **arbitrary message sends through it are valid**, under the rule that what
   Objective-C accepts this language accepts. So the dynamic layer is *in* the
   language: `respondsToSelector:`, `performSelector:`, KVC and any other selector are
   ordinary sends, at the cost §7.43 names (a send on `AnyObject` cannot be checked
   against a declaration).
   The gap this item used to describe — **no cast, no `as?`, no type test anywhere** —
   is now closed by decision: a cast is valid ObjC (`isKindOfClass:` plus a C cast), so
   one must be valid here, or an authorable `Array<AnyObject>` would be readable and
   unusable. §7.44 settles the pair — **`x as? T` yields `T?`**, nil when the conversion
   is not possible, with `T(x)` (§7.38's `Type(value)`) as the trapping form.
4. **Blocks and ARC capture — DECIDED (2026-09) in every part it raised (§7.51, §7.52, §7.53).**
   The capture semantics are ARC's, as the
   exploration below establishes; the spellings it found missing are settled — `self` is
   captured **strongly** by default, which is ARC's own rule, while a closure may name
   exceptions in a **capture list** (`[weak self, someVar]`, §7.51); a weak *variable*
   (`weak let` / `weak var`, §7.52) remains for a named weak reference. **The mutable capture is
   settled too — `var` in the capture list** (decided, 2026-09, the third qualifier §7.51 lists).
   What follows is the reasoning that produced the decisions, kept because the measurements are
   the useful part.
   **The exploration.** `{ … }` emits an ordinary
   block literal and ARC owns what it captures, so the item's premise holds — and it holds
   at the ABI level rather than by assertion. Measured, compiling a strong capture, the
   conventional weak-self idiom and a `__block` accumulator to an object leaves exactly
   these undefined symbols: `_NSConcreteStackBlock`, `_Block_object_assign`,
   `_Block_object_dispose`, `objc_retain`, `objc_release`, and the `objc_initWeak` /
   `objc_copyWeak` / `objc_destroyWeak` / `objc_loadWeakRetained` family. Every one of them
   comes from the runtime the plan already ships (libobjc2; `-fblocks` is already in the
   toolchain wrapper). So the language defines no capture semantics at all — and should not.
   **What it cannot do is *say* the two things those symbols exist for.**
   - **A weak local.** ObjC's only way to break a retain cycle is a weak *variable declared
     before the block* (`__weak Thing *w = t;`) — there is no per-capture marker — and the
     emitted weak calls above are that variable's. Sterling's `let`/`var` carried no ownership
     qualifier (§5's Local), so the standard weak-self idiom was **inexpressible** — which is
     the gap §7.52 closed, with `weak let` / `weak var` rather than the parenthesis this
     bullet first guessed at.
   - **A mutable capture.** A `__block` variable is shared with the block rather than copied,
     and without it ObjC *rejects* an assignment to a captured local (*"variable is not
     assignable (missing __block type specifier)"*) — so an accumulator inside a closure is
     inexpressible today. The interesting candidate needs no new keyword: the language's own
     `var` is already the mutability word, so mapping `var` → `__block` is a re-spelling rather
     than an addition — at the cost of being *more* permissive than ObjC, which forbids the plain
     assignment. **DECIDED (2026-09): a `var` entry in a capture list maps to `__block`.** So
     `[var count]` shares `count` with the closure — which is what an accumulator needs — and a
     second mutability word for one case would have been the worse cost.
     - **And under ARC a `var` capture of an *object* is a strong capture — measured, because the
       folklore is stale here.** Compiling `__block Thing *shared` both ways: with `-fobjc-arc` the
       object carries `objc_retain` and `objc_storeStrong`; with `-fno-objc-arc` neither appears,
       leaving only `_Block_object_assign` / `_Block_object_dispose`. So the pre-ARC trick —
       "*`__block` does not retain*, use it to break a cycle" — **is false on this tree**. For a
       scalar, `var` is exactly mutation; for an object it is a strong capture like any other, and
       `[weak …]` remains the way to break a cycle (§7.51).
   **And the hazard is inherited rather than chosen, so it is worth writing down.** A
   closure capturing `self` **retains it** — that is the `objc_retain` in the measured
   object — which is ObjC's most common memory bug arriving with the semantics. The fix is
   the weak local above, which is what makes it a *correctness* spelling rather than a
   convenience.
5. **Unannotated imports — the boundary hole. DECIDED (2026-09): an unannotated declaration
   is read as *nullable* — option (c).** An imported method's return is therefore `T?` and its
   parameters accept `T?`; the compiler never asserts what it has not been told, and the cost
   is a visible `!` or a binding rather than a silent wrong answer. Option (b) — assume
   non-null — was rejected on the measurements below: clang assumes nothing, warns about
   nothing, and a method returning nil would flow into a non-optional as a silent no-op.
   **What it buys, precisely:** the *return* side is sound, so a nil can no longer arrive
   typed as non-null. The *argument* side is permissive by construction — a nullable value
   passed to an unspecified parameter is accepted, and clang is silent about it (measured:
   `-Wall -Wnullability-completeness`, a region-using caller calling an unannotated header,
   exit 0). So this is a rule about what the language *claims*, not a fence around calls.
   **And it makes (a) a quality task rather than a prerequisite:** annotating the Foundation —
   434 declarations over 19 headers — removes the `!`s and changes nothing else, which is what
   now tracks in `docs/design/foundation-plan.md` §5.
   The investigation, kept because the measurements are the useful part:
   The rule (§4) holds only where a declaration carries the annotation, and **nothing this
   language imports carries one**: re-measured, `userland/Foundation/` has **0** nullability
   annotations across **19 headers, 434 methods, 1716 lines** — and no `@property` at all, so
   it is a methods-only pass — and the vendored libobjc2 headers have 0 as well.
   - **No emitter trick can close the hole, and that is the new finding.** The obvious move —
     put the `#import` inside the generated header's `clang assume_nonnull` region, so the
     imported declarations are assumed non-null *and* clang complains about the ones missing a
     specifier — is **impossible**: measured, *"cannot #include files inside '#pragma clang
     assume_nonnull'"*. And an import *outside* the region is simply **unspecified**, which
     clang accepts in total silence. So the boundary offers neither a signal nor a mechanism,
     only a choice.
   - **The real question is therefore the language's default for an unannotated declaration**,
     and (a) cannot be the whole answer: a header we do not own would still arrive bare. So it
     is (b) or (c):
     - **(b) optimistic** — treat unannotated as non-null. Measurable as the *dishonest* one:
       clang assumes nothing, so nothing warns, and a Foundation method that returns nil flows
       into a non-optional as a silent no-op (a message to nil being ObjC-legal and quiet). A
       guessed non-null is exactly the silent wrong answer the arithmetic decisions (§7.40)
       and `as?` refused to make.
     - **(c) pessimistic — recommended** — treat unannotated as nullable. Sound by
       construction: the compiler never asserts what it has not been told, and the cost is
       *visible* (`!` or a binding) rather than silent. It also ships, with no Foundation work
       as a prerequisite.
   - **Which reframes (a).** Annotating the Foundation becomes a **quality task rather than a
     soundness one**: 434 declarations is a bounded pass over something we own, and each
     annotation *removes* `!`s from the surface rather than enabling correctness. So the
     ordering is **(c) now, (a) as a `foundation-plan.md` item** — and that is testable: after
     the sweep the `!`s should disappear and nothing else should change.
   - The hole is only on the *import* side. A Sterling-written header is annotated by
     construction, because the emitter opens its own `assume_nonnull` region (§4).
6. **Sending to an optional — CONFIRMED (2026-09): yes, and the result is a `T?`.** ObjC's
   `nil`-receiver rule makes `[nil foo]` already safe — which is why Swift needs a `?.` and
   Sterling does not — and §7.43's principle says that what ObjC accepts, this language accepts.
   So `x.foo` where `x` is `Foo?` is **allowed, yielding `T?`, at zero cost**; the error reading
   (`x!.foo` required) is what the type rule would say on its own, and the principle excludes it
   rather than a preference doing so.
   - **The confirm earns its own line because the two readings would emit different code.** The
     `?.` reading would need a construct of its own, and the error reading would need `!` at every
     optional send. Under the confirmed one, the emitted ObjC is the send itself — `[nil foo]` is
     valid — and no syntax is added at all. §7.43 is what decides this, and §7.43 is settled.
7. **Comma-separated bindings — DECIDED (2026-09): in v0.** `if let a = x, let b = y { … }` and
   the same list on `guard` are both valid. A binding is a binding, and one-construct-per-binding
   would be a restriction with nothing behind it.
8. **Does a class type erase to `id` in the emitted C? — DECIDED (2026-09): no, the concrete
   pointer stays.** The model is that a class instance *is* an `id` at the runtime level, and
   that is an **ABI** statement: the emitted type is the concrete pointer (`MyClass *`), which is
   what `id`-compatibility means at the ABI *and* keeps clang's own checking on the generated
   code — the second pair of eyes being the point of emitting readable ObjC. Literal `id`
   erasure is the other reading of "internally `id`", and it would discard that for no gain.
9. **Imported structs beyond the type name — DECIDED (2026-09): their fields read as dot
   members.** `Range` can be named and constructed (§6), **and `r.location` reads it** — §5's
   field rule already makes a struct's member a dot access, through the pointer where there is
   one. **And the value helpers pass through as ordinary imports — DECIDED (2026-09)**, with the
   idiom documented rather than a mechanism added. The bullets below are the reasoning, kept
   because they are the context any later reading of this rule will want.
   - **What the helpers are for, and why the question has weight.** A `Range` — or any struct,
     scalar or `Character` — is a *value* (§4), and §7.26's lightweight generics take **object
     types only**: measured, a struct as a type argument is *"neither an Objective-C object nor a
     block type"*. So a value cannot ride in an `Array`/`Dictionary` at all, and ObjC's answer is
     to **box** it in an `NSValue` — which makes these helpers the only route a value type has
     into a collection.
   - **This Foundation has no `NSValue` yet**, and `NSRange` is only ever *used*, never defined,
     in the tree (`NSArray.h` passes it in three signatures) — it comes from the imported system
     headers. So this half is a *class to add* as much as an interface to decide, the same shape
     as `NSNull`.
   - **And v0's work here is the documented idiom, not a language feature.** `NSValue.value(withRange:
     r)` and `v.rangeValue` are ordinary class and instance methods, so they need no syntax (§6);
     what the language owes an author is the *knowledge* that boxing is how a value enters a
     collection. A `Range`-typed convenience belongs in the Foundation as ordinary library code —
     the division §7.59 gives the inbound `NSNull`.
   - **Automatic boxing is not available**, tempting as it is: it would be a *bridge* rather than
     a re-spelling (§0), because it runs in both directions — box on write, unbox on read — and
     every box is a **new object**, so a read would not answer identity. §7.59's `nil` element is
     deliberately outbound-only for the same reason, and is a *same-value* re-spelling where
     boxing a struct is a wrapper.
10. **A struct's protocol conformance — DECIDED (2026-09): a compile-time error, enforced.** Its
    *inheritance* is settled — the mechanism is `-fms-extensions` and it is measured (§5, §7.16)
    — but `struct X: P` names a **protocol** in the inheritance list, and conformance needs a
    dispatch table, which is a mechanism rather than a re-spelling (§8). So that list takes a
    base struct and nothing else, and naming a protocol there is an error the compiler raises
    rather than a rule the author has to remember.
11. **Multiple annotations — DECIDED (2026-09, §7.15): each is its own keyword, so there is
    no list to ask about.** `readonly copy property x: String` rather than
    `property (readonly, copy) x: String` — the parenthesis mirrors ObjC's attribute list and
    remains available, but **keywords are preferred** (2026-09). The question below ("a list,
    or one at a time") dissolves: one spelling per attribute, and several of them before
    `property` accumulate in any order, since the emitted attribute list is a *set*.
12. **Overriding on a struct — DECIDED (2026-09): it is an error.** With no dispatch an
    "override" can only be a same-named method in the derived struct, and §5 already forbids
    redeclaring an inherited *property* — so the method-shaped sibling is an error too, for the
    same reason. Shadowing would look like polymorphism and behave like neither, which is the one
    outcome the layout-only rule exists to prevent.
13. **The tagged-union enum — settled in full (§7.35).** The declaration (§5), the
    way a case is named (§7.18), and each half that used to be open below. Kept
    because the reasoning is worth having; there is nothing left to answer here,
    except the multi-pattern spelling, which moved to §7.24:
    - **The payload arguments — settled (§7.35): the qualified, labelled
      construction**, `MyOtherEnumType.valueOne(intValue: 44)`, each label being the
      field's own name → a compound literal (§6). The plain-function-per-case
      alternative is dropped.
    - **Matching — settled in full (§6, §7.17, §7.24, §7.35): a `switch` on the
      case**, one form for both enum kinds, exhaustive and without fallthrough, each
      case a **braced block** — `case .valueOne { … }` — inside which the matched
      case's associated values are in scope as `const` variables. It is the only way
      to read a payload, so there is no accessor form and no `if case`.
    - **Equality — settled (§7.34): `==` on it is a compile-time error.** A tagged
      union is a struct in the emission (§5), and C has no `==` for a struct at all;
      here it would be unsound besides, because the payloads carry padding. So the
      answer to "how do I compare two of these" is the exhaustive `switch` two
      bullets up — which is what makes saying *no* to `==` affordable.
    Settled rather than open: such an enum **does** carry instance `method`s,
    lowered exactly as a struct's are — and it has no `class method` (§5, §7.25).
14. **The qualified access hides a C collision.** `MyEnumType.valueOne` reads as
    namespaced, but a **plain** enum's C enumerator is **bare** (§5) — so two
    plain enums in one translation unit with a same-named member collide as C
    enumerators, and the author cannot see it in the source, because both are
    written qualified. Options: **(a)** prefix plain enums' enumerators too (the
    source is qualified either way, so nothing is lost but the C reads less like the
    declaration); **(b)** leave them bare and let the C compiler report it;
    **(c)** detect the collision in `sterlingc` and report it as a language error.
    **DECIDED (2026-09): (a).** The emitted enumerator carries the type-name prefix —
    `MyEnumType_valueOne`, the same `TypeName_member` shape §7.25 gives a value type's accessor —
    so two plain enums cannot collide in the C even when they collide in an author's head.
    `sterlingc` could also have detected it **(c)**, but *preventing* a collision is the stronger
    rule than reporting one, and the surface is unaffected either way.
15. **Does the inference stop at literals? — DECIDED (2026-09): no. Full type inference is
    supported.** §7.19 was written for a literal initializer, which is the case it could state
    without a type-checker; an initializer's type now comes from **any** expression that has one
    — `let v = makeThing()` takes the call's return type, `let s = a.name` takes the property's.
    - **Where the expression has no type of its own the annotation is still required**, and that
      is the same rule rather than an exception to it: `let x = nil` and an empty collection
      literal (§6) supply nothing to infer from, so each is an error until the type is written.
    - **What this settles is the initializer, not a general inference system.** The item asked
      whether the *initializer's* inference stops at literals; it does not. Whether inference
      reaches, say, a closure's parameter types is a different question and is not answered here.
16. **Where does a stored property's default go? — DECIDED (2026-09): in the declaration.**
    `property x: Int32 = 0` — a property *does* take an initializer form, and a **`readonly`
    property with no getter must use it**, because nothing else could ever give it a value (§5,
    §7.54). That settles the neighbouring question too: an initializer's body may **not** assign a
    `readonly` property (§9.25) — the declaration is the one place its value comes from.
    - **It is a *class* rule, which the struct correction makes explicit.** A struct has no
      synthesised property (2026-09, §5's Struct), so there is no struct shape for this rule to
      apply to: a struct's state is a `var` field carrying its own initializer —
      `var x: Int32 = 0` — and a struct property is an accessor over it. What the rule above
      describes is a *stored class property*.
    - **The emission — DECIDED (2026-09): a synthesised *defaults* method, called by every
      initializer.** Measured first: **neither an ObjC ivar nor a C struct member may carry an
      initializer** — `int32_t x = 7;` in an `@interface`'s ivar block, and in a `struct`, are
      each *"expected ';' at end of declaration list"* — so the declaration states the value and
      generated code applies it. The mechanism is the emitter's own method, one per class that has
      defaults, and every initializer calls it in a fixed three-step order, measured as compiling
      clean under ARC:
      1. **`self = Superclass()`** — the chain §7.49 requires;
      2. **the synthesised defaults**, applied to `self`;
      3. **the author's body**, whose own assignments therefore win.
      - **The order is not arbitrary: the chain comes first.** An ObjC initializer may return a
        *different object* from the one it was sent to — which is exactly what the chain is for —
        so anything written before it could be written into an object that is then discarded.
        "Before the body" is the rule; "before the initializer" would be the bug.
      - **It is per class and recursive by construction.** Each class's own initializer applies
        its own defaults, so the chain applies them from the root down, and a subclass's defaults
        may rely on state its base has already set.
      - **A struct takes the same shape through its constructor function** (§7.8), a value type
        having no `init` method to call: the function applies the field defaults and then the
        caller's arguments.
      - **The defaults method is the emitter's, not the surface's.** It is internal to the
        generated unit — `private` in §7.57's terms — and an author never names it.
      - **And no synthesised `init` is added — DECIDED (2026-09): a declared initializer is
        required.** A class with defaults but no initializer of its own is not constructible, and
        that has to be the *language's* rule rather than a consequence of the emission: measured,
        a subclass that declares no initializer is **still constructible in ObjC**, because `init`
        is *inherited* — `[[Sub alloc] init]` compiles against the superclass's. So nothing in the
        C would stop `Sub()` from getting the base's initializer and none of `Sub`'s defaults. The
        compiler is what refuses it.
      - **A struct is untouched by that requirement.** Its construction is §6's literal and
        §7.8's constructor function, which every value type already has; what is required is a
        *class's* declared initializer.
17. **Do the numeric types convert implicitly? — DECIDED (2026-09): no. A
    conversion must be written, and it may only go *up* (§7.39).** So
    `let a: Int64 = anInt32` is **not** allowed — it is
    `let a: Int64 = Int64(anInt32)`. `Int16(anInt8)` is valid; `UInt32(aUInt64)` is a
    compile-time error; and — the part that follows from *not promoting* — `x + y` of
    two `Int8`s is an `Int8`, not the `int` C would have made of it. The rephrased
    question above is answered no: the conversion is always written, which is what
    leaves the up-only rule as the only thing there is to check.
18. **Is the raw pointer parameterized, and what is `void **`? — DECIDED
    (2026-09): yes, and the settled pair becomes its *pointee-less* case.** The two
    mappings are settled — `void *` is `UnsafeMutablePointer`, `const void *` is
    `UnsafePointer` (§4) — and they arrive *unparameterized*, which is unambiguous
    only while every pointer has `void *`'s shape. **Lightweight generics cannot
    help**: that mechanism parameterizes ObjC *class* types — a protocol
    declaration cannot even take a parameter (measured, §5) — and a raw pointer is
    not one. This is not a corner: an Objective-C out-parameter is a *typed*
    pointer (`NSError **` in this Foundation's own API, `NSString **` in the
    classes it has yet to grow), and `char *`, `int32_t *` and `struct timeval *`
    are the rest of the C surface the prelude imports.
    **The rule.** Bare `UnsafeMutablePointer` stays `void *`, and adding a pointee
    makes it typed — so the settled mapping is a special case of it instead of a
    second mechanism, and there is one story:

    | surface | emits |
    |---|---|
    | `UnsafeMutablePointer` | `void *` |
    | `UnsafeMutablePointer<Int32>` | `int32_t *` |
    | `UnsafePointer<UInt8>` (the const form) | `const uint8_t *` |
    | `UnsafeMutablePointer<Point>` (a struct) | `Point *` |
    | `UnsafeMutablePointer<Error?>` | `NSError * _Nullable * _Nonnull` |
    | `UnsafeMutablePointer<UnsafeMutablePointer<Int32>>` | `int32_t **` |

    Two codegen rules fall out of it, and the first is measured rather than
    guessed:
    - **A class-typed pointee needs an ownership qualifier on the inner pointer,
      and ARC makes it mandatory.** Written plainly, `Err * _Nullable * _Nonnull`
      is a *hard error* under `-fobjc-arc` — *"pointer to non-const type 'Err *
      _Nullable' with no explicit ownership"* — while `Err * __autoreleasing *
      _Nonnull` compiles clean, and a *scalar* out-parameter (`int32_t *`) needs
      nothing at all. So the emitter inserts `__autoreleasing` exactly when the
      pointee is a class type — **decided (2026-09): it stays an emitter inference,
      and the source never spells ownership.** A source-level annotation would buy
      only the object-pointer table below, which is out of scope anyway — a
      spelling with one user.
    - **Each pointer level carries its own nullability** (§4), and the common
      out-parameter needs only the inner one: `UnsafeMutablePointer<Error?>` is a
      non-null slot that may hold a null object. Writing both levels is legal and
      rare.
    *Rejected (2026-09), and recorded so it is not re-opened: one more **untyped**
    name for `void **` plus a cast at every boundary. It keeps the type system
    closed — over the wrong thing: `char *` and `int32_t *` become one type, so
    clang stops checking exactly where the surface promised it would, and the
    emitter pays for the closure in casts.*
    *Out of scope in v0, and the honest boundary: a **table of object pointers**
    (`NSArray`'s internal buffer, an `id **` that is not an out-parameter), because
    the elements' ownership there is `__strong`, not `__autoreleasing`. It is the
    same absence the language has wherever a C-level qualifier has no surface
    spelling.*
19. **What is `char`? — DECIDED (2026-09): `Character`, a single UTF-8 byte.** It
    emits C's `char` — *not* `uint8_t`, and that is the load-bearing part: an
    imported `strlen(const char *)` or `- (const char *)UTF8String` must accept a
    `Character` pointer with no cast, and `unsigned char *` does **not** satisfy a
    `char *` parameter (measured: this toolchain reports no viable conversion — an
    error, not a warning). `Character` is therefore a *third* name beside
    `Int8`/`UInt8`, and it exists because C's `char` is a third type.
    - **Measured, and worth saying out loud: `char` is *signed* on this target**
      (`CHAR_MIN` is −128). So a `Character` holding a UTF-8 byte ≥ 0x80 reads
      **negative**: `c == 0xC3` is false for the byte 0xC3, because the literal is an
      `Int` and the `Character` is −61. Decoding UTF-8 therefore goes through the
      byte conversion (§9.17) rather than a bare compare — and that is a
      property of C's `char`, not of this mapping. *(This corrects the claim that
      briefly stood here: that `char` is unsigned on this target. It is true of
      `BOOL`'s carrier — which is what §4's note is about — and false of `char`.)*
    - **The alternative — emitting `unsigned char`, for honest 0–255 bytes — was
      rejected** because it moves the cost to every imported signature: a cast at
      each `char *` boundary, which is precisely the friction this language exists
      to remove.
    - **How a `Character` is written — DECIDED (2026-09): `'a'`, and it *is* a `Character`, not an
      `int`.** The language takes C's spelling and gives it the language's type, so the emission is
      a cast to C's `char`: `(char)'a'` — which is the whole of the difference, C's own `'a'` being
      an `int`. §7.38's guess at `Character(65)` is superseded; `Type(value)` remains what it
      always was, a *constructor call* for the numeric family (§7.38).
    - **A multi-byte character literal is a `String` — DECIDED (2026-09).** So a `'…'` literal is
      typed by its **byte count**: one byte is a `Character`, more than one is a `String` — an
      `NSString` literal in the emission (`@"é"`). Both emissions are measured as compiling clean:
      `(char)'a'` for the one-byte case and `@"\xC3\xA9"` for the multi-byte one, so the escapes
      serve either and `'\xC3'` is still a `Character`.
      - **The two are not interchangeable, which is the same rule as everywhere else** (§7.39):
        `let c: Character = 'é'` and `let s: String = 'a'` are both errors — the literal's type is
        what its bytes say, and nothing converts between them implicitly.
      - **The `String`'s length is a byte count here**, which is this Foundation's declared
        deviation rather than anything about literals: `'é'` is two bytes and reports 2.
      - **The empty literal `''` is a `String` with no content — DECIDED (2026-09): nothing but
        the terminating NUL.** Zero bytes is not a `Character` by the byte-count rule above, and it
        is not an error either — it is the empty string, which is what makes the rule a count
        rather than a special case.
20. **What does `==` mean on a class-typed value? — DECIDED (2026-09): it emits
    `[a isEqual:b]`.** Making `String` an `NSString` (§7.31) put this in front of a
    reader for the first time: C's `==` on two objects is *pointer* identity, so
    `a == b` would be false for two equal but distinct strings — surprising, and
    silently so, which is the worst kind. The decided spelling needs no new
    mechanism, because `Object`'s own `isEqual:` *is* pointer identity: it degrades
    to C's meaning for a class that does not override it, and becomes value equality
    for the ones that do (`String`, `Number`, `Data`, the collections). `!=` is its
    negation, `![a isEqual:b]`. Keeping pointer identity was rejected as honest
    about the C and wrong about the language: it would make `String` the one type
    whose `==` does not mean what a reader expects.
    - **Measured, and it is why the decision is safe:** this Foundation's `Object`
      declares `- (BOOL)isEqual:(id)other;` (`foundation/NSObject.h:145`), and a
      receiver whose class chain does *not* declare it is a **warning**
      (`-Wobjc-method-access`, *"instance method '-isEqual:' not found"*) rather
      than an error, with exit 0. So the prelude supplies the declaration in every
      ordinary case; the one that would warn is a Sterling **root class** that
      declines to declare it — a class that is not an `Object`, and so has no
      inherited notion of equality to be right about anyway.
    - **`==` on a *struct* is a compile-time error — DECIDED (2026-09, §7.34).** C
      has no `==` for a struct at all, so the honest re-spelling is to forbid it
      rather than invent memberwise equality; and for a tagged union it would be
      unsound regardless, because the payloads carry padding. That closes §9.13's
      equality sub-item too, since a tagged-union enum **is** a struct (§5).
21. **What happens to arithmetic that overflows its own type? — DECIDED (2026-09): it
    traps, signed and unsigned alike** (§7.40). The item went through three positions
    in one sitting, and they are worth summarising, because each was defensible and
    only the third is the language's:
    - *Inherit C's rule* — unsigned wraps (C defines it), signed is UB. Rejected:
      inheriting UB is not an answer.
    - *Wrap everywhere* — give signed overflow the defined result unsigned has, by
      emitting through unsigned. Free (measured) and coherent, but it chose cost over
      meaning: `Int8(100) + Int8(100)` quietly answering `-56` is a wrong answer where
      the author wanted 200.
    - **Trap everywhere, with explicit wrapping operators — the decision.** A stop beats
      a wrong answer, and `&+` / `&-` / `&*` keep the deliberate cases writable (§7.40).
      It is Swift's model exactly.
    A *compile-time* error was never available in general, and that is not a shortcoming
    of the design: overflow is a property of **values**, not of types, so the only sound
    type-level rule would be "no signed arithmetic at all" — or a range/dependent type
    system, which is a different language. The compiler's part here is §7.38's: refuse
    what it can *prove*, and let the runtime catch the rest.
22. **The UB with nothing to wrap to — DECIDED (2026-09): it traps, all three cases.** Division
    or modulo by zero, an out-of-range shift count and `INT_MIN / -1` are not overflow, so §7.40
    does not reach them by name — but the stance does: the language does not hand an author UB,
    and each of these is UB in the C it emits.
    - **How each is emitted, measured.** `__builtin_add_overflow`, `__builtin_sub_overflow` and
      `__builtin_mul_overflow` all exist for §7.40's arithmetic, but **clang has no division or
      shift builtin at all** — `__builtin_div_overflow`, `__builtin_sdiv_overflow` and
      `__builtin_shift_overflow` are each *"undeclared identifier"*. So these three are **guards**,
      on the same header-only footing as `STERLING_UNWRAP`: a `sterlingc_trap_*` entry beside
      `sterlingc_trap_overflow`.
    - **`INT_MIN / -1` traps because it *is* an overflow**, which sharpens what this item used to
      say. `2^31` does not fit an `int32_t`, so §7.40 already covers it; the machine's `INT_MIN`
      is the wrap, not the result. It needs no semantics of its own — only the guard C's `/`
      requires, and the unsigned trick that fixes `+` produces no answer for it (it computes
      `2^31 / (2^32 − 1)`, which is 0).
    - **The shift count traps too, and masking is rejected.** Masking to the type's width is what
      the hardware does and gives a defined answer, so `a << 40` *could* have meant `a << 8` — but
      that is the same class of quiet wrong answer §7.40's trap was chosen to refuse. Answering
      `a << 8` when the author wrote `40` is exactly what `Int8(100) + Int8(100)` answering `−56`
      was. One stance, one rule.
    - **A provable shift count is a compile-time error rather than a trap** — §7.40's own division
      of labour, "refuse what it can *prove*, and let the runtime catch the rest". Measured, the
      proof is available: clang itself warns on a *constant* count (`-Wshift-count-overflow`,
      *"shift count >= width of type"*), so the compiler can refuse that case outright. A count
      that is a *value* traps at runtime, which is where clang says nothing at all.
23. **What is a null *element*? — DECIDED (2026-09, §7.59): it is `nil`, converted on the way out.**
    `nil` is the only visible null value in Sterling (§4), and the emitter converts it to whatever
    the context needs — `[NSNull null]` in a collection slot, `NULL` for a raw pointer, `false` for
    a `Bool`. So an `Array<Number?>` **is** expressible, and a `nil` written for a slot emits the
    singleton. The question this item opened — *would that be a bridge?* — is answered **no**: the
    author writes one word and the C gets a different one, which is the same surface/emission split
    as `0o755` → `0755`, so §0 is untouched.
    - **The naming half stays as §7.31 gave it** — `NSNull` ⇄ `Null` — refined by §7.59: `Null` is
      a *type* and never a value. `Null()` is not how the singleton is reached; writing `nil` is the
      whole of it, and the class is named only in declarations.
    - **What is worth knowing instead is the asymmetry** (§7.59): the conversion is outbound only,
      so a legacy untyped API hands back the singleton object rather than `nil`. The typed Argentum
      collections absorb that in their own accessors — ordinary library code, not a mechanism the
      language needs.
    - **Two earlier positions in this item are withdrawn.** It first feared a *bidirectional*
      bridge, then answered the naming question with a `func` bridge (§7.56's misreading of §7.25).
      Both were working around a null the language did not have; the decision gives it one, and both
      workarounds go with it.
24. **How is a class method *called*? — SETTLED, and the item was mistaken; kept as a pointer.**
    A class-method send goes to the class object, and §6 already says the **receiver may be a
    class**: `MyClass.baz(arg1: 1)` → `[MyClass baz:1]`, with §3's map carrying the same row. So
    `class method foo(bar baz: Type) -> Void` is called `Foo.foo(bar: value)` — confirmed
    2026-09 (§7.58), and no separate call form was ever needed.
    - **What the item got wrong was the reason it thought the question was open.** It claimed the
      dot is not part of the surface; §6's *first line* says the opposite — *"the dot is the whole
      of the spelling"* — and that sentence covers the class receiver in its second bullet. So the
      three candidates it listed were never candidates, and the bare-`func` bridge §7.56 invented
      was doubly unnecessary.
    - **Kept rather than deleted because the wrong turn is easy to take twice.** A class method
      *looks* like the one thing the call syntax cannot express, and it is the one thing §6 had
      already covered — which is worth a line to anyone who reaches the same conclusion.
    - **Confirmed in the no-argument form too (2026-09): `ClassName.classMethod()`** — and the
      parentheses are *not* optional. §7.60 once permitted dropping them and has been withdrawn:
      `ClassName.classMethod` without them cannot be told from a bare name. One call form, one
      spelling.
25. **What must an initializer's body do? — all three of its questions are now DECIDED
    (2026-09).**
    - **It returns `self` implicitly — decided (2026-09, §7.49): the body writes no `return`.**
      The emitter supplies `return self;`, because ObjC's `- (instancetype)init` has to return the
      object; an explicit `return self` states the default and is accepted and ignored. That
      retires the guess the example class made.
    - **It may *not* assign a `readonly` property — DECIDED (2026-09): the declaration is where
      that value comes from.** A `readonly` property with no getter is a stored one and must carry
      its value in its own declaration (§5, §7.54, §9.16), which leaves an initializer nothing to
      do. Swift's answer was the other one, and this language's is the stronger guarantee: a
      `readonly` property is fixed where it is written, not merely unassignable everywhere else.
    - **What supplies `self = [super init]` — DECIDED (2026-09): the author does, explicitly.**
      A subclass's initializer must chain with `self = Superclass()` (§7.49), which emits
      `self = [super init]` rather than a fresh `[[Superclass alloc] init]`, so the object being
      initialized is the one kept. It is not automatic: the language supplies the `return`, and
      the author supplies the chain.
    *This item is kept although every question in it is settled, because all three were found by
    writing a single example class — which is the shape of the thing that will find the next one.*
